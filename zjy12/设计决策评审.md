## 一、🔴 A 类：事实性错误

### A1. 7.1 把 `Qwen-Audio-ASR` 当成流式候选，归类可能错误

7.1 表格把「阿里 Paraformer / Qwen-Audio-ASR」并列在同一格，暗示两者都是流式实时识别。

- 阿里的**流式实时**识别产品线是 **Paraformer-realtime**（FunASR 系），有明确的中间结果 + 独立 finalize 语义；
- **Qwen-Audio 系列**长期是"离线音频理解"模型（整段音频 → 文本/理解），不是流式 ASR 接口。即便新版本提供了流式能力，其接口形态、中间结果粒度、finalize 行为都需要单独核实，**不能和 Paraformer 当成同一类东西**。

**建议**：拆成两行，并在 7.2 的实测项里加一条「是否提供**独立的 finalize 接口**（而不是靠停止发送隐式结束）」。这一条直接决定 7.3 双引擎能不能做。

### A2. 5.3「WiFi 抖动时丢最旧，不丢最新」—— 对上行语音是错的

原文：`WiFi 抖动时丢最旧，不丢最新：保留最新音频才有意义`

这条策略适用于**实时视频 / 状态同步 / 遥测**这类"最新值即全部信息"的流。**上行语音是 ASR 的输入，每个采样点都是不可替代的信息**。丢最旧等于把"你好，我想问一下"削成"问一下"，ASR 直接识别成别的话，整轮答非所问——这恰好违反第七节自己定的原则「ASR 听错一个关键词，整轮答非所问」。

缓冲满时的正确优先级：

1. **反压**：阻塞 I2S 读取任务（RingBuffer 满就不读），让 DMA 自然溢出丢最旧的**采集侧**数据——但要在采集侧丢，不是在发送侧丢，且要计数上报；
2. **降码率**：切 Opus 低码率（这跟 9.2 第 7 条"先别上 Opus"冲突，见 D5）；
3. **显式失败**：超过阈值直接提示"网络不太好"，让用户重说。**静默丢音频是最差的选择**，因为它把网络问题伪装成 ASR 不准。

**建议改写**：`发送缓冲满 → 先反压采集；持续 >500ms 则上报网络劣化并提示用户；绝不静默丢弃已采集的音频帧。`

### A3. 第二节「与权利方**或**配音演员签授权」—— 这个"或"是错的

声音上的权利至少有两层，主体不同：

| 权利 | 主体 | 内容 |
|---|---|---|
| 著作权（录音制品） | 版权方 / 制作方 | 复制、信息网络传播 |
| **表演者权（邻接权）** | **配音演员本人** | 许可他人录音、复制、发行、信息网络传播 |

只拿到版权方授权、没拿到配音演员授权，仍然是侵权的。所以不是"或"，是**"和"**——两份都要。

**建议改写**：`必须同时取得「录音制品著作权人」与「配音演员（表演者）」的书面授权，两份缺一不可。`

### A4. 9.4 分区表里的 `model, data, spiffs, 2M` 是唤醒词时代的残留

设计已经明确取消 WakeNet（4.1）、三个模型全在云端（第三节），**板子上没有任何模型文件**。这块 2MB 的 `model` 分区没有归属。

同时分区表还有两个问题：

- `0xA20000 + 2M = 0xC20000`，到 16MB 顶部还空着 **3.875MB 未分配**；
- **没有 `coredump` 分区**。调试期崩溃无法取证，这是最影响开发效率的一项，成本只要 64KB。

**建议**：`model` 分区改名 `assets`（放提示音、思考音变体、OTA 校验清单），或直接删掉把空间并给 `storage`；新增 `coredump, data, coredump, , 64K`。

## 二、🔴 B 类：文档内部逻辑冲突

### B1. 「说话」状态下按一下，是打断还是挂断？

| 出处 | 原文 | 语义 |
|---|---|---|
| 4.3 表格 | 说话 → 按一下 → "打断，回到聆听" | 打断 |
| 4.4 条件 2 | "再按一下按键（挂断）" | 挂断 |

同一个物理动作，两个定义。而且这两个状态是重叠的——"正在说话时想挂断"是真实场景。

**建议**：定义成**短按 = 打断，长按 ≥600ms = 挂断**（或双击挂断）。写进 4.3 的表格，4.4 改成引用 4.3。

### B2. 5.1 说「第一版用 HTTP 后面等于重做」，十一节阶段 1 又写「PTT + HTTP」

- 5.1：`若第一版用 HTTP，后面改 WebSocket 基本等于重做。`
- 十一节阶段 1：`按住说→松手→听到角色回复（不做 AEC、不流式）`

5.1 的本意应该是「**协议按帧设计，传输层可以先一次性发**」，但"阶段 1 用 HTTP"这句话会让人真的去写一个 HTTP POST 接口。

**建议**：阶段 1 改成 `PTT + WebSocket（一次发送整段，不分片）`。传输层不变、只变发送节奏，这才是 5.1 想表达的。HTTP 只用于**离线调试脚本**，不进固件。

### B3. 6.5「不要牺牲稳定性」与「下行 16k PCM 直传」自相矛盾

- 4.5 / 9.2-3：下行用 16kHz PCM，理由省解码 ~100ms；
- 6.5：`把播放缓冲从 200ms 压到 80ms 能省 120ms，但 WiFi 一抖动就断音……这个交换不划算。`

但 16kHz/16bit 单声道 PCM = **256 kbps**，是 MP3 64kbps 的 **4 倍**，是 Opus 24kbps 的 **10 倍**。为了省 100ms 解码延迟，把带宽需求抬高 4–10 倍，在同样的 WiFi 抖动下**卡顿概率显著上升**——这恰恰是 6.5 要避免的交换。

这不是说一定要改，而是**文档必须把这个交换摆到明面上量化**，而不是只写"省解码"。

**建议**：加一张对比表（延迟 / 码率 / CPU / 抖动敏感度），并给出决策依据。个人倾向：**阶段 1–2 用 PCM 直传（简单、可调试），阶段 3 流式改造时同步引入 Opus 32kbps**，因为阶段 3 本来就要重做音频管道。

### B4. 8.4「分段策略固定」与流式 TTS 的固有分段冲突

- 8.4-3：`分段策略固定：同一文本不同切法，拼接处会有轻微音色跳变`；
- 但流式 TTS 的**本质**就是按到达的文本增量分段合成，切点由网络和 LLM 出字节奏决定，不可能"固定"。

两者无法同时满足。真实的可选项只有三个：

| 方案 | 延迟 | 音色一致性 |
|---|---|---|
| 整句合成完再播 | +300~600ms | 最好 |
| 流式合成，接受切点抖动 | 最优 | 拼接处可能跳变 |
| 流式合成 + **切点规则**（只在句末标点/逗号处切，不切在词中） | 折中 | 可控 |

**建议**：明确选第三个，并把"切点规则"写进协议——**网关负责在标点处切分文本再送 TTS**，不要依赖 TTS 服务自己切。这条同时解决 8.3 的情绪标记边界问题（见 C3）。

### B5. 4.5 的「唤醒后无语音 5s 提示」是术语残留，且与 4.4 的退出计时器关系未定义

4.1 已经明确取消唤醒词，4.5 却写 `唤醒后无语音 | 5s 提示，8s 退出 | 主动问"还在吗"`。

更实际的问题是：4.4 有 4 个退出条件，其中「连续 30 秒无有效输入」和「连续 2 次识别为空」，加上 4.5 的「5s 提示 / 8s 退出」，**一共三套计时器**，彼此关系完全没定义：

- 按键后 5 秒没说话 → 提示"还在吗"。这算不算"识别为空"1 次？
- 提示后又过 3 秒还是没说话 → 8 秒到了，退出。那"连续 2 次识别为空"什么时候才触发？
- "连续 30 秒无有效输入"和"8 秒退出"，哪个优先？

**建议**：画一张状态机图，把计时器画进去。文字描述状态机一定会漏。

### B6. 4.3 的状态机缺一个状态：**思考中**

4.3 只列了 待机 / 聆听 / 说话 三态。但在 1.2s 目标下，从"用户说完"到"首字出声"之间有 0.8–1.5 秒的空档（ASR finalize + LLM TTFT + TTS 首包）。这个状态下用户按一下键，会发生什么？文档没定义。

不定义的结果：用户按了没反应，会连续按，触发 B1 的歧义。

**建议**：加第四态「思考中」，按一下 = **取消本轮，回到聆听**。这一态同时是 6.4「思考音」的挂载点。

### B7. 硬件清单里没有按键、没有灯，但交互设计完全依赖它们

9.1 清单只有：主控 / 麦克风 / 功放 / 喇叭 / 电源。

但：

- 4.1：`按键是唯一入口`；
- 4.4：`退出必须有收尾反馈（提示音 + 灯光熄灭）`；
- 9.3-1：SoftAP 配网——**没有屏幕，怎么知道配网成功了？只能靠灯**。

**建议**：补 `按键`（建议轻触 + 硬件消抖，或 EC11 编码器兼音量）、`RGB 灯环`（WS2812 8 灯，兼配网状态指示）、`电量检测`（若走电池）。

**这是全文最大的空白**，单独在第四节展开。

### C2. VAD 到底在本地还是云端？三处提法互不相容

| 出处 | 说法 | 隐含归属 |
|---|---|---|
| 4.5 | 静音判定 600ms / 800ms 动态调整 | 未指定 |
| 5.3 | `本地 VAD 门控能省流量` + pre-roll 300ms | **本地** |
| 7.3 | `VAD 检测到尾点后用精度更高的模型出终稿` | **云端**（要用 ASR 中间结果做语义端点，只能在云端） |

这三者不是同一个 VAD：

- **本地 VAD**：能量/过零率，粗但快，负责"要不要开始上传"和"是否在说话"；
- **云端 VAD**：服务端自带的端点检测，负责切句；
- **语义端点**：用 ASR 中间结果的文本完整性判断"用户说完了"，比前两者准 200–400ms。

必须写清三者的**层级和优先级**，否则协议里"谁来发 end-of-speech"这件事永远定不下来。

**建议**：本地 VAD 只管"开始/静音省流"，**end-of-speech 一律由云端决定**（云端同时掌握能量 VAD 和 ASR 中间结果，判断依据最全），板子只负责在本地 VAD 判定静音后**停止发送**（不是发结束信号）。

### C3. 情绪参数通道与流式输出根本冲突（🔴 建议提升为 A 类）

8.3 的做法：

```
（微笑）→ emotion=warm → TTS happy / 语速 1.0
```

要实现它，LLM 必须**输出结构化的情绪字段**。但：

1. 纯 JSON 输出会显著降低中文自然度（模型把注意力花在格式上）；
2. **更致命**：流式播放在拿到第一句文本时就要送 TTS，此时 JSON 还没闭合，**无法解析**。等 JSON 完整 = 放弃流式 = 放弃 1.0–1.2s。

三条可行路线：

| 方案 | 做法 | 代价 |
|---|---|---|
| **行首标记**（推荐） | 约定每行以 `[warm]` 这类**轻量标记**开头，标记本身闭合，可以边出边解析边播 | 需要 few-shot 教会模型稳定输出；标记本身不能念出来 |
| 双通道 | 文本流 + 情绪字段走独立 SSE 事件 | 协议变复杂，两路要对齐 |
| 后置推断 | 不要求 LLM 输出情绪，用规则/小模型从文本推断 | 准确率低，但零延迟、零格式约束 |

**建议**：行首标记 + 严格 few-shot，并且**把标记解析放在网关**（不放板子）。8.3 现在只写了"必须清洗"，没写"怎么在流式下拿到情绪"。

顺带：8.3 的清洗规则要限定为「**只清洗行首或独立成段的括号**」，否则角色台词里合法的括号（比如引用书名、台词）会被误删。

### C4. 全文没有 LLM 选型，也没评估项目里已有的 zjy7 角色 LoRA

8.1 花了整节讨论"助手本能在压过人格"，但**通篇没说用哪个 LLM**。6.2 只写「LLM 换首 token 快的模型 ~100ms」，连候选都没有。

更关键的是：**这个仓库里已经有一个为同一角色训练好的 LoRA（zjy7，`qwen3.5:9b-gguf` + `elysia-lora`）**。文档完全没提。

这不该被忽略，因为三条对比对决策影响很大：

| | 云端 API（豆包/通义） | 本地 Ollama（zjy7 LoRA） |
|---|---|---|
| 人设稳定性 | 靠 prompt 硬撑，OOC 风险高（8.2 自己承认） | LoRA 微调过，人设是"长"在权重里的 |
| TTFT | 300–800ms | 本机 5070 实测需测（9B 约 200–500ms，取决于上下文长度） |
| 成本 | 按 token 计费 | 0 |
| 可用性 | 依赖公网 | 依赖本机开机 |
| 可维护性 | 改 prompt 即生效 | 改人设要重训 |

**建议**：至少做一次 A/B——同一批 OOC 诱导集（8.6 那 20 条），云端模型 vs zjy7 LoRA 各跑一遍。如果 LoRA 明显更稳，架构上应该保留"LLM 可切换"的抽象，而不是写死云端。

### C5. 会话状态与记忆持久化完全没设计

- 设备断电、重启、换房间之后，角色还"记得"上次聊到哪吗？
- 会话是保存在云端网关的内存里、Redis 里、还是数据库里？
- 板子断线重连（WiFi 漫游）后，是恢复原会话还是开新会话？

这是**角色扮演类产品的核心体验**（"她记得我"），也是这个仓库 zjy9 已经解决过的问题（混合检索记忆库 + 会话表）。文档一句都没写。

**建议**：明确「会话 ID 由云端下发、板子持久化在 NVS」+「断线 30s 内重连可恢复同一会话」。记忆摘要（8.2 的"人格锚定"）落库，不落板子。

### C6. `cancel` 帧有竞态，需要世代号

5.3 写了 cancel 帧，但没有防竞态：

1. 用户打断，板子发 cancel 并清空播放缓冲；
2. cancel 到达云端时，TTS 已经合成了第 2、3 段音频，正在回传途中；
3. 板子已经清空了缓冲，这**迟到的两段音频会被当成新一轮的回复播放出来**——用户听到的是上一轮的残句。

**建议**：所有下行音频帧带 `epoch`（每次新的用户轮次 +1），板子只播 epoch 等于当前值的帧，旧 epoch 一律丢弃。这个字段现在加成本几乎为零，后期加要改协议。

### C7. 没有失败模式与降级设计

一个只写了 happy path 的设计文档，在联调第一周就会被现实击穿。至少需要定义：

| 失败 | 用户看到什么 |
|---|---|
| WiFi 断（按键时无网） | ？ |
| ASR 超时 / 返回空 | ？ |
| LLM 超时（4.5 说 8s 说"信号不太好"） | 已定义 ✅ |
| TTS 失败（音色服务挂了） | ？ |
| 云端网关 5xx / 限流 | ？ |
| 音频流中断（播到一半） | ？ |

**建议**：加一张失败模式表，每行给「检测方式 / 用户提示（用角色的口吻说，不是系统提示音）/ 重试策略 / 是否计入退出条件」。注意：**角色设备不能用"网络错误 500"这种提示**，要用世界观内的话术——这本身是产品设计的一部分。

### C8. 没有隐私与合规设计

- 语音是**敏感个人信息**（《个人信息保护法》第 28 条），需要**单独同意**，不能混在通用隐私政策里；
- 云端是否留存音频？留存多久？ASR 厂商默认是否用于模型训练？（阿里/火山都提供"不用于训练"的开关，需要显式关闭）
- 设备一直在录（会话模式自动循环），"不按键不录音"这个卖点（4.1 理由 5）在会话模式里**不成立**——会话中麦克风是常开的。这一点文档自己没意识到。

**建议**：加一节「数据与隐私」：会话中麦克风状态的可视指示（灯环颜色）、音频不落盘、厂商侧关闭训练开关、单独同意流程。

### C9. 分区表留了双 OTA 分区，但全文没有 OTA 设计

`ota_0` / `ota_1` 各 4MB，说明打算做 OTA，但正文一个字没提：怎么触发（按键组合？配网页面？）、怎么校验（签名？）、怎么回滚（新固件起不来怎么办）、怎么防砖。

**建议**：要么补一节 OTA，要么把双分区砍掉换成单 app + 更大 assets（省 4MB）。不要留着一个"看起来支持但没人实现"的结构。

### C10. 没有成本预算，且 7.5 的推荐与 7.7 的数字打架

7.7 自己算出来：150 万字/月 → **阿里 300 元/月，火山 1950 元/月**（6.5 倍差）。
7.5 却推荐「**先用同一家（火山）跑通**」。

这笔账对个人开发者不成立。而且 7.7 只算了 TTS，**ASR 和 LLM 的成本完全没算**——ASR 按音频时长计费，会话模式下"一直录"意味着**待机也在花钱**（见 C2 的 VAD 和 4.4 的 30 秒退出）。

**建议**：

- 补一张「全链路成本表」：ASR（按分钟）× LLM（按 token）× TTS（按字符），分「原型期（20 轮/天）」和「试用期（200 轮/天）」两档；
- 7.5 的推荐改成「**ASR + LLM 用火山（准确率和生态优先），TTS 用阿里 CosyVoice（成本差 6 倍，且支持声音设计——正好是第二节的出路 2）**」。这样反而更符合文档自己的逻辑：TTS 换厂商成本高，那就**一开始就选便宜且能合法生成音色的那家**。

### C11. 厂商账号与资质门槛没验证

两个可能直接卡死原型的现实问题：

1. **声音复刻功能的审核**：火山「声音复刻」、阿里 CosyVoice 的 zero-shot 复刻，上传音源时**都要勾选授权承诺**，部分还要求上传授权书。用未授权的角色音源，**可能在原型阶段就被厂商审核拒绝**，或者违反服务条款。文档说"内部原型验证可以用现有音频"，但这一关在厂商侧，不在自己手里。
2. **深度合成服务备案**：备案主体是"服务提供者"，个人开发者基本无法完成（需要企业主体 + 算法备案）。这意味着**"公开发布"不是"上线前再解决"，而是"个人身份下不可能"**。

**建议**：这两条要在第二节里明确写成"**硬性前置条件**"，并调整路线——**阶段 1–3 全程使用合法的占位音色**（CosyVoice 声音设计生成的原创音色），把"角色音色"当成**可替换资产**，最后再决定要不要换。这样即使授权拿不到，产品也不会推倒重来。

## 四、延迟预算：文档最缺的那张表

### 4.1 为什么必须现在算

6.2 给的是「**优化能省多少**」（自顶向下），但没有「**基线是多少**」（自底向上）。两者对不上时，目标就变成了愿望。

另外 6.2 的收益**不能线性相加**：

- 「ASR 并行化 ~500ms」与「上传与录音并行 ~200ms」高度重叠（都是把串行变并行）；
- 「语义端点 ~450ms」本质是**把 600ms 固定静音换成 150–200ms 的语义判定**，它和 4.5 的「静音判定 600ms」是**互斥选项**，不是可叠加的两项优化。

按 6.2 简单相加得 1500ms 的节省，是虚高的。

### 4.2 自底向上加总（按文档自己的参数）

测量点：**用户说完最后一个字 → 喇叭发出第一个字**。

| # | 环节 | 乐观 | 中位 | 悲观 | 依据 |
|---|---|---|---|---|---|
| 1 | 说完 → 判定说完 | 150 | 600 | 800 | 语义端点 150 / 4.5 固定静音 600–800 |
| 2 | 末段音频送达云端 | 30 | 40 | 60 | 同城 RTT/2 + 20ms 帧 |
| 3 | ASR finalize（出终稿） | 150 | 300 | 500 | 7.2 明说"文档都不写"，必须实测 |
| 4 | 网关编排 + LLM TTFT | 300 | 500 | 800 | 云端 API 首 token |
| 5 | TTS 首包 | 200 | 350 | 400 | 7.7 表格（火山 300–400） |
| 6 | 下行首帧到板 | 30 | 40 | 60 | 同 #2 |
| 7 | 播放缓冲 | 100 | 150 | 200 | 6.5 明确说不能压到 80 |
| 8 | I2S DMA 起播 | 20 | 30 | 40 | 双缓冲 + DMA |
| | **合计** | **980** | **2010** | **2860** | |

### 4.3 结论

- **只有全部取乐观值（≈980ms）才落在 1.0–1.2s 区间**，而且这还是"刚好达标"，没有余量；
- **中位情况 2.0 秒**，正好落在 6.1 表格里"2.5s → 1.5s 巨大改善"的区间——也就是说，**按文档自己的参数，第一版大概率是 2 秒，不是 1.2 秒**；
- 吃掉预算最多的三项是 **#1 端点判定（150–800）+ #4 LLM TTFT（300–800）+ #5 TTS 首包（200–400）**。

### 4.4 所以目标应该这样写

> **KPI 定义**：`T_first_audio` = 用户最后一个字 → 喇叭第一个字，中位数 ≤ 1.5s，P90 ≤ 2.5s。
> **1.0–1.2s 是"三个前置条件同时成立"下的目标**：① 语义端点生效（把 #1 压到 ≤200ms）；② LLM 首句 ≤5 字且 TTFT ≤400ms；③ TTS 用流式首包 ≤250ms。
> 若三者缺一，目标改为 1.5s。

同时必须回答一个文档没回答的问题：**6.4 的「思考音」算不算进 KPI？** 如果说完立刻播"嗯……"（100ms 内），用户感知的等待是 100ms 而不是 1.5s——那 KPI 应该定义成 **`T_perceived` = 用户说完 → 有任何声音（含思考音）**，这个指标能轻松做到 0.3s。**两个指标都要有，但产品验收看 `T_perceived`，工程优化看 `T_first_audio`。**

## 六、建议的执行顺序（替换第十二节）

现在的第十二节是「埋点 → ASR 选型 → 定待定项」。但**埋点依赖一条能跑的链路**，而链路依赖厂商和协议。实际应该：

| 步 | 做什么 | 产出 | 为什么排在这 |
|---|---|---|---|
| **0** | 开厂商账号（火山 + 阿里各一个），**先验证声音复刻的审核要求** | 能否用目标音源的**明确结论** | 这是 C11 的硬门槛，最便宜的一次验证，可能直接改变整个路线 |
| **1** | **PC 上**用 Python 脚本跑通 ASR → LLM → TTS，麦克风进、喇叭出 | 一个 `bench.py`，六段埋点时间戳 | 不碰硬件，一天能出基线。**这是 4.2 那张表的实测版** |
| **2** | 用 30 句测试集跑 2–3 家 ASR，记录准确率 + finalize 延迟 | 选型结论 + 实测延迟分布 | 有基线才知道 1.2s 差多少 |
| **3** | 用 8.6 的 OOC 集做 **云端 LLM vs zjy7 LoRA** 对比 | LLM 选型 + 人设稳定性数据 | 决定架构要不要留"本地 LLM"这条路（C4） |
| **4** | **拿实测数字反推**：能不能达标？差在哪一环？ | 修订后的延迟目标 + 优化优先级 | 此时才配谈"优化收益排序" |
| **5** | 定协议（帧格式 + epoch + 情绪标记 + end-of-speech 归属） | 协议文档 v1 | 前四步的结论都是它的输入 |
| **6** | 买硬件（此时代号才确定 N16R8 / 麦克风方案） | BOM | **不要在第 0 步之前买板子** |
| **7** | 阶段 0 硬件自检 → 阶段 1 端到端 | 能说话的设备 | |

**核心调整：把"硬件"从第 1 步推到第 6 步。** 现在的路线是"先有硬件再验证"，但延迟目标能不能达成，在 PC 上就能测出来，没必要用板子去试。

## 附：文档结构建议

现在十二节是按"知识主题"组织的，读起来像一篇技术综述。建议改成按"**决策 → 依据 → 未决**"组织，每节都收敛到一句可执行的话：

```
1  产品定义与优先级（音色 > 延迟 > 自然度，明确排序）
2  合规前置（🔴 硬门槛，含厂商审核 + 表演者权 + 备案）
3  架构（端云分工 + VAD 归属 + 会话状态）
4  交互状态机（图 + 4 态 + 计时器 + 按键语义）  ← 现在是散在 4.1–4.5
5  协议（帧格式 + epoch + 情绪标记 + end-of-speech）
6  延迟预算（自底向上表 + KPI 定义）             ← 新增
7  选型（ASR / TTS / LLM，含实测数据与成本）
8  人格一致性（OOC 对策 + 评测集 + 自动化判据）
9  硬件（BOM + 坑 + 分区表 + OTA）
10 失败模式与降级（新增）
11 数据与隐私（新增）
12 路线图（阶段 0–4 + 验收数字）
```

另外加两件小事：**文档顶部加版本号与变更记录**（现在自称"唯一依据"却没有版本），**统一术语**（"首响/首包/首字/TTS 首包"混用；"唤醒"已取消但 4.5 还在用）。
