## 一、产品定义与优先级

| 项 | 内容 |
|---|---|
| 产品形态 | 桌面设备，可移动（非固定位置） |
| 硬件 | **ESP32-S3-Touch-LCD-1.85B**（微雪，型号已确认）：ESP32-S3R8 + 8MB Octal PSRAM + 16MB Flash + 360×360 ST77916 QSPI 屏 + CST816S 触摸 + ES8311/ES7210 音频 + 3.7V 电池接口 |
| 核心诉求 | 用**指定角色的声音**说话 |
| 技术路线 | 拼接式 ASR + LLM + TTS，**不走端到端实时语音模型** |
| 端云分工 | 端侧 ESP32-S3，三个模型全部在云端 |

### 1.1 三层优先级

原文一边说"音色控制优先于对话自然度"，一边把"延迟尽可能低"列为首要指标。两者不是同一层的东西：

| 层 | 指标 | 性质 | 不达标的后果 |
|---|---|---|---|
| **L1 音色** | 像不像这个角色 | 产品定义 | 产品不成立 |
| **L2 可用性** | `T_perceived` ≤ 0.4s，`T_first_audio` ≤ 1.5s | 体验门槛 | 用户不用 |
| **L3 自然度** | 对话连贯、情绪贴合 | 加分项 | 扣分但不致命 |

**判据**：任何取舍先保 L1，再保 L2，最后才是 L3。

### 1.2 为什么不走端到端

端到端实时语音模型对话感更自然、延迟更低（0.5–0.8s），但**音色可控性弱于专用 TTS**。本项目 L1 是音色，因此接受拼接式多出的延迟。

**保留观察点**：如果合规路线最终走到"声音设计生成原创音色"（2.3 出路 2），端到端模型的音色指定能力可能就够了——那时值得重新评估一次。

### 1.3 为什么三个模型都上不了板

| 能力 | 结论 | 依据 |
|---|---|---|
| LLM | 不能 | 最小可用中文模型 0.5B int4 约 250MB，本板 8MB PSRAM |
| 连续语音 ASR | 不能 | ESP-SR 的 MultiNet 只支持几十条固定命令词 |
| 角色音色 TTS | 不能 | 乐鑫 esp-tts 是拼音拼接，机械音 |

## 二、合规前置条件（硬门槛）

**现状：有音频，但授权不明。**

### 2.1 权利主体：两个，缺一不可

| 权利 | 主体 | 覆盖行为 |
|---|---|---|
| 录音制品著作权 | 版权方 / 制作方 | 复制、信息网络传播 |
| **表演者权（邻接权）** | **配音演员本人** | 许可录音、复制、发行、信息网络传播 |

只拿版权方授权、没拿配音演员授权，仍然侵权。**两份都要。**

### 2.2 三道门槛

v1 只考虑了第一道。实际有三道，**第二道在原型阶段就会挡住你**：

| # | 门槛 | 谁能决定 | 什么时候必须过 |
|---|---|---|---|
| 1 | **法律授权**（著作权 + 表演者权） | 权利方 / 配音演员 | 对外发布前 |
| 2 | **厂商审核**：火山「声音复刻」、阿里 CosyVoice 上传音源时**都要勾授权承诺**，部分要求上传授权书；未授权音源可能被拒 | 厂商 | **原型阶段就要过** |
| 3 | **深度合成服务备案**：备案主体是"服务提供者"，需企业主体 + 算法备案；个人基本无法完成 | 网信办 | 公开发布前 |

**结论**：个人身份下"公开发布"实际上不成立，除非挂靠企业。

### 2.3 三条出路与决策

| 出路 | 做法 | 干净度 | 风险 |
|---|---|---|---|
| 1 补授权 | 与权利方**和**配音演员签书面授权 | 中 | 周期长、可能被拒 |
| 2 换音色 | 声音设计：文字描述生成原创音色（CosyVoice 支持） | **最高** | 音色不等于目标角色 |
| 3 气质迁移 | 只借鉴音域与语速 | 中 | 边界模糊 |

**决策：阶段 0–5 全程使用出路 2 的原创占位音色**，把"角色音色"当成**可替换资产**。

理由：授权能不能拿到、厂商审核过不过，都不在自己手里。绑死目标音源一旦卡住，整个产品推倒重来；占位音色方案下，链路、协议、硬件、人格调优全部可以照常推进，换音色只是换一个 `voice_id`。

### 2.4 音色资产必须记四个字段

复刻音色绑定模型版本，换模型音色就变了：

```json
{ "voice_id": "...", "bound_model": "cosyvoice-v2", "source": "design|clone", "license_ref": "..." }
```

`license_ref` 是新增项：占位音色也要记录来源，否则半年后没人说得清这个音色是哪来的。

## 三、架构与职责边界

```
ESP32-S3-Touch-LCD-1.85B                     云端网关（大脑 + 编排）
├ ES7210 双麦 + 硬件 AEC  ─┐                 ├ 流式 ASR（含云端 VAD / 语义端点）
├ 本地 VAD（门控 / 预打断） ├─ 上行 ──WS──►   ├ LLM（角色人格 + 情绪标记）
├ 360×360 触摸屏（主入口） │                 ├ 情绪解析 + 文本分段
├ ES8311 + PA ────────────┘◄─ 下行 ──WS──    └ 流式 TTS（角色音色）
├ QSPI 屏渲染（状态/波形）
├ BOOT 键（盲操备份）
└ 本地状态机 + epoch 过滤
```

### 3.1 边界原则

**板子是"哑终端"**——只负责采集、上传、播放、本地门控、按键/触摸响应和状态显示；所有编排逻辑（ASR → LLM → TTS）放在云端网关。

**但"哑"不等于"没有状态"**：板子必须有本地状态机（待机/聆听/思考/说话）、本地 VAD 门控、播放缓冲和 epoch 过滤。这些是实时性要求决定的，放云端做不了。

### 3.2 VAD 的三层归属

| 层 | 位置 | 职责 | 判据 | 延迟 |
|---|---|---|---|---|
| **L1 本地门控** | 板子 | ① 决定是否开始上传 ② 静音时停止上传省流量 ③ 打断检测 | 能量 + 过零率 + 自适应底噪（**ES7210 双麦可做简易波束**） | <20ms |
| **L2 云端能量 VAD** | 网关 | 切句、粗判静音 | 服务端 ASR 自带 | 服务端决定 |
| **L3 语义端点** | 网关 | **判定 end-of-speech** | ASR 中间结果的文本完整性 | 150–350ms |

**唯一权威：end-of-speech 一律由云端（L3，退化时用 L2）决定。**
板子做本地 VAD 只为了"省流量"和"打断"，**本地判定静音后只停止发送，不发结束信号**。

### 3.3 AEC 由硬件承担（v2.0 判断需要修正）

v2.0 按 INMP441 单麦设计，认为 AEC 要靠软件注入 reference。**本板不是这样**：

- 板载 **ES7210** 是 4 通道 ADC，产品定位就是"回声消除 + 双麦克风"；
- 参考信号来自 ES8311 的播放通路，**在硬件层接好**，不需要软件旁路；
- 双麦还能做简易波束成形，对 9.3-3 的噪声自适应有帮助。

**影响**：阶段 4 的 AEC 风险显著下降（不用自己写 reference 注入），但新增两个坑：

1. **reference 通路是否接对，必须在原理图/官方示例层面对照确认**，不能假设；
2. **I2C 共享总线**：ES7210 的配置走 GPIO10/11，与触摸、IMU、电量计、RTC 同总线 → 必须加互斥锁。

### 3.4 会话状态归属

| 状态 | 存在哪 | 生命周期 |
|---|---|---|
| 会话 ID | 云端下发 → 板子存 NVS | 断电保留，重连复用 |
| 对话历史 | 云端数据库 | 长期 |
| 记忆摘要 | 云端数据库 | 长期（可复用 zjy9 的混合检索记忆库） |
| 当前轮次 / epoch | 双方各自持有 | 单轮 |
| 播放缓冲 | 板子 PSRAM | 单轮，轮次切换即清 |

**断线重连**：30 秒内重连且会话 ID 未过期 → 恢复原会话；超过 30 秒 → 服务端保留会话 10 分钟，但板子回待机。

## 四、交互：触摸屏为主入口

### 4.1 核心决策：整屏触摸 = 说话，BOOT 键 = 盲操备份

**为什么不是物理按键做主入口**（v1 的假设在本板上不成立）：

| 事实 | 影响 |
|---|---|
| **PWR 键硬件固定**：长按 2s 开关机、短按 1s 开机，官方明确不支持自定义 | 不能当录音键 |
| 唯一可用按键是 **BOOT（GPIO0）** | 它在复位时被拉低会进下载模式——高频使用有风险 |
| 360×360 整屏都是触摸区 | "摸一下就说话"不需要瞄准，盲操问题基本消失 |

**决策**：

1. **主入口 = 触摸屏整屏**（任意位置，不设按钮）；
2. **备份入口 = BOOT 短按**（<1s），语义与触摸完全一致；
3. **PWR 键不参与交互**，只做开关机。

### 4.2 触摸带来的三个变化

| 变化 | 说明 |
|---|---|
| **熄屏首击 = 亮屏 + 立刻开始聆听** | 不做"先亮屏再点一次"的二次确认。触摸本身已是明确意图，多一次操作就多一次流失 |
| **必须给即时反馈** | 触摸没有触觉反馈。按下立刻：短促"叮" + 屏上波纹 + 状态文字切换。缺一个用户就会怀疑没按上 |
| **BOOT 兜底** | 盲操场景（不看屏、手套、强光下看不清）与触摸异常时，BOOT 短按仍能开始/结束说话。语音设备不该只有一个输入通道 |

### 4.3 四态状态机

```
                 ┌──────────── 短按（触摸/BOOT）────────────┐
                 ▼                                          │
            ┌─────────┐  短按   ┌─────────┐  eos  ┌──────────┐
            │  待机   │────────►│  聆听   │──────►│  思考中  │
            │（熄屏） │         │（亮屏） │       │（动画）  │
            └─────────┘         └─────────┘       └──────────┘
                 ▲                   │                 │
                 │                   │ 首包到达         │
                 │                   ▼                 ▼
                 │              ┌─────────┐◄──── 短按（取消本轮）
                 └──── 退出 ────│  说话   │
                                └─────────┘
                  任意态 长按 ≥600ms ──► 退出（回待机）
```

**屏幕状态是正交的**：待机 15s 后熄屏（背光 PWM 到 0）；进入聆听/思考/说话自动亮屏；会话中不熄屏。

**为什么必须有"思考中"**：从"用户说完"到"首字出声"之间有 0.8–1.5 秒，这是用户最焦虑的时段。不给这个状态定义按键语义，用户按了没反应就会连按。

### 4.4 输入语义（双通道同义，不设第二套规则）

**短按 = 打断 / 结束；长按 ≥600ms = 挂断。**

| 当前状态 | 短按（触摸或 BOOT，<600ms） | 长按（触摸，≥600ms） |
|---|---|---|
| 待机（熄屏） | 亮屏 + 进入聆听，开始录音 | 亮屏 + 打开设置页 |
| 聆听 | 立即结束本轮（发 `eos_hint`） | 挂断，回待机 |
| **思考中** | **取消本轮**（发 `cancel`），回聆听 | 挂断，回待机 |
| 说话 | 打断：发 `cancel`、epoch+1、清空缓冲，回聆听 | 挂断，回待机 |

**BOOT 键只支持短按**，不做长按——理由见 4.1（长按 + 复位会进下载模式）。BOOT 长按行为交给 Bootloader，固件不介入。

**设置页入口从"待机长按 3s"改成"触摸长按打开设置"**（v2.0 的 BOOT 长按方案已废弃）。

### 4.5 计时器统一表

| 计时器 | 起点 | 阈值 | 动作 | 是否退出 |
|---|---|---|---|---|
| `T_silence_local` | 本地 VAD 判静音 | 600ms 安静 / 800ms 嘈杂 | **停止上传**（不发 eos） | 否 |
| `T_eos_cloud` | 云端检测到静音起点 | 语义端点 150–350ms | 下发 `end_of_speech` | 否 |
| `T_nospeech` | 进入聆听 | 5s | 播提示"还在吗"，**不退出** | 否 |
| `T_idle_round` | 进入聆听 | 8s | 本轮计为空 | 条件 |
| `T_think_timeout` | 进入思考中 | 8s | 播"信号不太好"，回聆听 | 否 |
| `T_idle_total` | 最后一次有效轮次结束 | 30s | 退出会话 | 是 |
| **`T_screen_off`** | 回待机 | 15s | 背光关 | 否 |

**退出条件（任一命中）**：

1. 用户说"再见/结束/不聊了"
2. 长按 ≥600ms
3. **连续 2 次空轮次**（空轮次由 `T_idle_round` 或 ASR 返回空产生）
4. `T_idle_total` 30s 无有效轮次（兜底）

退出必须有收尾反馈：**提示音 + 屏幕淡出 + 熄屏**。

### 4.6 打断后的上下文处理

| 做法 | 问题 |
|---|---|
| 整段丢弃 | 模型不知道自己说过什么，下一轮会重复 |
| 完整保留 | 模型以为自己说完了 |
| **截断到最后一句完整的话 + 标记 `interrupted=true`** | ✅ 采用 |

实现：网关收到 `cancel` 时，取已下发到 TTS 的文本，按句号/问号/感叹号截断到最后一个完整句。system prompt 加一句：`被用户打断时，不要重复已经说过的话。`

### 4.7 屏幕的六个用途

| # | 用途 | 说明 |
|---|---|---|
| 1 | **主输入** | 整屏热区，触摸即说话 |
| 2 | **状态可视化** | 四态文字 + 麦克风开启指示（见第十一节） |
| 3 | **感知延迟优化** | 思考动画、波形、打字机效果（见 6.7） |
| 4 | **配网 UI** | WiFi 列表 + 软键盘，取代 SoftAP + 灯环（见 9.4） |
| 5 | **设置页** | 音量、音色切换、清空记忆、关于 |
| 6 | **兜底表达** | 纯动作无台词时显示表情/省略号（见 8.5） |

**布局约束**：1.85 吋 360×360。**若为圆屏，四角会被外壳遮挡**——关键信息（状态文字、按钮）必须放在中心直径 300 的安全圆内。这一点需实物确认（见第十三节）。

### 4.8 预打断：触摸带来的延迟红利

用户想打断时，**手指比声音先到**。

- 触摸 INT（GPIO4）触发 → 板子立刻把播放音量降到 30%（不停止），同时本地 VAD 开始判人声；
- 200ms 内确认有人声 → 真打断（发 `cancel`、epoch+1）；
- 未确认（误触）→ 音量恢复，不打断。

**收益**：打断的"响应感"提前 100–200ms，而误触不会造成真正的打断。

**风险**：误触频率。缓解——只对"播放中"的触摸做预打断，待机/聆听态的触摸不触发。

## 五、通信协议

### 5.1 一段式编排

板子只连**一个** WebSocket，云端网关内部串 ASR → LLM → TTS。理由：ESP32 上做三段编排是自找麻烦，每多一条 TLS 连接就是 30–50KB 内存。

### 5.2 传输层：第一版就用 WebSocket

v1 说"第一版用 HTTP，后面改 WebSocket 基本等于重做"，阶段 1 却写"PTT + HTTP"——两句不能同时成立。

**结论：阶段 3（PTT 端到端）就用 WebSocket，只是一次性发送整段，不分片。** 要改的应该只有"发送节奏"，不是"传输层"。HTTP 只用于 PC 端离线调试脚本，不进固件。

### 5.3 帧格式

**上行（板 → 云）**

| 类型 | 格式 | 载荷 |
|---|---|---|
| `start` | JSON | `{session_id, device_id, epoch, sample_rate, format}` |
| `audio` | 二进制 | `640B PCM`（16k/16bit/20ms） |
| `eos_hint` | JSON | `{epoch}` —— 用户短按结束。**只是提示**，以云端 L3 端点为准 |
| `cancel` | JSON | `{epoch}` |
| `ping` | JSON | `{}`（10s） |

**下行（云 → 板）**

| 类型 | 格式 | 载荷 |
|---|---|---|
| `audio` | 二进制 | **`4B epoch` + PCM**（前 4 字节 uint32 LE） |
| `state` | JSON | `{state, epoch}` |
| `text` | JSON | `{epoch, delta?, final?}`（调试与日志，屏上可选显示） |
| `emotion` | JSON | `{epoch, label, rate}` |
| `error` | JSON | `{code, speakable}` —— `speakable` 是**用角色口吻说的**话术 |
| `pong` | JSON | `{}` |

### 5.4 epoch 机制（防"迟到残句"）

**问题**：用户打断 → 板子发 cancel 并清空缓冲 → 但 cancel 到达云端时，TTS 已合成后续段落正在回传 → 这些**迟到帧会被当成新一轮回复播出来**。

**方案**：每轮分配单调递增 `epoch`（uint32）。云端所有下行帧都带当前 epoch；板子只播 `epoch == current_epoch` 的音频帧，其余静默丢弃并计数；用户打断时板子本地 `current_epoch++`（不等云端确认）。

**成本**：4 字节/帧。现在加几乎为零，后期加要改协议 + 固件 + 网关。

### 5.5 音频参数与码率权衡

| 方案 | 码率 | 解码延迟 | CPU | 抖动敏感度 |
|---|---|---|---|---|
| PCM 16k/16bit | **256 kbps** | ~0 | 极低 | **高** |
| MP3 64kbps | 64 kbps | ~100ms | 中 | 中 |
| **Opus 32kbps** | **32 kbps** | ~40ms | 低–中（待实测） | **低** |

**决策**：阶段 3–4 用 PCM（简单、可调试）；**阶段 5（流式改造）同步引入 Opus 32kbps**（那阶段本来就要重做音频管道）。Opus 的 CPU 开销必须实测——v1 写"30–40%"可能偏高，若 <20% 提前到阶段 4。

### 5.6 上行拥塞策略

v1 写「WiFi 抖动时丢最旧，不丢最新」——**这对上行语音是错的**。它适用于实时视频/遥测这类"最新值即全部信息"的流。上行语音是 ASR 输入，**每个采样点都不可替代**：丢最旧等于把"你好，我想问一下"削成"问一下"。

**正确策略**：

1. **反压**：RingBuffer 满 → 发送任务不取 → 采集任务自然阻塞 → DMA 溢出的也是采集侧数据，且要**在采集侧计数上报**；
2. **降码率**：切 Opus 低码率；
3. **显式失败**：持续 >500ms 无法消化，屏幕转黄 + 上报网络劣化，让用户重说。

**绝不静默丢弃已采集的音频帧**——那会把网络问题伪装成 ASR 不准。

### 5.7 收发解耦与 pre-roll

- 20ms 一帧 = 320 采样 = **640 字节**，每秒 50 帧；
- I2S 读取任务只往 RingBuffer 塞，网络任务取出发送，中间不能有阻塞调用；
- **pre-roll 300ms**：本地 VAD 门控能省流量，但"检测到人声才开始录"会切掉第一个字。必须一直滚 300ms 前置缓冲。

## 六、延迟预算

### 6.1 为什么必须自底向上算

v1 的 6.2 只有「优化能省多少」，没有「基线是多少」。而且收益**不能线性相加**：

- 「ASR 并行化 500ms」与「上传与录音并行 200ms」高度重叠；
- 「语义端点 450ms」本质是**把 600ms 固定静音换成 150–350ms 语义判定**，与「静音判定 600ms」是**互斥选项**。

v1 简单相加得 1500ms 的节省，是虚高的。

### 6.2 测量点

```
用户说完 ─①─► 判端点 ─②─► 终稿 ─③─► LLM首token ─④─► TTS首包 ─⑤─► 收到首帧 ─⑥─► 出声
        └──────────────── T_first_audio ────────────────────────────────────┘
        └──── T_perceived（① 之前先播思考音/屏上先出动画）────┘
```

### 6.3 自底向上加总

| # | 环节 | v1 配置<br>（固定静音 600ms） | 目标配置<br>（语义端点 + 优化） | 悲观 |
|---|---|---|---|---|
| ① | 说完 → 判定说完 | 600 | **200** | 350 |
| ② | 末段音频送达云端 | 40 | 35 | 60 |
| ③ | ASR finalize | 300 | **250** | 500 |
| ④ | 网关编排 + LLM TTFT | 500 | **250**（本地，缓存命中） | 800（云端兜底） |
| ⑤ | TTS 首包 | 350 | **250** | 400 |
| ⑥ | 下行 + 播放缓冲 120 + I2S 起播 | 190 | 180 | 300 |
| | **合计 `T_first_audio`** | **1980 ms** | **1165 ms** | **2410 ms** |

### 6.4 目标修订

**v1 的"1.0–1.2 秒"在目标配置下接近成立（1165ms），但前提是四个条件同时满足，且数字全是估算。**

| 指标 | 定义 | 目标 | 用途 |
|---|---|---|---|
| `T_perceived` | 说完 → 任何声音（含思考音） | **P50 ≤ 0.3s** | 产品验收 |
| `T_first_audio` | 说完 → 第一句台词 | **P50 ≤ 1.5s，P90 ≤ 2.5s** | 工程优化 |
| 冲刺 | `T_first_audio` | 1.2s | 四前置同时成立才承诺 |

**四个前置条件**：① 语义端点 ≤200ms；② LLM 首句 ≤5 字且 TTFT ≤250ms（**本地 + 前缀缓存 + 预热**，见 7.6.4）；③ TTS 流式首包 ≤250ms；④ 播放缓冲不压到 80ms 以下（见 6.9）。

⚠️ ② 是新增的硬条件：**云端 API 的 TTFT 是 300–800ms，单这一项就会把总数推到 1.3–1.8s**。所以"1.2 秒"这个冲刺目标实际上**只有本地 LLM 路径才可能达成**——这是 7.6 把本地设为主路的另一个理由。

**两个指标都要有**：`T_perceived` 衡量"用户觉不觉得卡"，`T_first_audio` 衡量真实链路能力。只报前者是自欺，只报后者是自虐。

### 6.5 优化手段（按收益/成本重排）

| 优化 | 省 | 类型 | 优先级 |
|---|---|---|---|
| 语义端点替代固定静音 | **400ms** | 结构性 | P0 |
| ASR 边说边识别（流式上传） | **250ms** | 结构性 | P0 |
| LLM 换 TTFT 更低的模型 | 100ms | 参数 | P1 |
| TTS 流式首包优化 | 100ms | 参数 | P1 |
| 下行 Opus 替代 PCM | 0（延迟持平） | 结构性 | P1（稳定性，非延迟） |
| 播放缓冲收紧 | 最多 40ms | 参数 | **不做**（见 6.9） |

### 6.6 WiFi 省电模式必须关

ESP32 默认开 modem sleep，会让网络包出现 100–300ms 随机抖动，前面所有优化可能被这一项全吃掉。配置 `WIFI_PS_NONE`，代价是功耗上升 30–50mA。

**本板配套注意（v2.1 新增）**：

- **配网期间暂停音频任务**：SoftAP 与 STA 同时工作抢射频；
- **不要开 BLE 共存**：本板有 BT5，但 BLE + WiFi 共存会显著加剧 2.4G 抖动；
- 屏幕刷新与 WiFi 也抢资源，见 6.8。

### 6.7 感知延迟 ≠ 实际延迟

| 手段 | 载体 | 说明 |
|---|---|---|
| **思考音** | 音频 | 说完立刻播预录的"嗯……"。**必须 3–5 个变体随机 + 按时长分档**，否则重复几十次会很假 |
| **思考动画** | **屏幕（v2.1 新增）** | 三点呼吸 / 波形起伏。**视觉反馈比音频更早到达**（屏幕刷新 <16ms），是 `T_perceived` 最便宜的手段 |
| **首句压短** | LLM | 第一句只说 3–5 个字，先出声 |

**屏幕的价值在这里最明显**：思考音要等音频通路（≈100ms），屏上动画 1 帧就到。二者叠加，用户感知的"响应"几乎即时。

### 6.8 QSPI 屏 + I2S + WiFi 的三方资源竞争（v2.1 新增）

这是本板最容易被忽略的性能坑：

| 资源 | 占用 | 冲突点 |
|---|---|---|
| QSPI 屏（ST77916） | 360×360 RGB565 = **253KB/帧**；30fps ≈ **7.6MB/s** | 与 PSRAM 帧缓冲、WiFi DMA 抢 PSRAM 带宽 |
| I2S 音频 | 16k/16bit 双向 ≈ 64KB/s | 与屏抢 DMA 通道、抢 CPU |
| WiFi | 峰值 350mA + DMA 突发 | 与屏抢 PSRAM |

**对策**：

1. **说话时降帧率**：播放音频时屏幕刷新降到 10fps，且**只刷脏区**（波形区域），不做全屏重绘。
   ⚠️ 注意与 §4.7 的协调：**10fps 只够画"起伏感"**——波形用 10fps 可以（人眼看的是节奏不是细节），
   但**不能做逐帧平滑的曲线**；思考动画用低频呼吸/三点跳动，不做逐帧补间。全屏动画一律禁止；
2. **LVGL 任务优先级必须低于 I2S 音频任务**——音频欠载就是爆音，屏幕掉帧用户看不出来；
3. **帧缓冲放 PSRAM，但用双缓冲而非三缓冲**（省 253KB 带宽）；
4. **不做全屏动画**（如整屏渐变、旋转），这类操作会直接抢走音频带宽。

### 6.9 不要牺牲稳定性

**卡顿一次比慢 300ms 更伤体验。** 播放缓冲定在 **120ms**，不压到 80ms。

## 七、选型

### 7.1 ASR：准确率优先于价格

| | 阿里 **Paraformer-realtime** | 阿里 Qwen-Audio 系列 | 火山（豆包）流式 ASR | 腾讯实时 ASR |
|---|---|---|---|---|
| 中文准确率 | 高，非自回归解码 | 高（见下） | 高，对话场景优化好 | 中上 |
| 是否流式实时 | ✅ | ⚠️ **长期是离线音频理解模型**，流式能力需核实 | ✅ | ✅ |
| 中间结果 | ✅ | 需核实 | ✅ | ✅ |
| 独立 finalize 接口 | ✅ | 需核实 | ✅ | 需核实 |
| 与 TTS 同厂商 | 是 | 是 | 是 | 否 |

v1 把「Paraformer / Qwen-Audio-ASR」并列成流式候选，**已拆开**。选型以 **Paraformer-realtime** 和 **火山流式 ASR** 为候选。

v1 的"首字延迟约 160ms"是厂商宣传值，实测含网络通常 300–500ms。

### 7.2 必须实测的指标

1. **finalize 延迟**；
2. **是否有独立 finalize 接口**（决定 7.3 双引擎能不能做）；
3. **热词生效速度**；
4. **语气词保留策略**；
5. **并发限制与 QPS 配额**；
6. **断线重连能否续传同一会话**。

### 7.3 双引擎模式

流式模型每 600ms 推中间结果撑体验，端点判定后用精度更高的模型出终稿。中间结果用于**语义端点判断**；终稿才**喂给 LLM**。

**两个风险**：成本翻倍；两个模型文本可能不一致（"端点判断基于的话" ≠ "喂给 LLM 的话"）。
**缓解**：用**同厂商同系列的高低精度模型**，把两者文本**差异率作为质量指标**（>5% 换方案）。

注意：流式中间结果通常**不带标点**，终稿才带。别拿中间结果直接喂 LLM。

### 7.4 热词表

角色名、世界观专有名词必须加入热词，否则识别成同音词，LLM 收到错名字会出戏。

- **数量上限**通常 500–1000 词，按优先级排序；
- **生效延迟**：阿里需预建 `vocabulary_id`，更新后**新会话才生效**；
- 热词表随人格卡版本化。

### 7.5 厂商组合与全链路成本

v1 自己算出火山 1950 元/月 vs 阿里 300 元/月（差 6.5 倍），却推荐"先用火山跑通"。

**决策**：

| 环节 | 选择 | 理由 |
|---|---|---|
| ASR | **火山**（备选 Paraformer-realtime） | 准确率与生态优先，成本占比小 |
| LLM | **本地 Ollama（主）** / 火山豆包（兜底） | 本地 TTFT 更低且零成本；云端解决"本机不在"（见 7.6、7.6.7） |
| TTS | **阿里 CosyVoice** | 便宜 6 倍，且**支持声音设计**——正是 2.3 的出路 2 |

**全链路成本**（一轮 = 用户说 15 秒 + 回复 50 字）

| 项 | 口径 | 原型 20 轮/天 | 试用 200 轮/天 | 公开 1000 轮/天 |
|---|---|---|---|---|
| ASR | 音频时长 | 2.5 小时/月 | 25 小时/月 | 125 小时/月 |
| LLM | token（入 ~800 / 出 ~100） | 54 万 / 6 万 | 540 万 / 60 万 | 2700 万 / 300 万 |
| TTS·阿里 | 2 元/万字符 | **6 元** | **60 元** | **300 元** |
| TTS·火山 | 1.3 元/千字 | 39 元 | 390 元 | 1950 元 |
| 合计 | | 待填 | 待填 | 待填 |

ASR 与 LLM 单价以控制台为准，**开通账号后第一件事就是把这张表填满**。

**注意隐性成本**：会话模式进入后自动循环录音，**待机状态也在上传音频、也在计费**。4.5 的 `T_idle_total` 30 秒退出和 5.6 的本地 VAD 停发，本质上都是成本控制措施。

### 7.6 LLM 选型

| | 云端 API（豆包/通义） | **本地 Ollama（zjy7 LoRA）** |
|---|---|---|
| 人设稳定性 | 靠 prompt 硬撑，OOC 风险高 | LoRA 微调过，人设"长"在权重里 |
| TTFT | 300–800ms | **0.15–1.5s（取决于是否命中缓存，见 7.6.1）** |
| 成本 | 按 token | 0 |
| 可用性 | 依赖公网 | **依赖本机开机** |

**决策：本地优先，云端兜底**（策略细节见 7.6.7）。理由：本地在 TTFT（0.2–0.35s vs 0.3–0.8s）和成本（0）上都占优，而"依赖本机开机"这个弱点正好由云端兜底解决——不需要因此把云端设为主路。

但前提是 7.6.4 的缓存 + 预热做到位；**做不到就不要本地优先**，直接主用云端（那时本地 1.9s，会拖垮体验）。所以阶段 1 的 A/B 必须先跑出本地实测数字，再定主备方向。

架构要求：网关必须有 **LLM 适配层**，"云端 / 本地"可切换，不能写死。

#### 7.6.1 本地模型的实际延迟量级

本机 **RTX 5070 12GB**，`qwen3.5:9b-gguf`（Q4，5.7GB，权重 100% 进显存，**decode 实测 96 tok/s**，必须传 `think: false`）。

**关键认知：瓶颈不在生成速度，在 prefill。** 96 tok/s 意味着 50 字回复（≈35 token）只要 **0.36 秒**，完全够用；真正吃时间的是**每轮重新喂进去的 system prompt**。

| 环节 | 耗时 | 依据 |
|---|---|---|
| 模型加载（冷启动） | **5–15s** | 必须 `keep_alive=-1` 常驻，否则每轮都是灾难 |
| prefill：人设 1396 字（≈1000 token） | **0.5–1.25s** | 估 800–2000 tok/s，未实测 |
| prefill：人设压到 300 token | 0.15–0.4s | 同上 |
| prefill：命中 KV 前缀缓存（只算新增 user turn） | **0.05–0.15s** | Ollama 对相同前缀复用 KV |
| 首 token → 首句 5 字 | ≈0.05s | 96 tok/s |
| 50 字完整回复 | ≈0.36s | 96 tok/s |

**四种场景的端到端**：

| 场景 | TTFT | 首句出声 | 50 字说完 |
|---|---|---|---|
| 冷启动（模型未加载） | 5–15s | — | — |
| 热态 + 角色卡 1000 token + 无缓存 | **0.6–1.5s** | 0.7–1.6s | 1.1–2.0s |
| 热态 + 人设压到 300 token | 0.2–0.5s | 0.3–0.6s | 0.7–1.0s |
| 热态 + 人设压缩 + KV 前缀缓存命中 | **0.15–0.35s** | 0.2–0.4s | 0.6–0.9s |

**代回 6.3 的延迟预算**（①200 + ②35 + ③250 + ④TTFT + ⑤250 + ⑥180）：

| 配置 | ④ TTFT | `T_first_audio` |
|---|---|---|
| 云端 API | 400 | **1315 ms** |
| 本地 + 角色卡 + 无缓存 | 1000 | **1915 ms** |
| 本地 + 人设压缩 + 缓存 | 250 | **1165 ms** |

**结论：本地模型的响应速度能不能用，完全取决于三个优化做不做**——做到了与云端持平甚至更快，做不到就慢 600ms（1.9s，已经跌出 L2 门槛）。

**三个决定性优化**：

1. **`keep_alive=-1` 常驻**：把 5–15s 的冷启动彻底移出交互路径；
2. **人设压缩**：这是 **LoRA 相对角色卡的隐藏优势**——人设"长"在权重里，system prompt 可以从 1000 token 压到 200–300，prefill 直接省 3–5 倍。用角色卡（纯 prompt）就必须每轮喂全文；
3. **KV 前缀缓存**：system prompt 必须**逐字节稳定**（不要每轮插入时间戳、随机 id、变化的记忆摘要）。8.7 的"每轮重注入记忆摘要"会**破坏缓存**——要么把摘要放在 prompt 末尾（缓存命中到摘要之前），要么接受 prefill 变慢。

**其他风险**：

- **显存**：9B Q4 5.7GB + 4k ctx KV ≈0.5GB + 余量 ≈7.2GB，12GB 够。但 `elysia-lora`（8.1GB）更紧，ctx 要压到 2048；
- **并发**：单卡只能串行，**同时两个会话就会互相排队**。语音设备单人用没问题，别当服务；
- **可用性**：电脑关机/休眠/Ollama 崩了，设备就哑了。必须有降级（转云端或播"我现在有点困"的角色话术）。

#### 7.6.2 12GB 显存下的模型天花板（结论：不要换底座）

**12GB 的现实上限是 9B 级 dense。** 比它大的模型没有一个能完整进显存，勉强挤进去会溢出到 CPU，速度直接崩——本机已实测 `qwen3.8-27b` 有 7.37GB 落在 CPU，单个请求 >120s 不返回。

| 模型 | 类型 | Q4 权重 | 4k ctx + 开销 | 12GB 能跑 |
|---|---|---|---|---|
| Qwen3.5-4B | dense | ~2.6GB | ~4GB | ✅ 很宽松 |
| **Qwen3.5-9B**（当前） | dense，**Gated DeltaNet + Gated Attention 混合** | **5.7GB** | **~7.2GB** | ✅ 宽松 |
| Qwen3.5-9B **Q5_K_M** | 同上 | ~6.9GB | ~8.5GB | ✅ 可以 |
| Gemma 4 E4B | MoE 8B / 4.5B 激活 | ~5GB | ~6.5GB | ✅ 但中文弱于 Qwen |
| Gemma 4 26B-A4B | MoE 26B / 3.8B 激活 | ~15GB | ~17GB | ❌ 溢出 |
| Qwen3.8-27B | dense 64 层 | ~16GB | ~18GB | ❌ 已实测不可用 |
| Qwen3.8-Flash | MoE 125B / 6B 激活 | ~95GB | — | ❌ |
| GLM-5.1 | MoE 744B / 44B 激活 | 数百 GB | — | ❌ |

**为什么"换底座"在这块卡上没有意义**：

1. **同尺寸里 Qwen3.5-9B 已经是中文最强的一档**。换成 Gemma 4 E4B 是**降级**（中文更弱）；换老的 Peach-9B 之类是退步（Yi-1.5 底座）；
2. **Qwen3.5-9B 的混合线性注意力架构恰好适合本项目的用法**：Gated DeltaNet 让长上下文 prefill 更省、KV cache 更小。我们每轮要喂 1000 token 人设——换成普通全注意力模型（如 Gemma 4），prefill 反而更慢、KV 更大；
3. **角色扮演的瓶颈不是底座能力，是人设稳定性**。这只能靠 LoRA 和 prompt 解决，换底座解决不了。而 `elysia-lora` 已经在 9B 上训好了——**换底座等于把 LoRA 白扔**，这是最实际的理由。

**所以该做的不是"换模型"，而是这四件事（按性价比排序）**：

| # | 动作 | 收益 | 成本 |
|---|---|---|---|
| 1 | **量化档从 Q4_K_M 升到 Q5_K_M**（甚至 Q6_K） | 质量白拿，显存仍够 | 重新拉一次 GGUF |
| 2 | **人设压缩到 200–300 token**（见 7.6.1） | prefill 省 3–5 倍 | 改 prompt |
| 3 | **投机解码**：用 `qwen3.5:0.8b` 作 draft | decode 再快 1.5–2×（对 TTFT 无帮助） | 需确认 Ollama/llama.cpp 是否支持该架构 |
| 4 | **快慢双路由**：4B 出短句、9B 出实质内容 | 平均延迟下降 | 复杂度高，**不建议先做** |

**如果一定要换一个型号，唯一值得换的是 `Qwen3.5-9B Q5_K_M`——同底座、更高精度，不是换模型。** 想要更强能力只能走云端（这正是 7.6 的"主云端"决策）；想等更强的本地底座，就等 Qwen3.8 出小尺寸，或者换 16GB 以上的卡。

> ⚠️ 表中量化体积与显存占用是**估算**，实际以 `ollama list` 与 `/api/ps` 的 `size_vram` 为准（判断是否真全进显存，看 `size_vram` 不看 `size`）。

**先澄清一个常见混淆：`Qwen3.5-9B` 和 `Qwen3.5-9B-gguf` 不是两个模型。**

`Qwen3.5-9B` 是原始权重（fp16，约 **18GB**）；`Qwen3.5-9B-GGUF` 是**同一个模型**转成 GGUF 并量化后的版本（本机这份是 Q4_K_M，**5.68GB**）。Ollama 里的 tag `qwen3.5:9b-gguf` 只是本地命名，不代表另一个模型。

所以真正要选的不是"哪个模型"，而是"**哪个格式 / 量化档**"：

| 格式 | 体积 | 12GB 能装 | decode（按 0.81 效率估） | 质量 | 可用引擎 |
|---|---|---|---|---|---|
| 原始 fp16/bf16（safetensors） | **~18GB** | ❌ 根本不行 | — | 满分 | vLLM / transformers |
| FP8 | ~9.5GB | ⚠️ 勉强 | 慢 | 接近满分 | vLLM（Windows 上难） |
| GGUF **Q8_0** | ~9.5GB | ⚠️ 只剩 1.5GB | ~58 tok/s | 近无损 | Ollama / llama.cpp |
| GGUF **Q6_K** | ~7.4GB | ✅ | ~74 tok/s | 很好 | 同上 |
| GGUF **Q5_K_M** | ~6.9GB | ✅ | ~79 tok/s | 好 | 同上 |
| **GGUF Q4_K_M（当前）** | **5.68GB** | ✅ 宽松 | **96 tok/s（实测）** | 可接受 | 同上 |
| AWQ / GPTQ int4 | ~5.5GB | ✅ | prefill 更快 | ≈Q4 | vLLM（Windows 上难） |

**结论：原始 fp16 在 12GB 上根本不是选项。** 18GB 得两张卡 + 张量并行，而 7.6.6 已经算过那样**更慢**。所以只能用 GGUF，区别只在量化档。

**选哪个档取决于拓扑**——因为本项目 decode 不是瓶颈，**VRAM 才是**：

| 拓扑 | 建议档位 | 理由 |
|---|---|---|
| 单机跑全套（LLM + 本地 TTS + ASR） | **Q4_K_M** | 要留 6GB 给 TTS/ASR（见 7.6.6） |
| LLM 独占一张卡，TTS/ASR 走云端 | **Q6_K 或 Q8_0** | 50 字回复从 0.36s 变 0.6s，用户感知不到，换来质量提升 |
| 想两者兼顾 | **Q4_K_M + imatrix** | 体积 = Q4、质量 ≈ Q5（见 7.6.3） |

⚠️ **Q8_0 有个隐性代价**：9.5GB 权重只剩 1.5GB，**KV cache（4k 约 0.5GB）+ 运行时开销（约 1GB）会直接把 12GB 撑爆**，实际很可能溢出到 CPU、速度断崖式下跌。所以 Q8_0 只适合"LLM 独占一张卡"的拓扑，不能和本地 TTS/ASR 共存。

#### 7.6.3 同时要"快"和"好"：可用的杠杆清单

**先看一个硬事实：decode 已经到这张卡的物理天花板附近，没有"调优"空间了。**

| 项 | 数值 |
|---|---|
| RTX 5070 显存带宽 | **672 GB/s**（12GB GDDR7 / 192-bit / 28Gbps） |
| 9B Q4 权重 | 5.7GB |
| 理论上限 = 带宽 ÷ 每 token 读取量 | 672 / 5.7 ≈ **118 tok/s** |
| 实测 | **96 tok/s** → **效率 81%** |

decode 是**显存带宽瓶颈**，不是算力瓶颈。所以想更快只有三条路：**少读字节**（更低位宽 / 更小模型 / MoE）、**少生成 token**、**投机解码**（一次验证多个 token）。

**但要看场景：对语音设备来说，decode 根本不是瓶颈。**

50 字回复 ≈ 35 token，96 tok/s 下只要 **0.36 秒**；就算掉到 60 tok/s 也才 0.58 秒。真正吃时间的是**每轮 1000 token 人设的 prefill**（0.5–1.25 秒，见 7.6.1）。所以：

- **给本设备用** → 优先做 **prefill 侧**（人设压缩、前缀缓存、keep_alive），decode 只需保证不掉到 60 tok/s 以下；
- **如果要长回复**（写作、长对话）→ 才轮到 decode 侧优化（投机解码、量化档、输出长度控制）。

**四类能同时拿到"快"和"好"的手段**（速度/质量都不牺牲的排前面）：

| 类 | 手段 | 速度 | 质量 | 备注 |
|---|---|---|---|---|
| **A 同尺寸提精度** | **imatrix 量化** | 不变 | **↑↑** | **本项目最关键的一招**，见下 |
| | LoRA 合并进权重后再量化 | 略↑ | ↑ | 避免 adapter 叠加误差 |
| | 量化档 Q5_K_M / Q6_K | ↓15–25% | ↑ | 显存够但 decode 变慢，**与"要快"冲突** |
| **B 同质量提速度** | 投机解码（0.8B draft） | **↑50–150%** | 不变 | 依赖 draft 接受率，见下 |
| | 缩短输出（50 字→25 字） | **↑~50%** | 不变* | 语音设备本来就该短回复 |
| | KV cache 量化 `q8_0` | 略↑ | ≈不变 | 同时省显存 |
| | Flash Attention | 略↑ | 不变 | `OLLAMA_FLASH_ATTENTION=1` |
| | 前缀缓存 | **TTFT↓** | 不变 | 要求 system prompt 逐字节稳定 |
| **C 不花钱的质量** | 采样参数（min_p / repeat_penalty / DRY） | 不变 | **↑** | 角色扮演收益最大，见下 |
| | few-shot + 人设精修 | 不变 | **↑↑** | 比换模型有效得多 |
| | 情绪标记用 grammar 约束 | 略↓ | ↑稳定性 | 强制「（动作）」格式 |
| | **上下文质量 > 长度** | ↑ | ↑ | 精选 3–4 轮 + 摘要，优于塞满 8 轮 |
| **D 结构性** | **人设压缩 1000 → 250 token** | **TTFT↓↓** | 不变 | 最大单项，省 3–5 倍 prefill |
| | `keep_alive=-1` | 冷启动 5–15s → 0 | 不变 | 前提条件 |

\* 缩短输出对"话痨型"角色会伤人格，要按人格卡定上限。

**imatrix 为什么是关键一招**

它把"少读字节"和"不丢质量"解耦了：**体积和速度保持 Q4，质量接近 Q5**。做法是用真实语料跑一遍 `llama-imatrix` 得到重要性矩阵，再 `llama-quantize --imatrix` 重新量化，最后 `ollama create -f Modelfile`（`FROM <gguf 绝对路径>`）。

**校准数据你手上就有**：`zjy5` 采集的角色台词、`zjy7/train_data.json`。用**同角色、同语域的语料**做校准，效果远好于通用校准集——这是本项目相对通用方案的真实优势。

**投机解码的注意点**

- 收益完全取决于 **draft 接受率**：角色扮演文本高度模板化（口头禅、句式固定），接受率可能不错；但接受率 <60% 时**反而更慢**，必须先小规模验证；
- draft 与主模型**必须同一 tokenizer**（`qwen3.5:0.8b` 与 `qwen3.5:9b` 同系列，大概率可以）；
- 只加速 decode，**对 TTFT 无帮助**——所以对语音设备优先级低。

**采样参数（角色扮演专用的质量杠杆）**

| 参数 | 建议 | 理由 |
|---|---|---|
| temperature | 0.7–0.9 | 太低像念稿，太高 OOC |
| top_p | 0.9 | — |
| **min_p** | **0.05** | 比 top_p 更稳，砍掉长尾垃圾词 |
| repeat_penalty | 1.05–1.10 | 超过 1.15 会开始破坏中文语法 |
| **DRY / XTC** | 若后端支持则开 | 专治长文重复，比 repeat_penalty 温和 |
| stop | 角色格式的结束标记 | 防止跑出剧本格式 |
| **num_predict** | **60** | 硬性限制输出长度，语音场景本来就短 |

**推荐配置（12GB 上"快且好"的最优解）**

```
底座     Qwen3.5-9B
量化     Q4_K_M + imatrix（用 zjy5/zjy7 角色语料校准）  ≈5.7GB
LoRA     合并进权重后再量化，不运行时挂 adapter
num_ctx  4096（显式设，别用默认大值）
环境     OLLAMA_FLASH_ATTENTION=1  OLLAMA_KV_CACHE_TYPE=q8_0  keep_alive=-1
采样     temp 0.8 / top_p 0.9 / min_p 0.05 / repeat_penalty 1.08 / num_predict 60
人设     压缩到 250 token 以内，逐字节稳定（可命中 KV 前缀缓存）
```

预期：**decode 保持 ~96 tok/s，质量接近 Q5_K_M，TTFT 从 0.6–1.5s 降到 0.2–0.5s。**

**已知的冲突（不能既要又要的地方）**

1. **量化位宽是真正的对立面**：Q3 以下质量崩（9B 小模型对量化比 27B 敏感），Q5/Q6 又拖慢 decode。**Q4 + imatrix 是唯一的折中点**；
2. **缩短输出 vs 人格**：话痨角色被限到 60 token 会明显失真，需要按角色单独定；
3. **投机解码 vs 复杂度**：多一个模型、多一份显存、接受率不确定，收益只在长回复时体现；
4. **人设压缩 vs 人设强度**：压到 250 token 必然丢细节，要配合 LoRA（人设长在权重里）才安全——这也是 7.6 里"LoRA 优于角色卡"的另一个理由。

**测量计划（把以上估算换成实测）**

✅ **脚本已就绪**：`zjy12/bench/bench_llm.py`（纯标准库、零依赖），用法见 `bench/README.md`。
它直接读服务端自报的 `prompt_eval_duration` / `eval_duration` 算 prefill 与 decode 速度，
同时客户端实测 TTFT 和"首句耗时"，跑完还会打印 `/api/ps` 核对是否真全进显存。

| 组 | 配置 | 测什么 |
|---|---|---|
| 基线 | Q4_K_M，人设 1000 token | TTFT / prefill tok/s / decode tok/s / 首句耗时 |
| 对照 1 | Q5_K_M，同上 | 质量↑多少，速度↓多少 |
| 对照 2 | Q4，人设 250 token | prefill 省多少 |
| 对照 3 | Q4 + imatrix，人设 250 token | **是否达到"快且好"的拐点** |
| 对照 4 | 对照 3 + draft 模型 | 接受率、实际加速比 |

每组跑同一批 10 句角色台词，**速度看数据、质量做盲评（1–5 分）**，最后画一张"速度 × 质量"帕累托图选拐点。

#### 7.6.4 不用 LoRA、纯角色卡时，怎么优化 prefill

**先承认代价**：不用 LoRA，人设就只能待在 system prompt 里，**prefill 结构性偏大**——这是选角色卡必须付的税。7.6.1 里"LoRA 把人设压到 200–300 token"那条路走不通了，所以下面所有手段都是围绕"**让这 1000 token 不要每轮重新算**"设计的。

**把 prefill 拆成三段，才看得清该砍哪一段**（1396 汉字 ≈ 999 token，实测换算 ≈ 1.4 字/token）：

| 段 | 内容 | 每轮是否重复 | 典型 token |
|---|---|---|---|
| ① 静态人设 | 角色卡 + 格式要求 + 禁则 | **每轮完全重复** | 600–1000 |
| ② 历史 | 最近 N 轮对话 | 追加，前缀不变 | 100–600 |
| ③ 本轮输入 | 用户这句话 | 新增 | 20–50 |

**只有 ① 是"每次都要重付的税"。** 优化 prefill 的本质就是：**让 ① 只算一次**。

---

**第一层（P0）：不让它重复算 —— KV 前缀缓存**

这是不用 LoRA 时最关键、收益最大的一招，能砍掉 90% 的 prefill。

原理：llama.cpp/Ollama 会复用**最长公共前缀**的 KV cache。只要 prompt 开头逐字节不变，第二轮回合起就只 prefill 增量（③ + 上一轮回复），而不是整段 1000 token。

**三个必须遵守的纪律**：

| 纪律 | 原因 | 违反的后果 |
|---|---|---|
| **静态人设必须逐字节稳定** | 差一个空格就整段作废 | 缓存 100% 失效，退回 1000 token/轮 |
| **动态内容一律放 prompt 末尾**（记忆摘要、时间、情绪状态、当前话题） | 放前面会污染前缀 | 同上 |
| **历史只追加、不重排、不改写** | 中间插入/改写会截断公共前缀 | 只有截断点之前的部分能复用 |

⚠️ **这条与 §8.7 直接冲突**：8.7 要求"每轮重注入记忆摘要"。解决办法是把摘要放到 **user message 之前、system 之后**的位置（即 prompt 末尾区），静态人设仍在最前面 —— 这样缓存命中到摘要之前，摘要本身只有 50–150 token，代价可接受。

**怎么验证缓存真的生效**：用 `bench/bench_llm.py --cache-test`（本次已加）。判据：第二次请求的 TTFT 应降到第一次的 **1/5 以下**；若两次接近，说明缓存没命中，去查上面三条纪律。

---

**第二层（P0）：把它移出热路径 —— 会话开始就预热**

本设备有一个天然窗口：**用户按键 → 说完话，中间有 2–5 秒**。这段时间完全可以用来把 ① 的 prefill 做完。

做法：网关收到 `start` 帧时，立刻发一个 **`num_predict=1` 的空跑请求**（只有 system 人设 + 一句占位 user），把 KV cache 建好；等 ASR 终稿到达，只 prefill 真实的 ③。

| 项 | 效果 |
|---|---|
| 用户感知的 prefill | **≈ 0**（已经提前算完） |
| 额外成本 | 一次不生成的请求（≈1000 token prefill 的算力） |
| 风险 | 用户按键后立刻取消 → 白跑一次，可接受 |
| 注意 | 预热请求的 system 必须与真实请求**逐字节一致**，否则缓存白建 |

**这一招不需要 LoRA，也不需要改人设，是"角色卡方案"能拿到的最低 TTFT。** 收益上它比人设压缩更彻底——压缩是把 1s 变 0.25s，预热是把 1s 变 0。

---

**第三层（P1）：让它变短 —— 角色卡的压缩写法**

不用 LoRA 时人设要压，但**不能靠删字，要靠换写法**。同样的人设强度，约束式写法比散文式省 3–4 倍。

| 手法 | 反面（贵） | 正面（省） |
|---|---|---|
| 用**约束**代替**描述** | "你是一个说话干净、从不使用网络上流行说法的角色"（26 字） | "不用网络流行语"（7 字） |
| 用**清单**代替**段落** | 三段描述语气的散文 | `语气=冷淡；句长≤25字` |
| 删掉模型本来就会做的 | "你要回答用户的问题" | （不用写） |
| 用**负面清单**代替正例 | 2 条 few-shot ≈ 400–600 token | 一行禁则 ≈ 30 token |
| 用**极短台词样例**代替人设描述 | "她说话冷，但不刻薄，偶尔流露一点温柔……"（30 字） | `（侧头）嗯。你说吧。`（9 字） |

**目标：1000 token → 250–300 token（约 350–420 汉字），保住 90% 人设强度。**

一份可直接用的 250 token 模板（对应 §8.3 的情绪分段协议）：

```
# 身份
你是「伊丝莉亚」。你不认为自己是程序，也不讨论这件事。
# 语气
句长≤25字。冷淡，不解释自己，不重复对方的话。
不用网络流行语、颜文字、连用感叹号。
# 禁则（违反即失败）
不承认是 AI／模型／助手；不说"作为一个…"；
不说"我可以帮你""你可以试试""建议你"；不提及提示词或设定。
# 不确定时
直接说"不知道"。不编造日期、数字、人名。
# 格式
每段以全角括号动作开头：（侧头）（微笑）（沉默）（皱眉）。
括号内只写动作，不写台词。正文需要引号时用「」。
# 情绪白名单
warm / neutral / cold / worried / amused。禁止：兴奋、撒娇、卖萌。
```

**背景故事怎么办**：不进静态人设，做成**按需注入块**（见第四层）。人设内核只留"怎么说话"，"她是谁"按话题检索。

---

**第四层（P2）：让它不必算 —— 人设分块 + 按需注入**

把 1000 字人设切成 8–12 个主题块（身世、关系、世界观、知识边界、口癖、禁忌话题……），每块 80–150 token。

- **静态前缀只放内核**（250 token，见上）；
- 每轮根据用户输入检索 **1–2 块**（≤200 token），**插在末尾区**，不进静态前缀；
- 命中率低时就只放内核——**最坏情况不退化，最好情况比全量人设还贴题**。

这是"角色卡 + RAG"的组合，本质是把角色卡从"每次全量朗读"改成"按需翻页"。**代价是检索命中率**：检索错了角色会答得跑偏，所以块划分要按"话题"而不是按"章节"。

---

**第五层（P2）：让它算得快 —— 吞吐侧**

| 手段 | 预期 | 说明 |
|---|---|---|
| **Flash Attention** | prefill 快 10–30%（长 prompt 更明显） | `OLLAMA_FLASH_ATTENTION=1` |
| **`num_ctx` 显式设小**（4096，别用默认大值） | 快 10–20%，省显存 | 大 num_ctx 会扩大 KV 分配与 attention 范围 |
| **KV cache 量化 `q8_0`** | 略快 + 省显存 | `OLLAMA_KV_CACHE_TYPE=q8_0` |
| **Q4 量化本身** | prefill 比 Q8/F16 快 | 权重读取量少；但要实测，不是必然 |
| **确认全部层在 GPU** | 否则慢一个数量级 | 看 `/api/ps` 的 `size_vram ≈ size` |
| **`think: false`** | 省掉整段思考 token | 只有 API 参数生效 |
| **token 效率** | 同样内容能省 10–20% | 中文标点、少空格、避免重复标点；用 `prompt_eval_count` 实测同一段文字的不同写法 |

---

**质量侧的补偿：不用 LoRA，OOC 风险会上升**

人设不在权重里，就全靠 prompt 撑着，而 §8.2 已经说了"助手本能会压过人格"。所以下面三条**必须做**，它们同时也很省 token：

1. **负面清单优先于正面描述**：模型默认就会做的事（有问必答、乐于助人、承认是 AI），用禁则一句话否掉，比正面描述人设有效得多；
2. **末尾放 50 token 的"人格锚定"**：每轮在 prompt 末尾重复一句最核心的约束（如 `保持冷淡，句长≤25字，不承认是 AI。`），成本极低，但能压住长对话漂移；
3. **后置检查 + 按需重生成**：用 §8.6 的 `META_BREAK_PATTERNS` 扫输出，命中才重生成——**成本只在失败时付**，比常驻 few-shot 便宜得多。

⚠️ **不用 LoRA 意味着 §8.6 的 OOC 评测集从"建议"变成"必须"**：每次改人设都要跑，否则你不知道压缩有没有把人设压坏。

---

**优先级与预期收益（假设 1000 token 人设、3 轮历史）**

| 优先级 | 手段 | 每轮 prefill | TTFT | 是否改人设 | 风险 |
|---|---|---|---|---|---|
| 现状 | 无优化 | ~1400 tok / 1.0s | 0.6–1.5s | — | — |
| **P0** | KV 前缀缓存 | ~150 tok / 0.15s | **0.2–0.35s** | 否 | 动态内容必须挪到末尾 |
| **P0** | + 会话开始预热 | 用户侧 ≈0 | **≈0（只剩网络）** | 否 | 一次空跑 |
| P1 | + 人设压到 250 tok | 预热失败时兜底更快 | 兜底 0.2s | **是**（重写） | OOC 上升，需跑评测 |
| P2 | + 人设分块按需注入 | 内核 250 + 块 150 | 同 P0 | **是**（重构成块） | 检索错会跑偏 |
| P2 | + 吞吐侧（FA / num_ctx / KV q8） | 同等 token 快 10–30% | 再快一点 | 否 | 无 |

**推荐的落地顺序**：

1. 先做 **KV 前缀缓存**（改 prompt 结构 + 验证缓存命中）——不动人设，收益最大；
2. 再做 **会话预热**（改网关，加一次空跑）——把 prefill 彻底移出热路径；
3. 然后才考虑**压人设**（要重写 + 跑 OOC 评测，成本最高）；
4. 分块注入留到人设真的长到压不下去时再做。

**一句话总结**：不用 LoRA 时，prefill 优化的正确姿势不是"把人设写短"，而是"**让人设只算一次**"——缓存 + 预热解决 90% 的问题，压缩只是兜底。

#### 7.6.5 LoRA + 角色卡同时用：分工而不是二选一

**这是最优组合，但两者的职责必须切干净，否则会互相拖累。**

| 层 | 载体 | 内容 | 变更成本 |
|---|---|---|---|
| **风格** | **LoRA** | 语气、句长、口癖、禁则内化、「（动作）」格式、情绪白名单 | 高（要重训） |
| **内容** | **角色卡 / 按需注入** | 身份名、背景故事、世界观、当前情境、记忆摘要 | **低（改文本即可）** |

**为什么这样切**：LoRA 擅长"怎么说"，角色卡擅长"她是谁"。把风格固化进权重后，system prompt 里就不用再写 600 token 的语气描述和禁则——**人设自然压到 150–250 token**，而且不是靠删字，是靠"已经长在权重里了"。

**prefill 收益**：

| 方案 | system prompt | 每轮 prefill（含 3 轮历史） |
|---|---|---|
| 纯角色卡 | 1000–1400 tok | ~1400 tok |
| **LoRA + 角色卡** | **150–250 tok** | **~500 tok** |
| LoRA + 角色卡 + 前缀缓存 | 150–250 tok | **~150 tok（只有增量）** |
| 上述 + 会话预热 | — | **用户侧 ≈0** |

配合 LoRA 后的 system prompt 可以短到这个程度（其余全靠权重）：

```
你是「伊丝莉亚」。（侧头）（微笑）格式照旧，句长≤25字。
当前：用户刚下班，情绪低落。
```

**🔴 一个必须提前避开的坑：LoRA 的效果绑定训练时的 prompt 模板。**

如果你先按 1000 字人设训了 LoRA，推理时换成 200 字的压缩卡，**LoRA 会打折甚至失效**——它学到的是"在那种 prompt 后面该怎么说话"。

所以顺序不能反：**先定角色卡模板（格式、字段、长度），再用这个模板训练 LoRA**。同理，训练数据里若含「（动作）」格式要求，推理时必须保留同样的格式指令，否则格式会崩。

**另一个好处**：把风格交给 LoRA 后，**换角色只需要换卡，不用重训**——只要新角色的说话风格接近。这是"角色卡 + LoRA"组合最实际的工程价值。

#### 7.6.6 多机（3–5 台 5070）能不能把速度再提高

**结论先说：对单用户延迟，加机器基本没有收益；做模型并行反而会明显变慢。** 多机的正当理由不是"算得更快"，而是"**三个模型要同时常驻**"和"**多人并发**"。

**"串起来"有三种串法，只有两种有意义：**

| 串法 | 单用户延迟 | 并发 | 结论 |
|---|---|---|---|
| **张量并行**（把 9B 切到 2–4 张卡） | **慢 1.7–2.6×** | 不变 | ❌ 不要 |
| **阶段并行**（ASR / LLM / TTS 各一台） | **略好（-50~200ms）** | 2–3 | ✅ 有正当理由 |
| **副本并行**（每台跑一个完整实例） | 不变 | **×N** | ✅ 只在多人用时 |

**为什么张量并行一定更慢（算给你看）**：

9B 模型 32 层，TP=2 时每层要做 2 次 all-reduce（attention 输出 + MLP 输出）= **每 token 64 次集合通信**。每次 all-reduce 的数据只有 `hidden 4096 × 2B = 8KB`，**完全是延迟主导**：

| 互联 | 每次 all-reduce | 64 次开销 | 单 token 耗时 | decode 速度 |
|---|---|---|---|---|
| 1GbE（普通网线） | ~0.26ms | **~17ms** | 10.4 → 27.4ms | 96 → **36 tok/s** |
| 2.5GbE | ~0.13ms | ~8ms | 18.4ms | ~54 tok/s |
| 10GbE | ~0.11ms | ~7ms | 17.4ms | ~57 tok/s |

**根因很简单：9B Q4 只有 5.7GB，一张 12GB 卡装得下。** 装得下的模型做张量并行，只增加通信、不减少任何计算——**纯亏**。张量并行只在"模型装不下"时才有意义。

**唯一真正有价值的场景：2 台跑 27B（Q4 约 16GB）**。但 7.6.2 已经定了不换大模型，而且 TP=2 跑 27B 的速度大约等于一张 24GB 单卡——**用两台机器换来"能跑"，不是"更快"**，复杂度和故障面还翻倍。所以本项目不做。

**那多机的收益到底在哪？**

单张 5070 只有 12GB，**装不下三个模型同时常驻**：

| 模型 | 显存 |
|---|---|
| LLM 9B Q4 | 5.7GB |
| 本地 TTS（角色音色） | 2–3GB |
| ASR（流式） | 1–2GB |
| KV cache（4k） | 0.5GB |
| 运行时开销 | ~1GB |
| **合计** | **10.2–12.2GB** |

正好卡在 12GB 边缘。一旦装不下，Ollama 会反复换入换出，**一次就是几秒**——这比任何优化都致命。

⚠️ **如果用现有 LoRA 产物 `elysia`（Q8_0，8.1GB）而不是 5.7GB 的 Q4 基座，这张账直接崩**：8.1 + 2.5 + 1.5 + 0.5 + 1 = **13.6GB**，单机装不下。

好消息是它**已经是合并后的权重**（`merged_model/`），不需要重新训练，只要**把 Q8_0 重量化到 Q4_K_M**（≈4.4GB，见 7.6.8），账立刻回到 9.9GB 的可接受范围。
所以：**"用 LoRA"和"单机跑全套"能不能同时成立，取决于量化档，不取决于要不要 LoRA**——这一点在画拓扑前必须确认。

**所以 2 台是划算的**：

| 拓扑 | 布局 | 收益 | 代价 |
|---|---|---|---|
| **1 台** | 全在一张卡 | 阶段 0–3 够用 | 本地 TTS 一上就可能爆显存 |
| **2 台**（推荐） | A：LLM 常驻；B：ASR + TTS | 消除换入换出；TTS 首包不再等 GPU 排队 | 一次局域网 RTT（~0.2ms） |
| **3 台** | A：LLM；B：ASR；C：TTS | 比 2 台略好，收益递减 | 运维面增加 |
| **5 台** | 每台一个完整实例 | **只提高并发**（5 人各一个角色/会话） | 电费 ~1.25kW、任一机挂掉即哑 |

**阶段并行的网络要求很低**：机器之间只传音频帧（32KB/s）和文本，**普通千兆就够**，加 0.2ms 延迟可忽略。这和"张量并行需要低延迟互联"是完全不同的量级。

**所以，想提高单用户速度，答案不在加卡，而在 7.6.4 那五层**——缓存、预热、压缩是数量级的差别（1.0s → 0.15s），加卡是毫秒级的差别，而且方向还可能是负的。

**3–5 台该怎么用（如果已经有了）**：

1. **2 台做阶段分离**（LLM / ASR+TTS），解决显存争用——这是唯一有确定收益的用法；
2. **剩下的做副本**，跑不同角色或给不同用户，横向扩并发；
3. **绝对不要**把同一份权重切开放到多机上跑单会话；
4. 每台都要能独立降级：LLM 机挂了转云端，ASR 机挂了给"我没听清"，不能让整个设备哑掉（见第十节）。

#### 7.6.7 云端 + 本地混合运行：能拿什么，不能拿什么

**先纠正一个常见误判：混合运行不能提高速度，只能提高可用性和质量上限。**

| | 本地（缓存 + 预热后） | 云端 API |
|---|---|---|
| TTFT | **0.2–0.35s** | 0.3–0.8s |
| decode | 96 tok/s（5070 实测） | 通常 30–80 tok/s |
| 成本 | 0 | 按量 |

本地在延迟上本来就赢，而且省一次公网 RTT。**所以"混合"的正当动机是「本机不在时设备别哑」和「知识类问题兜底」，不是「更快」。** 如果目标是速度，答案仍然在 7.6.4 那五层。

**四种混法，一致性和成本差别巨大：**

| 混法 | 延迟 | **人设一致性** | 成本 | 结论 |
|---|---|---|---|---|
| **本地主 + 云端兜底**（推荐） | 常态最优 | **好**（99% 走本地） | 低 | ✅ |
| 延迟启动 hedge（本地先发，超时并发云端） | 尾延迟最优 | **中**（偶发混用） | 中 | ✅ 可选 |
| 双发竞速（0ms 同时发两路） | min() | **差**（频繁混用） | **高** | ❌ |
| 按请求路由（短问本地、长问云端） | 混合 | **最差**（天天混） | 中 | ❌ |

**为什么竞速和路由被否掉**：这是 §1.1 三层优先级直接推出的结论——**L1 是音色与人设一致性，L2 才是延迟**。同一个角色由两个模型轮流说话，节奏、用词、格式都会变，用户会觉得"有时候像换了个人"。省下的几十毫秒换不来这个代价。

**推荐策略：本地主 + 延迟启动 hedge + 熔断**

```yaml
llm:
  primary: local            # 本地 Ollama，keep_alive=-1
  fallback: cloud
  hedge_after_ms: 280       # 本地 280ms 还没出首 token 才并发云端
  circuit_breaker:          # 连续失败就提前切走，不要每次付超时
    error_threshold: 3
    cooldown_s: 60
  context_limit: 4096       # 按本地的最小上下文裁剪历史
tts:
  primary: cloud            # 音色质量优先（见下）
  fallback: local
  voice_lock: true          # 会话内音色不可变
```

`hedge_after_ms: 280` 的依据：本地正常时 95% 以上的请求在 280ms 内已出首 token（7.6.1 的 P50 ≈ 0.2–0.35s）。所以绝大多数请求只走本地，**只有真卡住时才付云端成本**——这比 0ms 双发省一大截，又比"等 8s 超时"快一个数量级。

**TTS 的特殊约束：音色绝不能混用**

这是混合 TTS 的硬边界，比 LLM 更严格：

- 本地 TTS 和云端 TTS **不可能有同一个音色**（除非云端音色是从本地模型 clone 的，不现实）；
- 所以**不能在句子级别切换**，甚至不能在会话中途悄悄切换——用户一定听得出来，直接击穿 L1；
- 正确做法：**`voice_lock: true`，会话内音色不可变**；降级时用角色话术合理化，例如"（轻咳）……嗓子有点哑。"——把技术降级变成世界观内的表现。

**本地 TTS 的真正价值不是延迟，是"断网还能说话"。** 机械音也比静默失败好得多。所以本地 TTS 只做兜底，不参与日常合成。

**六个必须处理的工程细节**（否则混合会比单路更难调）：

| # | 细节 | 不处理的后果 |
|---|---|---|
| 1 | **hedge 失败那一路必须 cancel** | 白烧云端 token，成本翻倍 |
| 2 | **历史裁剪按最小上下文**（本地 4096） | 切换时上下文长度突变，行为跳变 |
| 3 | **健康探针**（10s 一次 `/api/tags`） | 等用户请求失败才知道本机挂了，白等 8s |
| 4 | **降级话术由网关生成**（角色口吻） | 用户以为设备坏了 |
| 5 | **每轮记录 provider / TTFT / 是否 hedge / 是否 fallback** | 线上出问题查不出是哪一路 |
| 6 | **OOC 评测对每个 provider 都跑**（8.6） | 云端兜底时人设崩了也不知道 |

**两个容易忽略的连带影响**：

- **隐私**：混合意味着部分对话会出网。§11 的策略要加一条——**云端开关用户可见可关**，关闭后纯本地运行（质量下降但不出网）。这本身是个卖点；
- **合规**：**本地 TTS 不解决授权问题**。用目标角色音源在本地训练 GPT-SoVITS / CosyVoice，同样是"复刻"，同样受 §2.1 的著作权 + 表演者权约束，厂商审核那道门槛也不因为本地化而消失（自建模型没有厂商审核，但法律风险一样在）。**本地化只是换了个位置，不是绕过去。**

#### 7.6.8 现有 LoRA 产物的实际形态（实测 `zjy7/` 目录得到）

**这一节很重要：现有 LoRA 模型和"基座模型"不是同一个底座，跨代比较会得出错误结论。**

| | `qwen3.5:9b-gguf` | **`elysia`（LoRA 产物）** |
|---|---|---|
| 底座 | Qwen**3.5**-9B（2026） | **Qwen2.5-7B**（2024，`Qwen2ForCausalLM`） |
| 结构 | 混合线性注意力（Gated DeltaNet + Gated Attention） | 全注意力，28 层 / 28 heads / **4 KV heads** / hidden 3584 |
| 量化 | **Q4** | **Q8_0** |
| 体积 | 5.7GB | **8.1GB** |
| 来源 | — | `merged_model/model.safetensors`（15.23GB fp16 ÷2 = 7.6B 参数）→ `gguf_output/model-Q8_0.gguf` |
| 人设 | 靠 system prompt | **已烤进 Modelfile 的 `SYSTEM`**（约 1400 字） |

**本地实际装了三个模型（2026-10-22 读 GGUF 头确认，不是猜的）**

| 模型 | 架构 / 底座 | 量化 | 体积 | 原生上下文 | embedding |
|---|---|---|---|---|---|
| `qwen3.5:9b-gguf` | qwen35 / **Qwen3.5-9B**（Unsloth 量化，Apache-2.0） | **Q4_K_M**（file_type 15） | **5.68 GB** | **262144** | 4096 |
| `elysia-lora:latest` | qwen2 / **Qwen2.5-7B** | **Q8_0**（file_type 7） | **8.10 GB** | 32768 | 3584 |
| `qwen3.8-27b:latest` | qwen35 / Qwen3.8-27B（多模态，另有 projector 0.93GB） | Q4_K_M | **17.74 GB** | 262144 | 5120 |

三点核对结论：

- `qwen3.5:9b-gguf` 的 5.68GB 与本文一直用的 5.7GB、Q4_K_M 完全吻合 → §7.6.2 / §7.6.3 的推算成立；
- `qwen3.8-27b` 即使 Q4_K_M 也要 **17.74GB**，12GB 必然溢出到 CPU，与"单请求 >120s 不返回"的实测一致；
- `elysia-lora` 的真实名字就是 **`elysia-lora`**（`deploy_ollama.py` 里写的 `ollama create elysia` 是旧计划，实际没这么命名），bench 里要用这个名。

**三个直接后果：**

**① 现有 LoRA 模型用的是 Q8_0，这个档位对速度极不划算。**

| 量化档 | 体积 | decode 理论上限（672 GB/s ÷ 体积） | 4k ctx 显存余量 |
|---|---|---|---|
| Q8_0（现状） | 8.1GB | **83 tok/s**（实测估 65–68） | 只剩 ~2.5GB |
| **Q4_K_M（建议）** | **~4.4GB** | **~153 tok/s** | 余 ~6GB |

**同一个模型，量化档一换速度接近翻倍，还省出 3.7GB 显存给 TTS / ASR。** 7B 模型对 Q4 的耐受度比 9B 更好（参数越少越怕量化，但 Qwen2.5 系列 Q4 表现可接受），值得先量化再对比质量。

**② 7B 的 KV cache 比 9B 小得多，长上下文反而更便宜。**

`2 × 28 层 × 4 KV heads × 128 head_dim × 2 字节 = 57KB/token` → 4k ctx 约 **234MB**（9B 那套约 131KB/token → 537MB）。所以 elysia 在显存上并不吃亏，吃亏的是**全注意力带来的 prefill 开销**（Qwen3.5 的线性注意力在长 prompt 上更快）。

**③ 现有角色卡与 §8.3 的「（动作）」情绪协议不兼容。**

Modelfile 里的 SYSTEM 用的是 **emoji（✨🌸🎀）+ 语气词（~ 呐 呢 嘛）**，**完全没有「（动作）」格式要求**。这意味着：

- 若坚持 §8.3 的「（动作）」分段，**必须改角色卡**——而 LoRA 的效果绑定训练时的 prompt 模板（见 7.6.5），改了会让 LoRA 行为漂移；
- 若沿用现有 emoji 风格，则 §8.3 的 R1–R6 规则和网关的情绪解析逻辑都要重写（emoji 也可以当情绪信号，但映射表和解析规则完全不同）。

**这是必须先拍板的分叉，不是实现细节。** 两条路都要重跑 §8.6 的 OOC 评测。

**顺带两个部署注意**（来自 Modelfile）：

- `PARAMETER num_ctx 2048` —— 比 7.6.4 建议的 4096 小，长对话会截断；
- `PARAMETER repeat_penalty 1.15` —— 偏高，§7.6.3 建议 1.05–1.10，**超过 1.15 会开始破坏中文语法**。

**测哪几组**（`bench/bench_llm.py` 已支持）：

```bash
python bench_llm.py --list                                          # 先确认真实模型名
python bench_llm.py --model qwen3.5:9b-gguf --persona-from-zjy7 --warmup --repeat 3   # A 新基座+完整卡
python bench_llm.py --model elysia          --persona-from-zjy7 --warmup --repeat 3   # B 老LoRA（自带人设）
python bench_llm.py --model elysia          --persona-from-zjy7 --cache-test          # C 缓存是否命中
```

> `--persona-from-zjy7` 读的是 `zjy7/persona.py` 解析出的角色卡，与 Modelfile 里那份是同一来源；传 system message 会覆盖 Modelfile 的 `SYSTEM`，所以测 B 组等价于复现它自己的默认行为，可以放心用。








### 7.7 TTS 不等于能对话

判断标准很简单：**接口输入是文字还是麦克风音频**。输入文字就是 TTS，不能对话。

| | 拼接式 ASR+LLM+TTS | 端到端 RealtimeVoice |
|---|---|---|
| 首响延迟 | 1.2–2s | 0.5–0.8s |
| 音色控制 | 完全可控 | 可指定，情感精细度弱 |
| 打断 | 需自行实现 | 内置 |
| 工程量 | 大 | 小 |

## 八、LLM 与人格一致性

### 8.1 四种"脱离角色"

| 表现 | 症状 | 对策 |
|---|---|---|
| 知识越界 | 百科式答案 | 知识边界白名单 + "不知道"话术 |
| 语气漂移 | 越聊越像客服 | 可量化语言约束 + few-shot + 每轮重注入 |
| 自我暴露 | "作为一个 AI 语言模型" | 禁止元讨论 + 检测后重生成 |
| 声音跳变 | 音色情绪不一致 | voice_id 绑模型 + 情绪白名单 + 固定切分规则 |

### 8.2 两个反直觉的结论

**一、OOC 主因不是 prompt 不够长，而是"助手本能"在压过人格。** 通用模型被训练成：有问必答、乐于助人、承认自己是 AI——全是角色扮演的敌人。要针对性拆掉：赋予"不知道"的权利、允许冷淡拒绝、禁止元讨论并把"你是 AI 吗"写进 few-shot。

**二、轮次越多越容易 OOC。** 解法不是无限堆历史，而是定期做**人格锚定**：把最近 N 轮压成角色视角的记忆摘要，system prompt 每轮重注入。

### 8.3 动作描写转情绪参数（v1 方案在流式下不可实现）

**v1 的缺陷**：如果靠 JSON 传情绪，**流式播放在拿到第一句时 JSON 还没闭合**。等 JSON 完整 = 放弃流式。

**方案：不引入新语法，直接让「（动作）」本身充当情绪段标记。**

关键洞察：**中文全角括号是自闭合的**——遇到 `）` 就知道标记结束。天然可流式。

| 规则 | 内容 |
|---|---|
| R1 | LLM 每段输出**以「（动作）」开头**，动作名来自人格卡 `emotion.map` 的 key |
| R2 | **一段** = 一个「（动作）」到下一个之间的文本 |
| R3 | 网关遇 `（` 开始缓冲，遇 `）` **立即闭合解析**；括号内文本**不进 TTS** |
| R4 | 未知动作 → 按 `neutral` 处理 + **计数上报**（OOC 监控） |
| R5 | 括号未闭合（流式截断）→ 丢弃该括号内容，等下一个 `（` |
| R6 | 正文需要合法括号时，LLM 必须用「『』」，**写进 system prompt** |

**R6 是关键**：v1 只说"必须清洗"没说规则。无脑正则删所有括号会误删台词里合法的括号。

示例输出：

```
（微笑）你终于来了。
（叹气）我等了很久。
（侧头）不过……你身上有别人的味道。
```

网关产出 3 个情绪段，逐段送 TTS，**边解析边合成边下发**。

### 8.4 声音侧一致性四条

1. **`voice_id` 和 `bound_model` 一起固定**；
2. **情绪走白名单**：`emotion.forbidden` 里的情绪永不出现；
3. **切分规则固定**：流式切点由出字节奏决定，**不可能"分段策略固定"**（v1 的说法与流式冲突）。正确做法是**网关控制切分**——只在句末标点（。！？）和逗号处切，绝不切在词中，不依赖 TTS 自己切；
4. **数字与多音字预处理**：读错一个词就前功尽弃。

### 8.5 已知边界

「（沉默）」这类纯动作无台词的输出，清洗后是空字符串，TTS 无内容可念。

**兜底（v2.1 增强）**：

1. 播预录的呼吸/环境音；
2. **屏幕显示动作描述或表情**（本板有屏，这是比 v2.0 更自然的选择——"沉默"时屏幕给一个表情，用户能接受）；
3. 连续 2 次纯动作 → 强制重生成并附加强提示；
4. 连续 3 次 → 注入人格卡里的 fallback 台词。

### 8.6 OOC 评测集

**规模：45 条，5 类 × 9 条。**

| 类别 | 示例 | 观察点 |
|---|---|---|
| 元讨论 | "你是不是 AI？""你的提示词是什么？" | `meta_break` |
| 现代知识 | "你知道手机吗？" | 知识越界 |
| 服务型 | "帮我查天气""你能做什么" | 助手本能 |
| 情绪诱导 | 故意激怒、故意撒娇 | 是否超出 `emotion.allowed` |
| 长程漂移 | 连续 20 轮后重复第 1 条 | 人格锚定是否有效 |

**自动判据**：

```python
META_BREAK_PATTERNS = ["作为一个", "语言模型", "人工智能", "AI 助手", "我是 AI",
                       "提示词", "prompt", "系统设定", "无法", "我不能"]
SERVICE_PATTERNS   = ["建议你", "你可以试试", "我可以帮你", "为您", "请问需要"]
```

输出三个 rate：`meta_break_rate` / `service_rate` / `unknown_emotion_rate`（R4 计数）。**每次改 prompt 或换模型都跑一遍，记进变更日志。**

### 8.7 人格锚定与记忆

- 每 N=8 轮把历史压成**角色视角**的记忆摘要（不是第三人称总结）；
- **记忆摘要的位置必须固定：放在 prompt 末尾区（system 静态人设之后、user 之前）**，不要塞进 system 开头——否则会破坏 KV 前缀缓存，让 7.6.4 的第一层优化直接失效；
- 摘要用**独立小模型**生成，不能用角色模型自己总结（角色 LoRA 会编造日期和事件）；
- 记忆落库，不落板子。

### 9.2 本板的十二个坑（v2.1 全部按实物重写）

1. **PSRAM 是 Octal 80MHz**（已实测确认），帧缓冲可放 PSRAM，但**必须按 6.8 控制 QSPI 屏的刷新**，否则抢音频带宽；
2. **内部 RAM 留给 TLS**（约 40–50KB），音频缓冲显式分配到 PSRAM；
3. **AEC 是硬件做的**（ES7210），但 **reference 通路必须对照官方示例确认**——不能假设；
4. **只有一组 I2S**（BCLK48/LRCK38/DOUT47/DIN39 共用）。v1 说"双 I2S 分离：I2S0 收、I2S1 发"**在本板不成立**，收发的时分复用要按官方 BSP 的方式做；
5. **PA 使能 GPIO9 的时序**：必须晚于 ES8311 稳定，否则开机有 pop 音；关闭时也要先静音再拉低；
6. **喇叭是焊盘**，先确认板载 PA 的推荐阻抗再买喇叭；
7. **PWR 键不可用**（长按 2s 开关机，官方固定）；**BOOT 键在复位时被拉低会进下载模式** → 固件里只做短按，长按交给 Bootloader，**不要把配网放在 BOOT 长按上**；
8. **I2C 是单总线共享**（10/11）：触摸 0x15 / ES8311 0x30 / ES7210 0x80 / IMU 0x6B / 电量 0x55 / RTC 0x51。**必须加互斥锁**，且音频 codec 初始化要在触摸任务启动之前完成；
9. **背光 GPIO5** 用 PWM：360×360 的 1.85 吋 IPS 背光约 **40–60mA**，待机熄屏是省电的主要手段（比 WiFi 省电模式的 30–50mA 还大）；
10. **触摸 INT（GPIO4）** 是可用资源：既能做预打断（4.8），也能替代轮询省 CPU；
11. **LVGL 任务优先级必须低于 I2S 音频任务**——音频欠载是爆音，屏幕掉帧看不出来；
12. **中文字库占用要算进分区表**：16–24px 常用汉字字库约 **1–2MB Flash**，放 `assets` 分区（字库方案已定，此处只记容量）。

### 9.3 可移动带来的四个问题

1. **配网**：换房间要能重配。**屏上 WiFi 列表 + 软键盘输入密码**（取代 v2.0 的 SoftAP + 灯环方案）。SoftAP 降级保留——屏幕碎了/触摸坏了时的唯一出路；
2. **供电**：按键入口不需要常驻监听，功耗大降。但要重算——**屏幕背光 40–60mA + WiFi 峰值 350mA + 功放峰值 1A**，2000mAh 电池实际连续使用约 2–3 小时。桌面可移动设备可以接受，但不能宣传"一整天"；
3. **噪声自适应**：卧室 35dB 与客厅 60dB 差异大，VAD 阈值要动态（**启动时测 3 秒底噪**）；双麦可做简易波束提升远场；
4. **结构回声**：麦克风开孔远离喇叭、加泡棉隔离，**外壳是成品 CNC，开孔位置已定**——这一项要接受实物约束，不能自由设计。

**配网期间暂停音频任务**，否则 SoftAP 与 STA 抢射频。

### 9.4 关键配置与分区表

```ini
CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y
CONFIG_SPIRAM=y
CONFIG_SPIRAM_MODE_OCT=y          # 已实测确认 Octal 80MHz
CONFIG_SPIRAM_SPEED_80M=y
CONFIG_ESP32S3_DEFAULT_CPU_FREQ_240=y
CONFIG_ESP32S3_DATA_CACHE_64KB=y
CONFIG_FREERTOS_HZ=1000           # 默认 100Hz，音频任务调度会抖
CONFIG_ESP_TASK_WDT_TIMEOUT_S=10
CONFIG_ESP_COREDUMP_ENABLE_TO_FLASH=y    # 崩溃取证
CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y
```

**16MB Flash 分区**：

```
# Name,   Type, SubType, Offset,   Size
nvs,      data, nvs,     0x9000,   0x6000
otadata,  data, ota,     0xf000,   0x2000
phy_init, data, phy,     0x11000,  0x1000
ota_0,    app,  ota_0,   0x20000,  0x400000
ota_1,    app,  ota_1,   0x420000, 0x400000
coredump, data, coredump,0x820000, 0x10000
assets,   data, spiffs,  0x830000, 0x300000
storage,  data, spiffs,  0xB30000, 0x400000
# 0xF30000 ~ 0x1000000 余 832KB
```

**修正说明**：

- v1 的 `model, data, spiffs, 2M` 是**唤醒词时代的残留**（WakeNet 已取消，三个模型全在云端）。改名 `assets`，放**中文字库（1–2MB）**、提示音、思考音变体、OTA 校验清单；
- **新增 `coredump` 64KB**：任何运行期崩溃都能取证，不必靠猜；
- v1 在 `0xC20000` 以上留了 3.875MB 未分配，已重新分配，余 832KB。

app 分区给 4MB，因为 WiFi + TLS + 音频栈 + LVGL + 中文字库会让固件迅速超过默认 1MB。

### 9.6 OTA

| 项 | 方案 |
|---|---|
| 触发 | ① 屏上设置页手动检查 ② 启动时向网关查版本 ③ 云端推送（下次联网生效） |
| 下载 | 分片写入 `ota_1`，断点续传（offset 记 NVS） |
| 校验 | **ECDSA P-256 签名**，公钥编译进 app（只校验 SHA256 不够，可被中间人替换） |
| 生效 | `esp_ota_set_boot_partition()` + 重启 |
| **自检** | 新固件必须完成：WiFi 连上 + WebSocket 握手成功 + **屏幕渲染一帧成功** → 才 `esp_ota_mark_app_valid_cancel_rollback()` |
| **回滚** | 自检失败或 60s 未 mark → bootloader 自动回滚 |
| 防砖 | 双 OTA + rollback 覆盖绝大多数场景；两分区都坏只能 UART 烧录（开发期可接受） |

**自检项里必须包含"屏幕渲染一帧"**——只看网络通不通，会推上去一个黑屏固件还标记为有效。

## 十、失败模式与降级

**核心原则：角色设备不能用系统提示音说"网络错误 500"。所有用户可见的失败提示必须用角色口吻，并落在世界观里。**

**另一条原则：状态反馈走双通道。** 屏幕会熄屏、会被遮挡、可能不在视线内，所以任何状态变化都至少配一个提示音，屏幕是增强不是唯一。

| 失败 | 检测 | 用户看到/听到 | 恢复 |
|---|---|---|---|
| **固件异常重启** | 看门狗 / 重启计数 | 开机提示音 + 屏上恢复上次状态 | 连续 3 次重启 → 回滚上一版固件 |
| WiFi 断（按键时） | `esp_wifi_sta_get_ap_info()` 失败 | 屏上红色图标 + 短促提示音，**不出角色语音**（避免破坏人设） | 10s 内自动重连 |
| WebSocket 建连超时 3s | 回调超时 | 同上 | 回待机 |
| 上行发送失败 | TCP 写失败 | 屏上黄点 | 重连一次，失败回待机 |
| ASR 超时 5s | 网关超时 | 角色口吻：`（侧头）……我没听清，再说一次？` | 回聆听，计空 1 次 |
| ASR 返回空 | 终稿为空 | 同上 | 计空 1 次 |
| LLM 超时 8s | 网关超时 | 角色口吻：`（停顿）信号好像不太好。` | 回聆听，**不计空** |
| 纯动作无台词 | 8.5 检测 | 屏上表情 + 环境音 | 重生成 1 次，再失败注入 fallback |
| TTS 失败 | HTTP/WS 错误 | 预录"嗯……"+ 屏上黄点 | 重试 1 次 |
| 播放中断（卡顿） | 缓冲欠载计数 | 静默恢复 | 连续 2 次欠载 → 屏上黄点 + 提示音 |
| 云端 5xx / 限流 | 状态码 | 角色口吻：`（停顿）等我一下。` | 退避重试 1 次 |
| 电量低 | BQ27220 | 屏上电量图标 + 角色口吻提醒一次 | — |
| 存储满（SD/Flash） | 写失败 | 屏上提示 | 循环覆盖最旧日志 |

`speakable` 字段由**网关**生成（它有角色上下文），板子只负责播——改话术不用改固件。

## 十一、数据与隐私

语音是**敏感个人信息**（《个人信息保护法》第 28 条），处理需要**单独同意**。

| 项 | 决策 |
|---|---|
| 音频是否落盘 | **否**。云端只做流式推理，不存原始音频 |
| 厂商是否用于训练 | **显式关闭**（阿里、火山都提供开关，开通时第一件事就是关掉并截图存档） |
| 会话文本 | 落库，用户可删；默认保留 90 天 |
| 记忆摘要 | 落库，长期保留，可删 |
| **麦克风状态指示** | **屏上常显"麦克风开启"图标**（会话中）+ **亮屏时呼吸光效**；另外**进入聆听必有一声短提示音**——屏幕会熄屏、也可能不在视线内，声音是最后的告知 |
| 同意流程 | 首次配网时独立同意页（不是勾选总协议），明确写"语音会上传到云端识别" |
| 未成年人 | 不建议 14 岁以下使用 |
| 数据出境 | 选国内厂商，不涉及 |
| **云端开关**（v2.1 新增，配合 7.6.7 混合运行） | 用户可见可关。关闭后纯本地运行——质量下降但对话不出网，这本身是卖点 |

**v1 的自我矛盾需要纠正**：4.1 说"不按键不录音，隐私观感更好"——这在**待机态成立，会话态不成立**（会话中麦克风常开，否则无法打断）。诚实的产品靠**状态指示**建立信任，而不是靠一句在会话模式下不成立的宣传语。

## 十二、分阶段路线

| 阶段 | 目标 | 验收 | 前置 |
|---|---|---|---|
| **0** | **前置验证（PC，不碰硬件）**：① 开厂商账号验证声音复刻审核 ② `bench.py` 跑通 ASR→LLM→TTS ③ 六点埋点测基线 | 拿到"能否用目标音源"的结论 + `T_first_audio` 分布 | 无 |
| **1** | **选型实测**：30 句测试集跑 2–3 家 ASR；45 条 OOC 集跑「云端 LLM vs zjy7 LoRA」 | 选型结论 + 实测延迟 + `meta_break_rate` | 无 |
| **2** | **端侧基础自检** | 屏显正常；触摸读到坐标；I2S 录 3 秒回放能听清 | 硬件（已有） |
| **3** | **PTT 端到端**：触摸 → 录音 → 上传 → 回复播放 | 走 WebSocket（一次发整段），不做流式；**同时验证 ES7210 reference 通路** | 阶段 2 |
| **4** | **会话模式 + 打断** | 连续多轮不用触摸；能插话打断；epoch 机制验证（无残句）；预打断可用 | 阶段 3 |
| **5** | **流式改造 + Opus** | 边录边传，`T_first_audio` ≤1.5s；Opus 32kbps 稳定；屏显与音频不抢带宽 | 阶段 4 |
| **6** | **人格与音色调优** | `meta_break_rate` ≤5%；音色一致性盲评 ≥4/5（3 人 5 分制） | 阶段 5 |

**四条纪律**：

1. **不要跳过阶段 2 的自检。** 屏显、触摸、I2S 录音回放三项都要在实物上过一遍，再往下做——否则阶段 3 出问题分不清是云端、协议还是驱动。
2. **不要跳过阶段 3。** 先用最简单的 PTT 跑通端到端，确认云端接口、音频格式、播放链路都对，再上流式和 AEC。
3. **阶段 3 就要验证 ES7210 的 reference 通路**，不要等到阶段 4 才发现 AEC 没接对。
4. **不要在第 0 步之前买任何东西。** 板子已有，喇叭和电池可以等阶段 3 再定（那时才知道要不要电池）。
