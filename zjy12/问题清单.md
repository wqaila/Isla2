## 原始清单（存档，逐条细节见 `设计决策评审.md`）

## A 类 · 事实性错误（4 条）—— 照文档做会走错路

- [ ] **A1** · 7.1 表格 —— `Qwen-Audio-ASR` 被当成流式候选。阿里的流式实时产品线是 **Paraformer-realtime**，Qwen-Audio 长期是离线音频理解模型。
      → 拆成两行；7.2 实测项加「是否有**独立 finalize 接口**」。
- [ ] **A2** · 5.3 —— 「WiFi 抖动时丢最旧，不丢最新」对**上行语音**是错的。丢最旧 = 把「你好我想问一下」削成「问一下」，ASR 直接听错，恰好违反第七节自己的原则。
      → 改成：反压采集 → 持续 >500ms 上报网络劣化并提示 → **绝不静默丢弃已采集帧**。
- [ ] **A3** · 第二节 —— 「与权利方**或**配音演员签授权」，这个"或"是错的。著作权与**表演者权（邻接权）**是两个主体。
      → 改成「**和**」，两份缺一不可。
- [ ] **A4** · 9.4 分区表 —— `model, data, spiffs, 2M` 是 WakeNet 时代残留（模型全在云端，板子上没有任何模型文件）；且 `0xC20000` 以上还有 **3.875MB 未分配**；**没有 coredump 分区**。
      → `model` 改名 `assets` 或删掉并入 `storage`；补 `coredump, data, coredump, , 64K`。

## B 类 · 内部逻辑冲突（7 条）—— 同一份文档两处打架

- [ ] **B1** · 4.3 vs 4.4 —— 「说话」状态下按一下：4.3 说**打断**，4.4 说**挂断**。同一动作两个语义，而这状态是重叠的。
      → 定成**短按=打断 / 长按≥600ms=挂断**，写进 4.3，4.4 改为引用。
- [ ] **B2** · 5.1 vs 十一节阶段 1 —— 5.1 说「第一版用 HTTP 后面基本等于重做」，阶段 1 又写「PTT + HTTP」。
      → 阶段 1 改成 `PTT + WebSocket（一次发送整段，不分片）`；HTTP 只留给 PC 调试脚本，不进固件。
- [ ] **B3** · 6.5 vs 4.5/9.2-3 —— 6.5 说「不要为 120ms 牺牲稳定性」，但下行 16k PCM = **256kbps**，是 MP3 的 4 倍、Opus 的 10 倍，抖动下卡顿概率显著上升，正是 6.5 要避免的交换。
      → 加一张「延迟/码率/CPU/抖动敏感度」对比表并给依据；建议阶段 1–2 用 PCM，阶段 3 同步上 Opus 32kbps。
- [ ] **B4** · 8.4-3 vs 流式 TTS —— 「分段策略固定」与流式合成**本质冲突**（切点由 LLM 出字节奏决定，不可能固定）。
      → 选「流式合成 + 切点规则」：**网关负责只在句末标点/逗号处切分文本再送 TTS**，不依赖 TTS 自己切。
- [ ] **B5** · 4.5 —— 「**唤醒**后无语音 5s 提示」是术语残留（4.1 已取消唤醒词）。更实际：4.4 的「30 秒无有效输入」「连续 2 次识别为空」+ 4.5 的「5s/8s」，**三套计时器关系完全未定义**。
      → 画状态机图，把计时器画进去。文字描述状态机一定漏。
- [ ] **B6** · 4.3 —— 状态机缺「**思考中**」态（用户说完 → 首字出声之间的 0.8–1.5s）。此状态下按键无定义 → 用户连按 → 撞上 B1。
      → 加第四态，按一下 = 取消本轮回聆听；同时作为 6.4 思考音的挂载点。
- [ ] **B7** · 9.1 —— 硬件清单只有 主控/麦克风/功放/喇叭/电源，**没有按键、没有灯**。但 4.1「按键是唯一入口」、4.4「灯光熄灭」、9.3 SoftAP 配网（无屏幕只能靠灯）全靠它们。
      → 补：轻触按键（或 EC11 兼音量）、WS2812 8 灯环（兼配网状态）、电量检测。

## C 类 · 结构性空白（11 条）—— 现在不写，阶段 2–3 一定返工

- [ ] **C1** · 全局 —— **没有延迟预算表**。6.2 只有"能省多少"，没有"基线多少"。自底向上加总：乐观 980 / 中位 **2010** / 悲观 2860ms。
      → 换成加总表 + 定义 KPI（`T_first_audio` 与 `T_perceived` 两个都要）。
- [ ] **C2** · 4.5 / 5.3 / 7.3 —— **VAD 归属未定义**，三处提法互不相容（本地门控 / 云端 VAD / 语义端点），协议里"谁发 end-of-speech"永远定不下来。
      → 本地 VAD 只管"开始/静音省流"；**end-of-speech 一律由云端决定**；板子在本地静音时只停止发送，不发结束信号。
- [ ] **C3** · 8.3 —— **情绪参数与流式输出根本冲突**：JSON 无法边出边解析边播，等 JSON 闭合 = 放弃流式 = 放弃 1.2s。**建议提升为 A 类。**
      → 行首轻量标记（`[warm]`）+ few-shot，**标记解析放网关不放板子**；清洗规则限定为「只清洗行首或独立成段的括号」。
- [ ] **C4** · 全局 —— **完全没有 LLM 选型**，也没提仓库里已有的 zjy7 角色 LoRA（`qwen3.5:9b-gguf` + `elysia-lora`）。
      → 用 8.6 的 OOC 集做「云端 LLM vs LoRA」A/B；架构上保留"LLM 可切换"抽象。
- [ ] **C5** · 全局 —— **会话状态与记忆持久化没设计**：断电/重启/换房间后角色还记不记得？会话在网关内存、Redis 还是库？断线重连是恢复还是新开？
      → 会话 ID 由云端下发、板子存 NVS；断线 30s 内可恢复同一会话；记忆摘要落库（可复用 zjy9）。
- [ ] **C6** · 5.3 cancel 帧 —— **有竞态**：cancel 到达时 TTS 已合成后续段落并在回传途中，板子清空缓冲后这些**迟到帧会被当成新一轮回复播出**（用户听到上一轮残句）。
      → 所有下行音频帧带 `epoch`，板子只播当前 epoch。现在加成本≈0，后期加要改协议。
- [ ] **C7** · 全局 —— **没有失败模式与降级设计**：WiFi 断 / ASR 超时 / TTS 挂 / 网关 5xx / 流中断，用户看到什么全空白。
      → 加失败模式表（检测方式 / **用角色口吻说**的提示 / 重试策略 / 是否计入退出条件）。角色设备不能说"网络错误 500"。
- [ ] **C8** · 全局 —— **没有隐私合规设计**：语音是**敏感个人信息**（PIPL 第 28 条）需单独同意；云端是否留音频？厂商是否用于训练（需显式关）？另外「不按键不录音」这个卖点在会话模式下**不成立**——会话中麦克风常开，文档自己没意识到。
      → 加一节：麦克风状态可视化、音频不落盘、关闭厂商训练开关、单独同意流程。
- [ ] **C9** · 9.4 —— 留了双 OTA 分区（4M×2），但**全文没有 OTA 设计**：怎么触发、怎么签名校验、怎么回滚、怎么防砖。
      → 要么补一节 OTA，要么砍双分区换单 app + 更大 assets（省 4MB）。别留"看起来支持但没人实现"的结构。
- [ ] **C10** · 7.5 vs 7.7 —— **成本自相矛盾**：7.7 算出火山 1950 元/月 vs 阿里 300 元/月（差 6.5 倍），7.5 却推荐"先用火山跑通"。且只算了 TTS，**ASR 与 LLM 成本完全没算**——会话模式下"一直录"意味着待机也在花钱。
      → 补全链路成本表（原型 20 轮/天、试用 200 轮/天两档）；推荐改为「**ASR+LLM 用火山（准确率优先），TTS 用阿里 CosyVoice**（便宜 6 倍且支持声音设计）」。
- [ ] **C11** · 第二节 —— **厂商侧门槛没验证**：① 火山/阿里声音复刻上传音源**都要勾授权承诺**，未授权音源可能**在原型阶段就被审核拒绝**；② 深度合成备案主体是"服务提供者"，需企业主体+算法备案，**个人身份下"公开发布"实际不可能**。
      → 写成"硬性前置条件"；阶段 1–3 全程用 **CosyVoice 声音设计生成的原创占位音色**，把角色音色当可替换资产。

## D 类 · 需要细化（11 条）—— 不挡开工，但会踩坑

- [ ] **D1** · 6.2 —— 收益表无基线，且项间重叠（「ASR 并行 500ms」与「上传并行 200ms」重叠；「语义端点 450ms」与 4.5 的 600ms 是**互斥选项**不是可叠加项）。简单相加 1500ms 是虚高的。
      → 换成 C1 的加总表。
- [ ] **D2** · 7.3 双引擎 —— 成本翻倍；中间结果（A 模型）与终稿（B 模型）**文本可能不一致**，导致"端点判断基于的话"≠"喂给 LLM 的话"。
      → 用**同厂商同系列的高低精度模型**；把两者差异率作为质量指标监控。
- [ ] **D3** · 7.4 热词 —— 未提**数量上限**（通常 500–1000 词）与**生效延迟**（阿里需预建 `vocabulary_id`，更新后新会话才生效）。
      → 写清热词表规模上限、更新流程、是否需要重启会话。
- [ ] **D4** · 9.1 —— `INMP441 或 ES7210` 不能并列：前者是 **I2S 数字麦**（单麦，AEC reference 靠软件注入），后者是 **4 通道 ADC**（需外接 2–4 个**模拟** MEMS 麦 + codec）。两者电路完全不同。
      → 二选一并写清配套电路。按键方案推荐 **INMP441**（简单、便宜、够用）。
- [ ] **D5** · 9.2-7 —— 「Opus 吃 30–40% CPU」可能偏高（esp-opus 16k 单声道通常 10–20%）。
      → 实测后再定；若 <20%，阶段 2 就该上 Opus，直接解决 B3 的带宽矛盾。
- [ ] **D6** · 9.4 —— 同 A4（3.875MB 未分配、缺 coredump）。
- [ ] **D7** · 9.3-1 —— SoftAP 配网与 STA 同时工作会抢射频；若再用 BLE 配网，2.4G 共存会**加剧 6.3 说的抖动**。
      → 配网期间暂停音频任务；明确不用 BLE 共存。
- [ ] **D8** · 8.6 —— 20 条评测集偏少；"人工打分"不可持续。
      → 加到 40–50 条；加**自动判据**（黑名单词：`作为一个`/`AI`/`语言模型`/`助手`/`建议你`/`我可以帮你`），`meta_break` 触发率自动统计。
- [ ] **D9** · 6.4 —— 单一"嗯……"重复几十次会很明显。
      → 录 3–5 个变体随机播，按时长分档（短/中/长思考音）。
- [ ] **D10** · 十一节阶段 1 —— "不做 AEC"正确，但会让阶段 2 同时面对「协议改造 + AEC 调试」两个新变量。
      → 阶段 1 就把 **AEC reference 通道打通**（只验证参考信号正确，不做消除），阶段 2 只调参数。
- [ ] **D11** · 十二节 —— 顺序错了：埋点依赖可运行链路，链路依赖厂商和协议。
      → 见下「执行顺序」。

## 附 · 待拍板的 6 个问题

1. **KPI 用哪个**：`T_first_audio`（首字出声）还是 `T_perceived`（含思考音，约 0.3s）？建议两个都要。
2. **LLM 走云端还是 zjy7 LoRA**？若 LoRA 人设明显更稳，愿不愿接受"必须开着家里的机器"？
3. **音色**：坚持目标角色（等授权），还是先接受 CosyVoice 原创音色？
4. **按键语义**：短按打断/长按挂断，还是双击挂断？
5. **会话记忆**：断电后要不要"记得"上次？（决定要不要接 zjy9 记忆库）
6. **要不要 OTA**：要（双分区 +4MB + 签名回滚设计）还是不要（省 4MB，坏了只能拆机烧录）？
