## 二、前置验证（在 zjy14 环境重测，不沿用旧数据）

zjy13 的流式数据是 2026-10-26 测的，当时参考音频是官方示例、文本前端未启用、
`token_hop_len` 有污染。现在前提全变了，必须重测。

**实测（2026-11-16，每组 3 次采样取中位数）**：

| 文本 | 字数 | 非流式首包 | 流式首包 | 改善 | 块数 |
|---|---|---|---|---|---|
| 短句 | 10 | 1.60s | 1.67s | **−4.4%** | 2 |
| 中句 | 22 | 3.11s | 1.72s | **+44.8%** | 3 |
| 长句 | 44 | 5.36s | 1.48s | **+72.4%** | 4 |

**结论比 zjy13 当时更好**：长句改善从 41% 提升到 72.4%。
原因可能是参考音频编码已缓存、文本前端启用后韵律处理更高效。

### 为什么短句流式反而慢

上游 `cosyvoice/cli/model.py` 的流式逻辑是「攒够 `token_hop_len(25)`
+ `pre_lookahead_len(3)` = **28 个 token** 才出一包」。

28 token ≈ 1.12 秒音频。短句总音频才 2.36 秒，
等第一包出来时已接近生成完，流式失去意义。

**这就是必须做长短句路由的原因。**

### 分块大小实测

| 文本 | 块数 | 块大小（样本） | 换算 |
|---|---|---|---|
| 短句 | 2 | [27840, 19200] | 1.16s / 0.80s |
| 中句 | 3 | [27840, 48000, 52800] | 1.16s / 2.0s / 2.2s |
| 长句 | 4 | [27840, 48000, 96000, 76800] | 1.16s / 2.0s / 4.0s / 3.2s |

首块固定 27840 样本（1.16s），后续块逐渐变大（上游 `token_hop_len` 递增策略）。

### 拼接处爆音检测

检测相邻样本差值 > 0.6 的次数：

| 文本 | 最大跳变 | 超阈值样本 |
|---|---|---|
| 短句 | 0.383 | 0 |
| 中句 | 0.492 | 0 |
| 长句 | 0.524 | 0 |

**无爆音**，流式分块可以直接拼接播放。

## 三、实现内容

### 3.1 长短句路由（`inference/streaming.py`）

```python
STREAM_CHAR_THRESHOLD = 15   # 实测 10 字无收益、22 字有收益，取中间

class StreamPolicy:
    def should_stream(self, text) -> bool:
        return count_chars(text) >= self.threshold
```

**用有效字符数而非总长度**：标点不产生音频，不应影响路由判断。

### 3.2 真流式引擎（`synthesize_stream`）

```python
for seg in segments:              # 分句（若要求停顿控制）
    for upstream in model.inference_zero_shot(..., stream=True):
        yield AudioChunk(pcm=..., is_final=False)
    if seg.trailing_pause_ms > 0:
        yield AudioChunk(pcm=silence, ...)   # 段间静音
yield AudioChunk(pcm=b"", is_final=True)     # 结束标记
```

**流式与停顿控制的兼容处理**：流式本身不支持分句停顿（需要多次独立合成），
所以采用「分句 + 逐段流式 + 段间插静音」。段内仍是流式，段间显式停顿。

### 3.3 HTTP 流式接口（完全复用 zjy13 协议）

```
每块 = 4 字节大端 uint32 长度 + 该长度的裸 PCM S16LE 单声道数据
末尾发送长度 = 0 的块表示结束
```

**为什么不用 SSE / chunked JSON**：
- 音频是二进制，Base64 会增加 33% 体积
- 长度前缀无歧义，断流时能明确检测（缺结束标记）

**失败处理**：
- 首块前出错 → JSON 错误响应
- 中途出错 → **不发结束标记**，让调用方明确知道流不完整，而不是静默截断

**协议一致性有测试守护**：`test_protocol_matches_zjy13` 会读 zjy13 源码
检查 `struct.pack(">I", ...)` 模式是否一致。

### 3.4 并发调度（`inference/scheduler.py`）

| 能力 | 实现 |
|---|---|
| 并发限制 | `threading.BoundedSemaphore` |
| 有界队列 | 队列满返回 429 `QueueFullError` |
| 排队超时 | 超时返回 503 `RequestTimeoutError` |
| 取消 | 标记 + 检查点退出 |
| 统计 | served / rejected / timeout / 排队时长 / 执行时长 |

**异常安全**：`try/finally` 保证槽位一定释放。
有专门测试 `test_scheduler_releases_slot_on_exception` 验证——连续 3 次异常后
仍能正常执行，若泄漏则会卡死。

## 四、发现并修复的关键 bug

### 4.1 async 路由里调同步阻塞函数，卡死事件循环（严重）

**现象**：
```
单请求 6.40s，3 并发墙钟只有 8.03s
median_wait_ms = 0（完全没记录到排队）
```

如果并发真的被限制为 1，3 个请求应该耗时 19.2s 左右。

**根因**：

```python
@router.post("/synthesize")
async def synthesize(...):
    result = sched.run(...)   # ← 同步阻塞调用，在事件循环里跑
```

FastAPI 的 `async def` 路由在**事件循环线程**里执行。
`sched.run()` 会阻塞几秒，期间事件循环完全停转，
后续请求根本进不来——被 uvicorn 层串行化了。

**结果**：调度器形同虚设，它的排队逻辑从没被触发过。

**修复**：用 `run_in_threadpool` 把阻塞调用挪出事件循环：

```python
from starlette.concurrency import run_in_threadpool

result = await run_in_threadpool(_do_synth)
```

**修复后实测**：
```
单请求中位 1.96s
3 并发墙钟 6.13s（比值 3.12，接近串行）
各请求耗时 [4.11, 2.00, 6.12]   ← 阶梯状，说明真的在排队
排队请求数 2
排队中位 4098.5ms
```

### 4.2 流式请求绕过调度器

流式接口最初没走调度器，会和非流式请求抢显存。

**修复**：在生成器里直接操作信号量（不用 `run()`，因为 `run()` 要求函数
返回后才释放，而流式需在整个传输期间持有）。用 `try/finally` 保证释放。

### 4.3 排队统计指标被零值拉平

`median_wait_ms` 统计全部历史请求，大量零等待请求把中位数拉成 0，
指标失去意义。

**修复**：增加 `waited_count` / `median_wait_queued_ms` / `max_wait_ms`，
只统计等待 > 10ms 的请求。

## 五、配置项

新增 5 个配置（全部已登记消费方）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `max_queue_size` | 8 | 等待队列上限，超出返回 429 |
| `queue_timeout_s` | 60 | 排队超时，超时返回 503 |
| `stream_enabled` | true | 流式开关 |
| `stream_char_threshold` | 15 | 路由阈值（有效字符数） |

`max_concurrent_requests` 保留默认 1。

**为什么默认单并发**：TTS 峰值显存 3.45GB，12GB 理论上够 2-3 并发，
但 CUDA 上下文和中间张量会叠加。放开前需实测显存峰值。

## 十、经验教训

1. **async 路由里不能直接调同步阻塞函数**。这会卡死事件循环，
   让所有并发控制形同虚设。必须用 `run_in_threadpool`。
   这个 bug 很隐蔽——功能正常、请求成功，只是并发限制完全没生效。

2. **前置验证不能省**。zjy13 的数据是 3 周前、不同配置下测的。
   重测后发现改善幅度从 41% 提升到 72.4%，如果直接沿用旧数据会低估收益。

3. **指标要区分「全部」与「有意义的子集」**。`median_wait_ms` 被零值
   拉平后完全无用，加 `waited_count` 才看得出拥塞。

4. **协议一致性要用测试守护**。`test_protocol_matches_zjy13` 会读
   zjy13 源码验证 `struct.pack` 模式，防止两边协议漂移。
