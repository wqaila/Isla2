## 逐条展开

### D1：已实测 —— 情绪指令无效，走路线乙

**2026-11-16 更新：D1 已完成验证，结论是路线乙。**

实测方法（三条独立路径 + 安慰剂对照）：

| 验证路径 | 真指令差异 | 安慰剂效应 | 判定 |
|---|---|---|---|
| 混合模式（W2 组合 prompt） | 10.1 Hz | **15.4 Hz** | ❌ 未超过安慰剂 |
| 官方 `instruct2`（空 spk） | 24.3 Hz | **72.5 Hz** | ❌ 未超过安慰剂 |
| 方向性检查 | 开心 −5.3 / 伤心 −15.4 | 同向 | ❌ 不符合直觉 |

**决定性证据**：加入「请用**蓝色**的语气说一句话」这种无意义指令，
产生的 F0 变化比真正的情绪指令还大。说明模型只是对"prompt 变长"有反应，
并没有理解情绪。

完整数据见 [13_D1_EMOTION_VERDICT.md](13_D1_EMOTION_VERDICT.md)。

**路线乙（已采用）**

1. **保留确定生效的控制维度**：
   - `speed` 语速（已验证 0.9/1.0/1.1 有明确时长差异）
   - 音量（音频层增益实现，不依赖模型）
   - 停顿（文本标点/分句控制）

2. **情绪交由 LLM 侧用词表达**：
   - zjy13 角色卡已有 `emotional_expression` 字段
   - 让 LLM 在文本层面体现情绪（"嘿嘿~" vs "唔…"），TTS 只负责忠实朗读
   - 符合原提示词"不让情绪标签导致声音身份漂移"的要求

3. **文档如实标注**：模型不支持独立情绪控制

**受影响的既有设计**

| 位置 | 原设计 | 改为 |
|---|---|---|
| D4 情绪标签集 | 3 官方 + 2 实验，映射到指令 | 保留为元数据，不映射 |
| `SynthesisRequest.emotion` | 接受但未生效 | 明确标注"仅记录，不影响合成" |
| Phase 2b 计划 | 情绪映射 + 平滑状态机 | 语速/停顿控制 + LLM 侧情绪 |

**技术副产品（重要）**

验证过程中修正了 Phase 0 混合调用方案的缺陷：

| 方案 | 时长 | 语速 |
|---|---|---|
| 正常 zero_shot | 5.76s | 6.17 字/秒 |
| prompt=参考 + **保留** llm token | 6.16s | 6.11 字/秒 ✅ |
| prompt=参考 + **删除** llm token | 14.72s | 2.25 字/秒 ❌ |

Phase 0 为绕开卷积报错而删掉 `llm_prompt_speech_token`，代价是**慢 2.5 倍**。
正确做法是把 prompt 构造成「指令 + `<|endofprompt|>` + 参考正文」并保留该 token。

### D2：引擎升级（方案 A）

```text
现状（zjy13）：
  ESP32 固件 → zjy13/server/ws/server.py → zjy13/server/tts/client.py
                                        → WSL HTTP :50000 → tts_server_wsl.py → CosyVoice3

升级后：
  ESP32 固件 → zjy13/server/ws/server.py → zjy14 引擎服务
                                        → WSL HTTP :50001 → custom_voice/inference/engine.py
                                                          → CosyVoice3（混合调用）
```

**具体动作**：
- zjy13 侧只改一处：`TTSConfig.base_url` 从 `:50000` 改到 `:50001`
- zjy14 的 HTTP 接口**保持 `/synthesize` 与 `/health` 的请求/响应契约**，zjy13 的 `TTSClient` 无需改动
- 新增字段（emotion / style / instruction）通过可选参数扩展，旧调用不受影响
- 固件、协议、角色卡：**一行不改**

**回滚**：把 `base_url` 改回 `:50000` 即恢复原状。

### D4：情绪标签（受 D1 结论影响，已调整语义）

**2026-11-16 调整**：D1 实测证明情绪指令无效，因此标签不再映射到模型指令。

| 标签 | 语义 | 实现方式 |
|---|---|---|
| neutral | 中性 | LLM 用平实措辞 |
| happy | 开心 | LLM 用「嘿嘿~」「耶~」等 |
| sad | 难过 | LLM 用「唔…」「呜呜…」等 |
| angry | 生气 | LLM 用短促、直接的措辞 |
| comforting | 安慰 | LLM 用温柔、放慢的措辞 |
| playful | 俏皮 | LLM 用俏皮语气词 |

**关键变化**：
- 标签保留为**元数据**，供 LLM 侧和前端 UI 使用
- **不传给 TTS 模型**（传了也无效，已验证）
- TTS 只接收：文本 + 语速 + 音量 + 停顿配置

自造标签（comforting/playful）不再标"实验性"，因为它们本来就不走模型指令，
而是作为 LLM 提示词的一部分。

### D5：先非流式

| 阶段 | 流式状态 |
|---|---|
| Phase 2–3 | 全部非流式 |
| Phase 4 | 实现流式 + 长短句路由（阈值待实测，参考 zjy13 的 18 字分界） |

`engine.py` 接口从一开始就返回 chunk 生成器，但 Phase 2–3 内部一次性 yield 完整音频，Phase 4 再换成真流式。**接口不变，实现替换**，避免后期改调用方。

### D6：单机

ASR / LLM / TTS 全在 RTX 5070 这台机器（WSL2 + Windows 双环境）。
- 无跨机协议设计
- Service 层不假设进程内调用，保留 HTTP 边界，便于将来拆分
- 显存预算按单机共存算：TTS 3.45GB + ASR 2GB = 5.45GB，余量 4.4GB

### D7：范围收敛

**做**：TTS 引擎、情绪控制、角色/声音管理、管理 API、Web 界面、性能优化
**不做**：ASR 重写、LLM 重写、固件重写、协议重设计

Phase 5 从"ESP32 联调"缩为"桥接验证"：
- 只做 `ws_bridge.py`（zjy14 引擎 ↔ zjy13 protocol v1）
- 24kHz PCM S16LE 单声道输出，固件已固定此格式
- 不重新烧录固件

### D8：完整 8 页

仪表盘 / 角色管理 / 声音管理 / 情绪管理 / 合成测试 / 设备管理 / 系统设置 / 日志中心。

情绪管理页是 D1 的关键可视化：并排试听 6 种情绪，直接支撑盲听决策。

### D9：单角色做深

- 角色 CRUD 功能照做（为将来准备）
- 当前只装 elysia 一个实例
- 重点验证：跨文本、跨情绪、跨会话的音色一致性
- 不做多角色串音色测试（原文档要求 3 个角色，**因素材不足降级，需在验收报告注明**）

### D10：默认 localhost + token

- 默认 `127.0.0.1:50001`
- 开启局域网需显式改配置，且**必须**设置 `auth_token`
- 未设 token 时拒绝监听 `0.0.0.0`（启动时报错，不静默放行）
- ESP32 联调：走 Windows 侧 `ws/server.py` 转发，不直连 zjy14
