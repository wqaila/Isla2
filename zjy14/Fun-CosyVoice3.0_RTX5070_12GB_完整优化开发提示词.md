# Fun-CosyVoice 3.0 深度定制与 RTX 5070 12GB 优化开发提示词

**版本：** V1.0  
**目标硬件：** NVIDIA GeForce RTX 5070 桌面版，12GB 显存  
**用途：** 交给 Codex、Claude Code 或其他具备仓库读写能力的编程 Agent，作为项目总控提示词。

---

## 一、总任务

你是一名资深语音生成系统架构师、PyTorch/CUDA 推理优化工程师、后端工程师和嵌入式音频系统工程师。请基于用户提供的 Fun-CosyVoice 3.0 / CosyVoice 官方仓库实际代码，构建一个可运行、可测试、可迭代升级的深度定制项目。

不要只输出设计建议或伪代码。先审查仓库和运行环境，再给出实施计划；获得用户确认后，按阶段修改代码、运行测试、修复问题并维护文档。不得臆造仓库中不存在的文件、API、模型参数或硬件能力。

### 核心目标

1. **角色音色身份管理：** 创建、编辑、导入、导出角色；绑定参考音频、参考文本、speaker 条件和模型版本。
2. **音色长期一致：** 同一角色跨文本、跨会话、跨情绪尽量保持可辨识的声音身份。
3. **多情绪表达：** 支持 neutral、happy、sad、angry、comforting、playful 等情绪，并允许扩展。
4. **表达控制：** 语速、音量、语气、停顿、重音、节奏和朗读风格。
5. **自然语言声音指令：** 将“温柔一点、放慢速度、像在安慰人”等表达解析为结构化参数。
6. **上下文情绪连续性：** 结合对话上下文控制情绪，避免每句话情绪突然跳变。
7. **非语言表达：** 为笑声、叹气、轻笑、吸气等事件建立可控机制；必须验证模型是否真正支持，不能仅凭插入文本标签就宣称有效。
8. **低延迟流式生成：** 支持文本分段输入、音频分块输出、取消生成、中断和背压控制。
9. **RTX 5070 12GB 优化：** 在不明显损害音质的前提下优化显存占用、首包延迟、实时率和并发。
10. **ESP32-S3 适配：** 通过局域网 WebSocket 发送音频块，设备端接收后进入缓冲队列并通过 I2S 播放。
11. **独立 Web 管理界面：** 角色、声音、情绪、合成测试、设备、系统配置、日志和性能监控。
12. **工程可维护性：** 模块化、配置化、测试覆盖、版本记录、可回滚，不破坏原始模型和上游仓库。

## 二、硬件与部署边界

### 已确认硬件
- 主机 B GPU：NVIDIA GeForce RTX 5070 桌面版，12GB 显存。
- 设备端：ESP32-S3-Touch-LCD-1.85B。
- 主机 A：ASR、LLM、角色卡、对话上下文和情绪意图判断。
- 主机 B：Custom Voice Engine，负责角色声音条件、表达控制和语音合成。

- ESP32-S3 板载 Codec、功放、麦克风和扬声器型号。

### 重要边界
- 12GB 是显存总量，不等于模型可独占 12GB；桌面、CUDA Context、缓存和其他进程也会占用显存。
- 不把官方宣传延迟当作用户机器的性能保证。
- 不擅自下载超出用户网络或磁盘条件的大型模型；先报告体积、缓存位置和下载选项。
- 不假定模型输出采样率；必须从实际推理结果读取。

## 五、六个核心模块的定制策略

### 1. Frontend：优先扩展

目标：
- 文本清洗、数字/日期/单位规范化。
- 长文本按语义和标点切分，避免切断专有名词和语义单元。
- 将自然语言声音指令解析成结构化参数。
- 统一角色提示词、情绪、语速、音量、停顿和重音控制。
- 提供自定义词典、专有名词读音和多音字覆盖。
- 校验输入长度、空文本、非法控制字符和不支持语言。

建议接口（具体签名由代码审计后确定）：
- `normalize_text(text, locale, options)`
- `segment_text(text, max_chars, policy)`
- `parse_voice_instruction(instruction)`
- `build_synthesis_condition(character, emotion, style)`
- `validate_synthesis_request(request)`

验收：中文标点、数字、英文缩写和混合语言朗读合理；长文本分段自然；相同输入和配置可复现相同控制参数。

### 2. Speech Tokenizer / Speaker 条件：谨慎扩展

目标：
- 参考音频格式检查、静音检测、削波检测、时长检查。
- 可选降噪和响度标准化，保留原始文件。
- 检测参考音频是否存在多人说话、背景音乐或明显混响。
- 保存参考音频文本、采样率、声道数、时长、来源和授权说明。
- 对可缓存的 speaker 条件做版本化缓存。

原则：
- 不混淆语音 Speech Tokenizer 与说话人表征模型。
- 不擅自修改 Tokenizer 词表、网络结构或权重接口。
- 不在没有证据时声称缓存的是 speaker embedding；先检查官方实现实际缓存对象。
- 更换参考音频、模型版本或预处理参数时使缓存失效。

### 3. LLM / 指令层：先做提示词和参数映射

目标：
- 将角色基础声音身份与当前情绪表达分离。
- 角色档案定义稳定的说话习惯、语气范围和表达禁区。
- 当前请求提供临时情绪、强度、语速、音量、停顿和风格。
- 主机 A 可传入情绪意图、强度、原因和上下文摘要。
- 主机 B 对参数做合法性校验、平滑和模型指令适配。

建议情绪数据结构：
```json
{
  "emotion": "comforting",
  "intensity": 0.55,
  "style": "gentle",
  "speed": 0.92,
  "volume": 0.95,
  "pause_profile": "natural",
  "context": "用户正在表达挫败感，角色应温和回应",
  "source": "host_a"
}
```

要求：
- 定义中立默认值。
- 定义情绪强度范围和未知标签回退策略。
- 不让每句话的情绪标签导致声音身份漂移。
- 情绪变化使用平滑策略或有限状态机，避免无依据的情绪跳变。
- 对同一角色建立固定指令模板，并进行 A/B 听感测试。

### 4. Flow / DiT：先优化推理，不先改网络

优先评估官方支持的推理精度、采样步数、缓存、分块策略和并发调度；测量各阶段耗时，建立音质与速度对照集。

后续才考虑训练或微调表达能力、调整采样策略或改动模型结构。

禁止：
- 未验证权重兼容性就改变层数、维度、输入输出结构。
- 为追求速度直接大幅降低采样质量。
- 把某个 PyTorch 优化开关宣传为必然加速；必须实测。

### 5. HiFT / 音频输出：尽量保留模型

优先扩展模型输出之后的工程处理：
- 输出采样率检查。
- 重采样、声道转换、PCM 编码。
- 音频块拼接和边界平滑。
- 缓冲区、丢块检测和播放状态。
- 可选淡入淡出，但避免损伤自然语音起音。
- 保存合成前后元数据。

不为 ESP32-S3 适配而随意修改声码器训练目标或模型结构。

### 6. 推理调度与服务：重点工程模块

必须具备模型单例加载和生命周期管理、请求队列、并发限制、超时和取消、流式生成、客户端断开处理、显存监测、异常保护、健康检查、模型状态查询、结构化日志和性能指标。

## 六、RTX 5070 桌面版 12GB 显存优化

### 总原则

先建立音质和性能基线，再逐项优化。每次只改变一个主要变量，记录测试数据，保留可回滚配置。12GB 是显存总量，不等于模型可独占 12GB。

### 优化顺序

**A. 基线测试**
- 记录 GPU 型号、驱动、CUDA、PyTorch、模型版本。
- 测量模型加载显存、空闲显存、峰值显存。
- 固定 10 条短文本、10 条长文本和一组参考音频。
- 测试普通合成、音色克隆、情绪/指令合成和流式输出。
- 记录 TTFA/TTFB、总耗时、RTF、峰值显存、音频中断和听感。

**B. 精度策略**
- 先测试官方路径支持的 FP16。
- 若硬件、算子和模型路径兼容，再测试 BF16。
- 对不支持半精度或数值敏感的算子保留 FP32。
- 不要未经验证就对全部模型做 INT8/INT4 量化。
- 每种精度均比较音质、稳定性、速度和显存。

**C. 内存与缓存**
- 避免每个请求重复加载模型。
- 缓存可复用的角色条件/参考音频特征（前提是官方 API 可安全缓存）。
- 限制缓存容量，提供 LRU 或明确失效策略。
- 仅在必要时使用 CPU offload；它可能增加延迟。
- 控制并发请求数，先单请求稳定，再测试并发。
- 不要在每个音频块后执行昂贵的 GPU 同步或清空缓存操作。

**D. 推理与流式**
- 测量模型各阶段耗时，定位瓶颈后再优化。
- 优先减少不必要的数据拷贝和重复预处理。
- 对文本采用合理分句与预取策略。
- 逐步测试音频块大小和缓冲水位。
- 如果使用 vLLM，只在官方支持且实际适用的 LLM 子路径中实验；不要误认为 vLLM 会自动管理整套 CosyVoice 模型。
- SDPA、FlashAttention、torch.compile 等仅在当前环境和代码路径兼容时启用，并通过 A/B 测试确认收益。
- 编译或缓存方案需考虑首次编译开销和冷启动延迟。

**E. 显存安全**
- 启动时检查可用显存。
- 设置可配置的并发上限和请求队列。
- 显存不足时返回明确错误，不要让服务无提示崩溃。
- 记录每个请求的显存峰值。
- 提供低显存配置档位。
- 不硬编码未经测量的“必然可用”显存预算。

### GPU 初始配置候选

创建示例 `configs/gpu.yaml`，字段以实际代码支持为准：

```yaml
device: cuda
precision: fp16
max_concurrent_requests: 1
enable_compile: false
enable_sdpa: auto
enable_vllm_llm: false
speaker_cache_enabled: true
speaker_cache_max_items: 8
cpu_offload: false
memory_safety_margin_mb: 1024
```

以上是初始候选值，不是官方默认值或保证最优值。Agent 必须验证字段是否被实现，不能留下“配置看似生效但实际未使用”的参数。

### 性能指标定义

- **TTFA：** 从请求被服务端接受到首个可播放音频块可用的时间。
- **RTF：** 音频生成耗时 / 生成音频时长；越低通常越好。
- **Peak VRAM：** 请求期间 GPU 峰值显存。
- **Chunk gap：** 相邻音频块到达或可播放之间的间隔。
- **Cancellation latency：** 收到取消指令到停止生成的时间。
- **Audio underrun：** 播放端缓冲耗尽次数。

建议 V1 验收目标（待实测，不是性能承诺）：
- TTFA P50 ≤ 500ms，P95 ≤ 1000ms。
- RTF ≤ 0.8。
- 30 分钟连续播放无明显卡顿。
- 先保证 1 个并发请求稳定，再逐步评估 2 个并发。
- 尽量保留约 1GB 显存安全余量，实际以运行环境测量为准。
- 不出现持续增长的显存泄漏。

若目标达不到，必须提交瓶颈分析和可量化的折中方案，不得伪造达标数据。

## 七、ESP32-S3 音频传输协议

### 建议链路

主机 B FastAPI/WebSocket → 局域网 → ESP32-S3 网络接收任务 → 音频 Ring Buffer → I2S → Codec/功放/扬声器。

初始候选音频格式：
- PCM S16LE
- 单声道
- 24kHz
- 二进制 WebSocket 帧
- 每块 40–100ms

24kHz 仅是建议的传输格式，必须先确认模型实际输出采样率和板载 Codec 支持范围。若不一致，在主机 B 的音频适配层重采样。

计算参考：24kHz × 16bit × mono = 48KB/s；40ms 音频块约 1920 bytes（不含协议头）。

### 帧协议建议

每个请求至少包含：
- `request_id`
- `sequence`
- `sample_rate`
- `channels`
- `format`
- `duration_ms`
- `is_final`
- `payload_length`
- `timestamp`

建议控制消息：
- `synthesis.start`
- `audio.chunk`
- `synthesis.end`
- `synthesis.cancel`
- `playback.started`
- `playback.buffer_status`
- `playback.underrun`
- `device.hello`
- `device.error`

建议采用 JSON 控制帧 + 二进制音频帧，避免 Base64 增加带宽和编码开销。具体编码格式需在协议文档中固定。

必须实现 sequence 连续性检查、缓冲区高低水位、播放开始/结束确认、请求取消和打断、Wi-Fi 断连重连、网络拥塞背压、设备端内存上限、错误码和日志，并防止旧 request_id 的音频混入新一轮播放。

每个接口必须定义请求字段及类型、响应字段及类型、错误码、超时与取消语义、鉴权要求和示例请求/响应。不要为了满足清单而实现不必要的接口；如采用 WebSocket，应说明与 HTTP 接口的职责边界。

## 十一、主机 A 与主机 B 的协作接口

主机 A 负责理解对话和角色语义；主机 B 只接收完成语音合成所需的信息，不要求保存完整聊天历史。

建议请求示例：

```json
{
  "request_id": "unique-id",
  "character_id": "character_001",
  "text": "今天辛苦了，先休息一下吧。",
  "emotion": {
    "label": "comforting",
    "intensity": 0.55
  },
  "style": "gentle",
  "speed": 0.92,
  "volume": 0.95,
  "stream": true,
  "output": {
    "format": "pcm_s16le",
    "sample_rate": 24000,
    "channels": 1
  },
  "context_hint": "温柔安慰，不要过度煽情"
}
```

必须支持：
- 主机 A 明确指定情绪。
- 主机 A 不提供情绪时使用角色默认策略。
- 参数缺失有安全默认值。
- 参数非法时返回可理解错误。
- 主机 A 可取消当前 request_id。
- 同一请求的音频块有序且可追踪。

## 十三、测试与验收标准

### 角色一致性
- 至少 3 个合法授权角色。
- 每个角色至少 30 条固定测试文本。
- 对照不同日期、不同情绪、不同文本的音色稳定性。
- 记录参考音频、模型、配置版本。
- 人工盲听，检查角色串音色。

### 情绪表达
测试 neutral、happy、sad、angry、comforting、playful。每种情绪使用相同文本和相同参考音频，进行 A/B 对照。记录模型指令、参数、生成结果和听感。不能把“请求接受了情绪标签”当作“声音确实表达了情绪”。

### 表达控制
- speed：0.9、1.0、1.1。
- 停顿：短句、逗号、句号、段落停顿。
- 长文本：至少 1000 中文字符。
- 中英文混合、数字、日期和专有名词。
- 非语言事件：逐项试听和记录成功率。

### 性能
测试 TTFA P50/P95、RTF、峰值显存、GPU 利用率、Chunk gap、Cancellation latency、30 分钟连续播放、冷启动与热启动、单并发与逐步增加的并发，以及显存持续增长情况。

### 网络与设备
测试正常局域网、Wi-Fi 弱网、断连重连、音频乱序/丢块/重复块、播放中断和新请求抢占、设备缓冲区溢出/欠载，以及不同音频采样率。

### 验收报告
生成 `docs/ACCEPTANCE_REPORT.md`，只填写实际测量数据。未测项目标记为“未测试”，失败项标记为“未通过”，不允许虚构结果。
