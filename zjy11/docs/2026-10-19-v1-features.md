# 第一版功能说明（文字版）

日期：2026-10-19  
状态：范围已确认——先做文字版跑通，再接语音  
对应项目：zjy11（ESP32-S3 云端角色对话原型）

## 1. 一句话定义

第一版做一个**能联网聊天的桌面文字终端**：用户在串口或触摸屏幕输入文字，ESP32-S3 发送到电脑上的轻量网关，网关加入朋友型爱莉希雅的人设与最近几轮对话后请求云端文本模型，回答显示在 360 × 360 屏幕上。

语音（录音、识别、合成、播放）全部推迟到 V2，不在本版范围内。

这个决定的原因是：文字链路能先验证三件更难排查的事——板端稳定联网、屏幕中文排版、角色回答质量。音频会引入麦克风驱动、编码格式、回声、多服务商超时等变量，同时上马会让故障定位变难。

## 2. 用户可见的功能

### 2.1 开机与联网

| 功能 | 具体行为 | 验收标准 |
|---|---|---|
| 开机自检 | 上电后显示角色名与初始化状态 | 3 秒内出现可读界面，不黑屏、不反复重启 |
| Wi-Fi 连接 | 连接预先配置的 2.4 GHz 网络 | 连上后状态显示「已连接」；失败显示可读原因 |
| 网关探测 | 连上 Wi-Fi 后请求一次 `/health` | 网关就绪显示「在线」，未配置显示「网关未配置」 |
| 离线提示 | 断网或网关不可达 | 明确显示网络或网关问题，不假装在思考 |

### 2.2 一次对话

| 步骤 | 行为 | 验收标准 |
|---|---|---|
| 输入 | 串口输入一行文字，按回车发送 | 长度上限明确，超长有提示，不静默截断 |
| 请求 | 板子带设备令牌请求网关 `/v1/chat` | 不携带模型 API Key；同一轮只发一次 |
| 生成 | 网关加入角色设定与最近 4 轮对话 | 回答与当前话题相关，保持朋友型人格 |
| 显示 | 屏幕显示角色回答 | 360 × 360 内可读，长回答可滚动，不裁切半句 |
| 历史 | 成功一轮后保存 `session_id` 并进入短期上下文 | 下一轮能接上刚才的话题 |
| 失败 | 断网、超时、鉴权失败、网关未配置 | 分别给出可读提示，不伪造回答 |

第一版的输入通道是**串口**，屏幕只负责输出。小屏幕上做中文输入法成本高、体验差，且不属于本次要验证的内容。

### 2.3 屏幕显示

同一时间只显示一个主状态：

- **待机**：角色名 +「等待输入」提示。
- **已发送**：显示用户刚发送的文字，进入等待。
- **回答中**：分段显示云端返回的完整回答。
- **错误**：可读原因与「重试 / 返回」操作。
- **设置**：Wi-Fi 名称与状态、网关地址与状态、角色版本。

屏幕是输出设备，不承担输入。每次切换状态要能一眼看出设备当前在做什么。

### 2.4 显示细节

- 中文必须正确显示，缺字要有回退，不能只让英文状态正常。
- 回答超过一屏时可手动滚动，滚动后能回到开头重新阅读。
- 不显示 Markdown 标题、列表符号、代码块等标记。
- 长回答按语义分段换行，不在半个汉字或半个词中间硬切。

## 3. 角色行为的硬要求

第一版就按已确认的朋友型定位验收，不放到后续再调。

| 要求 | 说明 |
|---|---|
| 人格稳定 | 温柔、自信、俏皮、有自己的意见，不是通用客服 |
| 现实话题 | 能聊工作、学习、生活，不强行转回原作剧情 |
| 朋友边界 | 不自动暧昧、不吃醋、不索取独占、不制造内疚 |
| 尊重偏好 | 用户要求换称呼、少表情、直接给建议时立即遵从 |
| 不编造 | 不虚构共同经历，不假装实际到场或操作了设备 |
| 身份诚实 | 被直接询问时说明是 AI 角色伙伴 |
| 安全性 | 高风险话题优先安全与现实支持 |
| 语言形态 | 短句、少 emoji、不出 Markdown 符号，便于小屏阅读 |

回答长度目标为普通问题约 30 至 80 个汉字，复杂问题可适度展开；不要为了凑长度把半句话截断。

## 4. 系统组成与分工

```text
ESP32-S3 板端
  串口输入 / 屏幕显示 / Wi-Fi
        ↓ 文字请求，取回文字回答
电脑轻量网关（本项目 gateway/，已实现）
  设备鉴权 / 角色设定 / 短期会话 / 请求云端
        ↓ HTTPS
云端文本模型
  生成角色回答
```

分工原则：

- **板端**只负责输入、显示和联网，不保存模型密钥，不写死人格。
- **网关**是唯一可信边界，负责角色版本、设备令牌和调用控制。
- **云端**只做文本生成，不认识具体设备。

第一版复用已经运行并测试通过的网关，不修改其角色与安全设计，除非实测发现明确缺陷。

## 5. 网关现有能力与第一版所需

现有网关已具备：文字对话、设备令牌鉴权、最近 4 轮短期历史、请求去重、限流、超时与错误处理、用量回传。第一版不新增音频接口。

需要补的只有便于固件联调的部分：

| 能力 | 说明 |
|---|---|
| 状态可探测 | 板端可通过 `/health` 判断是否已配置 |
| 错误码稳定 | 固件按 `code` 映射到用户可读提示，不解析中文文案 |
| 响应大小可控 | 回答长度受 `LLM_MAX_TOKENS` 限制，避免超出板端缓冲 |

接口细节以 [RUNNING.md](../RUNNING.md) 为准。

## 6. 明确不做的事情

第一版不包含，避免范围膨胀：

- 录音、语音识别、语音合成、音频播放。
- 唤醒词与全程监听。
- 长期记忆、用户画像、知识图谱、RAG 检索。
- 多角色切换、角色市场、亲密度数值、关系升级。
- 音色克隆、原版配音演员音色复刻。
- 联网搜索、天气、智能家居等工具能力。
- 公网部署、多用户账户、付费订阅。
- 手机 App 与树莓派联调。
- 板端本地大模型或离线推理。

## 7. 第一版验收场景

跑完这些场景才算完成，建议逐条记录结果。

| 编号 | 场景 | 期望 |
|---|---|---|
| 1 | 上电并连上 Wi-Fi | 3 秒内出现界面，显示已连接 |
| 2 | 网关未配置时发送 | 提示网关未配置，不显示假回答 |
| 3 | 问候「你好」 | 得到角色风格回应并显示 |
| 4 | 倾诉「今天很累」 | 先理解处境，不机械安慰 |
| 5 | 要求换称呼后再聊 | 使用新称呼 |
| 6 | 直接问是否是真人 | 如实说明是 AI 角色伙伴 |
| 7 | 连续 10 轮对话 | 无重启、无卡死、上下文连续 |
| 8 | 超长输入 | 明确提示，不静默截断成半句发送 |
| 9 | 断网后发送 | 明确提示，恢复后可继续使用 |
| 10 | 长回答显示 | 可滚动，不裁切半句 |
| 11 | 重复提交同一轮 | 网关去重，不重复计费 |
| 12 | 网关返回错误码 | 屏幕显示对应提示，不当作角色台词 |

其中 3 至 6 需要人工判断角色效果，不能只看是否返回 200。

## 8. 开发顺序

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| 1 | 板端点屏、触摸与 Wi-Fi | 官方示例可跑，稳定不重启 |
| 2 | 串口文字接入现有网关 | 板子能拿到真实文字回答 |
| 3 | 屏幕显示与状态机 | 中文可读，长文可滚动，状态清晰 |
| 4 | 错误处理与回归 | 12 个验收场景通过 |

第 2 阶段直接用现有网关，先证明网络与协议正确，再叠加显示，避免多种问题同时排查。

## 9. 前置条件

开工前需要确认：

1. 实物完整型号与 PCB 修订（B 型与 C 型引脚和音频芯片不同）。
2. 云端服务商与具体模型，以及对应账号与测试预算。
3. 是否接受电脑必须开机运行网关。

## 10. V2 语音版预留

文字版稳定后再做语音，届时新增：

- 按住屏幕录音，最长 10 秒，可取消。
- 网关调用语音识别，识别不到文本就不生成。
- 回答先显示文字，再播放普通女声合成语音。
- 重播上一条不重新请求模型。
- 半双工，不做唤醒词和边说边听。

V2 需要额外的 ASR 与 TTS 账号和预算，不在第一版内隐含承诺。

## 11. 风险与边界

- 语音推迟后，第一版的价值取决于角色回答质量，需要用验收场景 3 至 6 人工判断，不能只用接口成功衡量。
- 局域网 HTTP 无传输加密，仅限可信网络；公网使用必须先补 HTTPS。
- 板端串口输入需要终端配合，属于开发调试形态，不是最终产品交互。
- 屏幕中文显示依赖字体资源，需提前确认字库覆盖常见汉字。
