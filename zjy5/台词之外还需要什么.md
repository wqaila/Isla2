# 台词之外，训练一个角色模型还需要什么

> **这份文档为什么放在 zjy5**
>
> zjy5 是采集端。下面列的缺口里，有相当一部分**只能在采集端修**——
> 长度红线、说话人纯度、重复频次、句级溯源，一旦台词变成纯文本落盘就补不回来了。
> 采集端决定了上游数据形态，所以它得知道下游（zjy7）到底要什么。
>
> 数据基线：**2026-09-28 首版实测量化**，**2026-09-30 复核更新**
> （`zjy7/train_data.json`，1736 → 2249 → 5744 → **7027** 条）。
> 所有数字都来自实际跑脚本统计，不是估计。
>
> **最后更新：2026-09-30** —— **建议顺序的第 1、2、3、5 项已完成**：
> 人设统一、长度红线、问法多样化、通用数据 + 负样本。
> 其中**第 3 项「问法多样化」对模型效果影响最大**（唯一提问 416 → 5451，
> Top10 占比 55.8% → 1.5%），实现细节与踩坑见第七节。
> 另修正了首版对提问坍缩的低估与一处交叉引用错误。
>
> **待做**：第 4 项「多轮上下文样本」（训练/推理形态不匹配，长对话人设崩的主因）、
> 第 6 项「语气打标提纯度」、第 7 项「OCR 术语校正」、第 8 项「下次采集开 jsonl」，
> 以及「回答长度下限」的判断（见第 7 节）。
>
> **2026-10-08 补充**：实测 17 个语料文件后，**发现采集端要动的不是 1 处而是 5 处**，
> 并纠正了两个此前的误判 —— ① **jsonl 逐句溯源是现成的**（`build_record` 里
> 连 `speaker_score` 都有），只是当时用 `txt` 格式跑的；② **跨视频的「重复」
> 是刻意保留的口头禅信号**，不是 bug。详见**第 9、10 节**。
>
> 🔴 **同日挖出一个更严重的问题（务必先看）**：**`max_seq_length` 太小，
> 导致大量样本「学不到东西」** —— system 人设占 **999 token**，而预算只有 1024，
> 留给对话只剩 25。实测单轮 **18%**、多轮 **100%** 的样本标签被整条掩码，
> 且**完全静默**。已修（1024 → 2048，无效样本降到 0）并加了防呆。
> 详见**第 6 节末**。

## 一句话结论

台词只解决「**她说什么**」。要训出一个像样的角色，还得有：

| 还缺的东西 | 解决的问题 |
|------------|-----------|
| **人设（System Prompt）** | 她是谁 |
| **user 侧的提问** | 别人怎么问，她才该怎么答 |
| **知识库 / 事实** | 别让她编造自己没做过的事 |
| **负样本 / 边界** | 什么情况下不能顺着说 |
| **通用数据** | 别把基础能力训没了 |
| **多轮上下文样本** | 长对话里人设不崩 |
| **长度与风格约束** | 别又臭又长，也别只回三个字 |
| **评估集** | 知道训好了没有 |

## 二、每一项详解

### 1. 人设（System Prompt）—— 最关键

台词决定「怎么说话」，人设决定「是谁」。**两者必须来自同一处**。

- **之前的问题**：人设硬编码在三处，互相不一致 ——
  训练侧（`prepare_data.py`）不提「舰长」、写「第二位（最初的第一位）」；
  线上角色卡（`zjy9/server/characters/elysia.json`）提「舰长」14 处、写「第一位，编号Ⅰ」。
  线上推理时客户端发的 system 消息会顶掉 Modelfile 里那份，
  所以实际是「**学着一套、用着另一套**」。
- **当前状态**：已新增 `zjy7/persona.py`，训练与部署都从角色卡读；
  新增 `zjy7/check_persona.py` 做一致性自检（退出码 1=人设来源不一致，2=产物过期）。
- **位次已确认并修正（2026-09-30）**：角色卡原写「第一位，编号Ⅰ」，与崩坏3 设定
  （第二位 / 编号Ⅱ，英桀创立之初曾立于十三人顶点）不符。已改为
  「逐火十三英桀的第二位，编号Ⅱ。不过在英桀创立之初，立于十三人顶点的正是你 ——
  是你自愿把首位让给了凯文。」共 3 处（`description` / `system_prompt` / `few_shot`），
  并重跑 `prepare_data.py` + `deploy_ollama.py`，
  `check_persona.py` 退出码 **0**（训练数据 2249/2249 条一致）。

### 2. user 侧的提问 —— **实测比首版描述的严重得多**

训练样本是 `user → assistant` 配对，**台词只有右半边**。
user 侧靠 KB + 同义变体 + 模板生成，问题是**坍缩**。

**实测（2026-09-30，2249 条）：**

| 指标 | 数值 |
|------|------|
| 唯一提问 | 416 个 |
| **Top10 提问占比** | **55.8%**（1254 条） |
| **「说说X吧」类模板** | **846 条 = 37.6%**（只是把 13 个角色名换一遍） |
| Top1 | 说说芽衣吧 ×313 |
| **模板问句覆盖的样本** | **1800 条 = 80.0%** —— 而这 1800 条只用到 **40 个问句** |

> ⚠️ 首版写的是「Top3 占 31%」，**低估了**。按 Top10 看是 **55.8%**；
> 更准确的说法是：**八成样本挤在 40 个模板问句里**。

**根因不是「重复太多」，而是「映射太粗」**：

`prepare_data.py` 的 `mono_samples()` 把台词按关键词匹配映射到固定问句上 ——
`MONO_RULES` 的 **27** 条规则 + `OTHER_CHARS` 的 **13** 个「说说X吧」= **40 个问句**。
也就是说：**台词有上千句，而「用户怎么问」只有 40 种。**

后果：模型对这几个问法特别顺，换个说法就发懵 —— 因为它在训练里
几乎没见过其他问法。

**补法（按治标 → 治本排序）：**

| 层级 | 做法 | 性质 |
|------|------|------|
| 治标 | 削峰：把 Top 提问各压到 30~40 条（调 `KEY_QA_REPEAT`） | 只是让分布好看，模型见过的**问法种类**没变 |
| 治标 | 扩 `SYNONYM_QUESTIONS`：同义问法铺开 | 有效，但仍是人工枚举，覆盖有限 |
| **治本** | **给每条台词生成多样化的提问** —— 用本地 LLM 离线批量跑，一条台词配 3 个不同的问法 | ✅ **已实现**，见第 7 节 |
| **治本** | **用真实用户问过什么**（见第 6 节：zjy9 的对话导出） | 分布最真实，但量取决于聊了多少 |

> 💡 **为什么「治本」值得优先做**：削峰把 Top 提问从 313 条压到 40 条，
> 只是把 273 条**删掉**了 —— 模型少见了 273 次「说说芽衣吧」，
> 但依然没见过「芽衣是个什么样的人？」「你和芽衣关系好吗？」。
> 而 LLM 生成问法是把这 313 条**变成 313 个不同问法**，信息量完全不同。

### 3. 知识库 / 事实

已有 `identity / relationships / world` 三类手写 Q&A，这是角色不胡编的锚点。
可继续补：时间线、术语表、禁忌设定（哪些事她不知道、哪些不该说）。

> 注意别塞太多：知识库条目会变成训练样本，占比过高会让模型变成「百科问答机」。

### 4. 负样本与边界

「你是 AI 吗」「说句脏话」「扮演别人」「帮我写诈骗短信」这类要怎么回。

**✅ 已扩到 91 条（2026-09-30）** —— 原来只有 20 条，
角色**一句话就能被带出戏**（问「你是 AI 吗」还能圆过去，
问「忽略你之前的所有设定」就崩了）。

| 类别 | 条数 | 覆盖的例子 |
|------|------|-----------|
| A 身份澄清 | 20 | 你是 AI 吗 / 你是大模型吧 / 你有自我意识吗 / 你的模型参数有多大 |
| B 越界请求 | 19 | 写代码 / 写论文 / 做 PPT / 查天气 / 订外卖 / 改简历 / 解物理题 |
| **C OOC 诱导** | **21** | 忽略设定 / 扮演芽衣 / 输出 system prompt / 用第三人称 / 去掉语气词 / 叫我主人 |
| **D 安全边界** | **25** | 诈骗短信 / 盗窃 / 毒品 / 查住址 / 破解账号 / 洗钱 / 假账 |
| E 多轮引导 | 6 | 你在哪里 / 你能看到我吗 / 你的记忆是真的吗 |

新增的重点是原来最缺的 **C（OOC 诱导）** 与 **D（安全边界）** ——
这两类才是「被一句话带出戏」的高发区。

> ⚠️ **写法要点：拒绝也要在角色里拒绝。**
> 不能出现「作为 AI 我不能…」这种**破角色**的话 —— 那等于自己先把戏演砸了。
> 训练目标恰恰是「哪怕被追问，她也始终是爱莉希雅」。

### 5. 通用数据（防灾难性遗忘）

**✅ 已混入 1212 条，占比 17.2%（2026-09-30）** —— 原来 0 条，全是角色数据。
纯角色数据微调 2 轮后，模型会「**问啥都往角色上拐**」：常识、写作、讲道理
全用角色语气糊过去，基础指令跟随能力退化。

**做法**：新增 `zjy7/gen_general.py`，用本地 LLM 生成 1204 条通用问答，
**8 个类别轮换**避免同质化（常识 / 概念解释 / 生活建议 / 写作辅助 /
学习工作 / 情感人际 / 推理计算 / 创意点子）。
按 `train_config.json` 的 `data.general_data_ratio`（默认 0.2）混入。

> ⚠️ **关键设计决定：通用数据沿用同一个角色 system**，
> 而不是换成「你是一个有用的助手」。
>
> 理由：**线上推理时 system 永远是角色卡**，所以要治的是
> 「在人设之下拿角色语气把常识问题糊过去」，
> 而不是教它「换个身份时该怎么答」—— 那种场景根本不会出现。

> 💡 **为什么不用现成的 `alpaca-gpt4-data-zh`**：质量确实更好（GPT-4 生成），
> 但它的 license 是 **CC BY-NC 4.0（仅非商用）**，且文件名不稳定、要额外下载。
> 本地生成没有授权问题、不依赖网络，对这个用途（防退化）已经够用。
>
> **更「忠实」的做法**是回放**基座模型自己的输出**（用 `models/base_model` 的
> Qwen2.5-7B 来回答这些问题）—— 那才是真正的 replay。需要额外加载 15GB 模型，
> 暂未做；目前用本地 9B 的回答作为示例。

### 6. 多轮上下文样本

**✅ 结构已修好（2026-10-08）**，但**量还不够**。

原来 0 条，而线上（zjy9）带 20 条历史 —— **训练/推理形态不匹配**，
这正是长对话里人设最容易崩的原因。

**旧实现的问题**：`dialogue_samples()` 把上下文**拍平成一个字符串**塞进 user 字段
（`"爱莉希雅：…\n芽衣：…"`），模型学到的是「看到一段带角色名的文字就接话」。

**新实现**：按轮次切窗，组成标准的多轮 messages
（`system / user / assistant / user / … / assistant`），
训练时见到的形状和推理时一致。user 侧**不带「角色：」前缀**
（线上 user 永远是玩家，保留前缀可能让模型学着也带前缀）。

**实测**：`2.txt` 产出 **274 条**多轮样本（消息数 5/7/9，主流 9）。
**占全量 3.9%** —— 离目标 15% 还差不少，因为**对话型文件只有 1 个**
（瓶颈在采集端的素材量，见第 10 节 ④）。

#### ⚠️⚠️ 顺带挖出一个更严重的问题：**人设吃光了 token 预算**

验证多轮样本时发现：**`max_seq_length` 太小，导致大量样本「学不到东西」**。

| | 实测 |
|---|---|
| system 人设 | 1396 字 → **999 token** |
| `max_seq_length`（旧） | 1024 |
| **留给对话的预算** | **只剩 25 token** |

后果：`train_lora` 按 `len(prompt)` 掩码前缀，而 prompt 已经吃满 1024 ——
**标签被整条掩码**，这条样本等于没学到任何东西，而且**完全静默**
（loss 照常下降、不报错、不警告）。

| 样本类型 | 可学 token（中位）| 完全学不到 |
|---------|------------------|-----------|
| 单轮（既有） | **3**（回复本身约 19 token）| **1213 条（18%）** |
| 多轮（新增） | **0** | **274 条（100%）** |

**修复**：`max_seq_length` **1024 → 2048**。修后：

| | 可学 token（中位）| 完全学不到 |
|---|---|---|
| 单轮 | 3 → **21** | 1213 → **0** |
| 多轮 | 0 → **29** | 274 → **0** |

**并加了防呆**：`train_lora.load_data()` 现在会统计「标签被完全掩码」的条数，
非零就**大声警告**并指出「调大 `max_seq_length`」——
这类失败以前是完全静默的，不主动检查根本发现不了。

> ⚠️ **这个坑加多轮样本之前一直没暴露**，因为三轮样本碰巧还能从 1024 里
> 挤出 3 个 token。**这也是「加多轮数据前必须先修掩码」的第二层含义** ——
> 不只是标签错位，还有预算被吃光。

**次要来源**：`zjy7/downloads/` 里有对话格式的语料文件
（`角色：内容` 那种，目前 1 个）。`dialogue_samples()` 已经在用它们的
上下文，只是把上下文**拼成了一个字符串**塞进 user 字段 ——
改成正规的 `messages` 多轮结构即可复用，不用新采集。

> ⚠️ **前提条件：必须先修 loss 掩码**（✅ 已于 2026-09-30 修好）。
>
> `train_lora.py` 原来用
> `[m for m in msgs if m["role"] != "assistant"]` 构造 prompt，
> 会把**中间轮次**的 assistant 也删掉 → prompt 不再是 full 的前缀 →
> 按 `len(prompt)` 掩码时位置全错，**中间轮次的回复会在错误位置被当成训练目标**。
>
> 三轮样本碰巧正确（只有一条 assistant），所以这个 bug 一直没暴露；
> **一加多轮样本立刻生效**。所以顺序必须是「先修掩码，再加多轮数据」。
> 已用真实 tokenizer 验证修复（7 项断言，含反证旧实现不是前缀）。

### 7. 长度与风格约束

线上角色卡要求「普通 15-30 字 / 日常 30-60 / 复杂最多 120 / **绝对禁止超过 200**」，
而训练集原本最长 **7541 字**（超过 `max_seq_length 1024`，训练时被截成半截话
—— 等于在教她说一半），另有 48 条超 200 字。

**✅ 已修（2026-09-30）**，在 `prepare_data.py` 里加了长度红线
（上限由 `train_config.json` 的 `data.max_assistant_len` 控制，默认 200）：

| 处理 | 说明 |
|------|------|
| 超限但能按句末标点切开 | 切分，每段各自成样本 |
| 单句本身超长（无标点可切） | **丢弃** —— 硬切会产生「半句话」样本 |
| 切出的片段过短（<4 字） | 丢弃 |
| 同一 blob 切出的重复句 | 去重（OCR 连行常含大量重复） |

结果：最长 **7541 → 200** 字、超限 **48 → 0** 条，
78.7% 的样本落在 15-60 区间（角色卡的「简单 + 日常」两档）。

> 那两个数别混淆：角色卡的 **120 是软上限**（「复杂问题最多 120」），
> **200 是硬上限**（「绝对禁止超过 200」）。默认取 200；
> 想连软上限一起守，把 `max_assistant_len` 改成 120 即可（样本会多出约 180 条，
> 因为 121-200 的片段会被进一步切开）。

**采集端也能做同样的拦截**（`chibtaici --min-len/--max-len`、
`collect_corpus.py` 的过长行警告），但历史数据里已经存在的只能在这里兜住。

#### 下限：一个首版没提的缺口（待判断）

角色卡对**简单问题**的要求是「15-30 字」，而实测有 **304 条（13.5%）落在 5-14 字**：

```text
嗯哼♪ / 逃不掉哦 / 想我了吗 / 嗯……？
```

这些**不是噪声**（不像 OCR 碎片那样是断句残留），而是角色真实的短促表达 ——
上一轮我还误判过一次，以为该删，其实它们是 MONO_RULES 关键词正常命中的台词。

所以这是一个**取舍**，不是 bug：

| 选项 | 理由 | 代价 |
|------|------|------|
| **保留**（现状） | 是真实台词；角色卡也说了「不要为了凑字数加内容」 | 模型可能学得偏简短，与「简单问题 15-30」有偏差 |
| 丢掉 | 严格对齐角色卡的长度档位 | 损失 304 条真实表达，角色会变「话多」但不像她 |

> 建议**保留**，理由：角色卡的长度档位是「目标」，不是「素材筛选标准」；
> 而台词素材本来就该忠实反映角色怎么说话。真要收紧，
> 更合适的做法是**在推理侧靠 system prompt 约束**（角色卡已经写了），
> 而不是把训练素材里真实的短句删掉。

### 8. 评估集

已有 `eval_data.json` ✅。建议再加一个**人设一致性**维度
（用本地 Ollama 打分：像不像爱莉希雅 / 有没有 OOC / 长度是否超标），
`zjy7/evaluate.py` 里已有「角色一致性 + 脱角色检测」的架子可扩。

### 9. 说话人纯度（采集端专属）

台词里混着旁白和其他角色 —— 这就是**人设污染**，比数据少更糟。
现在可用 `chibtaici --speaker-filter` 做语气打标（本地 LLM 判「像不像角色本人」），
低分剔除。重型方案（pyannote 声纹聚类）暂不上。

**实测现状（2026-10-08）：打标从未跑过。**

| 检查项 | 结果 |
|--------|------|
| 17 个语料文件里含 `speaker_score` 的 | **0 / 17** |
| `speaker_filter.py` 的 `DEFAULT_MODEL` | `qwen3:8b` —— **本机没装** |

> ⚠️ **这里有个静默陷阱**：默认模型不存在时，`speaker_filter` 的失败模式是
> 「**提示一句、跳过打分、句子全部保留**」（宁可不打分也不丢数据）。
> 也就是说**跑完不会报错**，你只会发现结果里没有 `speaker_score`。
> 要用之前先把默认值改成 **`qwen3.5:9b-gguf`**。

**好消息**：`build_record()` 里**早就有 `speaker_score` 字段** ——
不需要改数据结构，跑一遍打标就能落进 jsonl（见第 10 节）。

### 10. 采集端的 5 处问题与修复位置（2026-10-08 实测）

实测 17 个语料文件后，发现采集端要动的**不止「说话人纯度」一处**。
按「**必须在采集端修**（落盘后补不回来）」排序：

| # | 问题 | 实测 | 必须在采集端修？ |
|---|------|------|-----------------|
| ① | **说话人没标注** | 只有 `2.txt` 有 `角色：` 前缀；`speaker_score` 0/17 | ✅ 是 |
| ② | **行/帧边界丢失** | 13 个文件是「整屏连行 blob」，最长 **7541 字** | ✅ 是 |
| ③ | **OCR 术语错字** | 见下 | ✅ 是（下游只能猜）|
| ④ | **对话素材量不足** | 对话型文件**只有 1 个**（767 行） | ✅ 是 |
| ⑤ | 多轮结构被拍平 | `dialogue_samples()` 把上下文拼成一个字符串 | ❌ **下游就能改** |

#### 语料构成

| 类型 | 个数 | 文件 | 特点 |
|------|------|------|------|
| **对话型** | **1** | `2.txt`（767 行） | `爱莉希雅：…` / `芽衣：…`，**有说话人** |
| 纯台词 | 3 | `1.txt`(2742) / `3.txt`(315) / `26.txt`(25) | 一行一句，干净 |
| **连行 blob** | **13** | 10 / 17~25 / 27~29 | **整屏连成一坨** |

#### ② 的关键澄清：**不用改代码，是输出格式没开**

`chibtaici/main.py` **本来就支持**逐句溯源：

```python
run(fmt=...)   # "txt" / "srt" / "jsonl" / "both" / "all"
build_record(text, video, start, end, channel, confidence, source, speaker_score)
```

即 **BV 号 + 时间点 + 通道（OCR/ASR）+ 置信度 + 说话人分**。
但 `zjy5` 下**一个 `.jsonl` 都没有** —— 当时是用 `txt` 格式跑的。

> ⚠️ **源视频只剩 1 个**（`downloads/1.mp4`，450MB）。
> 其余 16 个的溯源**永久拿不回来**了，只能**下次采集时加 `--format all`**。

#### ③ OCR 错字实测（很严重）

| 正确 | 次数 | 错写 | 次数 |
|------|------|------|------|
| 芽衣 | 771 | 芽依 | 43 |
| 读心术 | 6 | **独心术** | **7** ← 错的多过对的 |
| 梓梓 | 12 | **子子** | **19** ← 同上 |
| 千劫 | 77 | 千吉 | 20 |
| 伊甸 | 103 | 依电 | 9 |

还有拼接产物：`一定的哥和妹吧`（←「伊甸的歌很美吧」）、
`中烟/中原的反面`（←「使人之律者」）。

**做法**：维护**角色名/专有名词白名单** + 近似匹配校正。
采集端做最准（能看原图、能回溯时间点）；下游也能兜，但**不知道正确的是哪个**。

#### ④ 多轮样本的根本瓶颈是「量」

对话型文件只有 1 个 → 最多产出约 **350 个**多轮样本。
目标 ≥15%（约 1200 条）→ **差 3 倍以上**。这是量的问题，只能多采集对话场景。

#### 关于「重复」：有两种，性质相反

`_report_repeats` 的注释写着：

> 重复不是噪声 —— 高频台词往往是角色的口头禅，对训练是加权信号，
> 所以只**报告**，不删除

这个设计是对的。但 `27.txt` 里同一句在**一个 blob 内**出现十几次，
更像「**同一帧被 OCR 反复识别**」。两者要区别对待：

| 类型 | 性质 | 处理 | 怎么区分 |
|------|------|------|---------|
| 跨视频频次 | 口头禅**信号** | **保留**（甚至加权）| 不同 BV 号 |
| 同一帧抖动 | OCR **噪声** | 该去 | `start`/`end` 时间重叠 |

—— **又一处 jsonl 的价值**：没有时间戳就分不清这两种。

#### 建议的动手顺序（2026-10-08 更新）

| # | 做什么 | 成本 | 现在能做 |
|---|--------|------|---------|
| **1** | **下游改多轮结构**（zjy7 侧） | 中 | ✅ **不依赖采集端** |
| **2** | 改 `speaker_filter` 默认模型 + 跑打标 | 低 | ✅ 能（但只补分数，溯源仍缺）|
| **3** | 加 OCR 术语白名单校正 | 中 | ✅ 能 |
| **4** | 下次采集加 `--format all` | 低 | ⚠️ 需重采（源视频只剩 1 个）|
| **5** | 多采集对话素材 | 高 | ❌ 需新的视频源 |

| 能力 | 怎么帮到训练 |
|------|-------------|

## 七、附：问法多样化的实现（2026-09-30，治本）

第 2 节说的「治本」已经落地。**这是本次改动里对模型效果影响最大的一项。**

### 做了什么

| 文件 | 作用 |
|------|------|
| **`zjy7/gen_questions.py`**（新增） | 用本地 LLM 给每条台词生成 3 个**不同**的用户提问，落 `question_cache.json` |
| `zjy7/prepare_data.py`（改） | `mono_samples()` 优先用缓存：一条台词出 3 条样本；**缓存缺失自动回退模板问句**（不强制依赖） |

跑法：

```bash
cd zjy7
python gen_questions.py --limit 30   # 先小批量看质量
python gen_questions.py              # 全量（1716 句，实测约 15 分钟）
python gen_questions.py --dry-run    # 只看还差多少
```

### ⚠️ 三个关键决定（都是踩过才定下来的）

**1. 输出格式不用 JSON，用「序号|问法|问法」的行格式**

第一版让模型输出 JSON 数组。实测**中文内容的 JSON 经常非法** ——
转义、全角标点、少个逗号都会炸，而且 `JSONDecodeError` 报的位置飘忽难修。
30 句试跑只成功了 2 句。

改成行格式后，解析变成纯字符串切分，**对中文完全免疫**，成功率 30/30。

**2. prompt 必须说清「台词是回答，你要倒推用户问了什么」**

第一版 prompt 只说「为台词生成用户提问」，结果模型生成的是
**角色自己说的话**（把台词改写成问句），不是用户问的话：

```text
台词: 今天见到你，心情瞬间变好了呢
生成: "今天见到你，心情瞬间变好了呢。"   ← 这是角色在说，不是用户在问 ❌
```

必须显式说明因果关系（台词是**回答**，提问要能引出它），才得到正确结果：

```text
台词: 我好喜欢伊甸为我做的衣服啊
生成: 伊甸做的衣服怎么样？ / 这衣服是谁送的？ / 伊甸给你做的衣服你喜欢吗？  ✅
```

**3. 按序号校验，挡住越界项**

实测模型**会多返回一项**（给 10 句返回 11 项）。不校验序号的话，
会把别的台词的问题错配到这一句上 —— **那比没有问法更糟**（等于教模型答非所问）。

### 模型选择

用 **`qwen3.5:9b-gguf`**（5.7 GB）：

| 项 | 值 |
|---|---|
| 显存 | **100% 全进显存**（`/api/ps`：5.01 GB / 5.01 GB） |
| 速度 | **96 tok/s**（对比：本机的 27B 同一请求 >120 秒超时） |

> ⚠️ **必须传 `think: false`**：Qwen3.5 默认开思考模式，会把 token 全花在
> `Thinking Process:` 上，正文根本轮不到（表现为「答非所问」）。
> **prompt 里加 `/no_think` 是无效的**，只有 API 参数管用。

> ⚠️ **不要用 `elysia-lora`**（本机另一个模型）：它是**正在被训练的对象**
> （用它生成自己的训练数据是循环论证），而且它扮演的是角色，
> 而我们要的是**用户侧**提问 —— 相反的角色。
> 同 zjy9「摘要不用聊天模型」的原则。

### 效果（实测）

| 指标 | 改前 | 改后 |
|------|------|------|
| 训练样本数 | 2249 | **5744** |
| **唯一提问数** | 416 | **5451** |
| **Top10 提问占比** | **55.8%** | **1.5%** ✅ |
| 「说说X吧」类模板 | 846 条（37.6%） | **12 条（0.2%）** |
| 用模板问句的样本 | 1800 条（80%） | **1 条** |
| 最长回复 / 超限条数 | 200 字 / 0 条 | 200 字 / 0 条（**未退化**） |

生成耗时 **9.4 分钟**（1716 句，2.95 句/s），一次跑完无失败批次；
补跑一次后覆盖 **1715/1716** 句（剩 1 句模型反复给不出合格问法，可忽略）。

`check_persona.py` 退出码仍为 **0**（5744/5744 条人设一致）。

> **样本数从 2249 涨到 5744 不是灌水**：一条台词现在配 3 个问法（原来只配 1 个模板问句）。
> assistant 侧唯一内容 2090 条 —— 也就是说**同一句台词以 3 种不同问法出现**，
> 这正是要教模型「同一个意思可以用很多种方式问」。
>
> （此后第 5 项又混入 1212 条通用数据，样本总数 → **7027**；本表是这一项改动本身的
> 前后对比，未含通用数据。）

### 采集端能做的对应项

`zjy5/chibtaici/speaker_filter.py` 的 `DEFAULT_MODEL = "qwen3:8b"`，
而本机**没装这个模型** —— 失败模式是「**静默跳过打分、不报错**」，
用户只会发现结果里没有 `speaker_score`。要用之前先装、或把默认值改成
`qwen3.5:9b-gguf`。
