> **版本体系**：从 `1.0.0` 起算，采用 `主.次.修订`（SemVer 语义化版本）。
> **当前版本**：**`4.13.0`**（2026-11-26）
> **编写依据**：git 全量提交历史（150 个提交，2026-07-01 → 2026-11-18）、根 README、
> `docs/` 分析报告、`zjy13/docs/` 与 `zjy14/docs/` 全部工作记录，以及桌面四份需求文档
> （`ESP32-S3方案.txt`、`ESP32-S3_…_V2.0_本地TTS版.txt`、`Fun-CosyVoice3.0_RTX5070_12GB_…提示词.md`、
> `design-decisions.md`）。
> **原则**：只写有证据的结论，未验证项明确标注「未验证」。各版本号是按**时间久远 / 功能重要性 /
> Bug 修复严重度**回溯定义的里程碑，不是当时实际打过 tag 的版本。
> **tag 现状**：2026-11-19 补打了 6 个里程碑 tag（`v1.0.0` / `v2.0.0` / `v3.0.0` /
> `v4.0.0` / `v4.11.0` / `v4.12.0`），均为**附注 tag**，指向该版本完成时的 commit。
> 中间的修订号与部分次版本号仍未打 tag —— 它们是文档里的文字里程碑。

## 一、版本号怎么定（规则）

| 位 | 什么时候进位 | 本项目里的判定标准 |
|---|---|---|
| **主版本**（X.0.0） | 项目形态、架构路线发生**不可逆的质变** | ① 从零建设某个子系统（如语音系统诞生）；② 整条链路首次在真实硬件上跑通；③ 整体技术路线改变（不能靠改配置回退） |
| **次版本**（X.Y.0） | 在形态不变的**前提**下，加入有分量的新能力 | 新增模块/子项目、新协议、新引擎、新的用户体验机制（流式、填充音等） |
| **修订**（X.Y.Z） | 只修缺陷、调参数、补测试、补文档，能力面不变 | 修复影响可用性的 Bug（崩溃、断连、静默失效）；P0 级缺陷单独占一个修订号 |

补充约定：

1. **同一版本内同日多提交合并**：同一天围绕同一目标的若干提交（如「修 P0 + 补测试 + 补文档」）合并为一个修订号。
2. **纯文档订正、目录整理**并入当期版本，不单独进位。
3. **「发现」与「修复」分开记**：审查/审计发现的问题本身不算迭代，只有**实际修复**才进位。
4. **按仓库节奏而非日历进位**：空档期（08 月、10-16 ~ 10-18 等）不计版本。

### 2.1 已打 tag 的里程碑

| `v4.12.0` | `d613a74` | 2026-11-19 | **真机联调闭环** + 4 个静默失效修复 |

为什么是这 6 个：每个都是**形态或能力发生实质变化**的节点（主版本 4 个 + 可观测性收尾 +
真机在环）。中间的修订号多为缺陷修复，逐个打 tag 会让 tag 列表失去区分度。

常用命令：

```bash
git tag                          # 列出所有 tag
git tag -n20 v4.12.0             # 看某个 tag 的完整说明
git diff v4.11.0 v4.12.0         # 看两个版本之间改了什么
git checkout v4.11.0             # 检出历史版本（只读查看）
git checkout main                # 切回主干
git show v4.12.0                 # 看 tag 详情 + 该 commit
```

> 注意：`git checkout v4.11.0` 会进入 detached HEAD 状态（正常，tag 不是分支）。
> 查看完务必 `git checkout main` 回来，否则新提交不会落在任何分支上。

**最严重的一个：async 路由里调同步阻塞函数，导致并发限制形同虚设。**

现象：单请求 6.40s，3 并发墙钟只有 8.03s，`median_wait_ms = 0`（从未记录到排队）。

修复：用 `run_in_threadpool` 把阻塞调用挪出事件循环。

**关键设计：游标分页而非 OFFSET**

第 1 页已看过的记录。改用 `(created_at, id)` 复合游标：

WHERE created_at < ? OR (created_at = ? AND id < ?)
ORDER BY created_at DESC, id DESC

同一秒内多条记录也能正确翻页（靠 id 兜底）。有测试
`test_pagination_same_timestamp` 守护。

**日志反向读取**：从文件尾部按 64KB 块回读，只解析需要的行数。
「看最近 100 条」不会因文件有 50MB 而变慢。
坏行跳过并计数（`bad_lines`），不因一行坏了整体失败。

第一版用 FTS5 默认的 `unicode61` 分词器，实测：

```
数据: '今天天气不错'
搜 '天气'   -> 0 条
搜 '天*'    -> 0 条
搜 整句     -> 1 条
```

**原因**：unicode61 按 Unicode 词边界切分，把整句当成**一个完整 token**。
它不是子串搜索。若直接上线，「搜天气返回 0 条」会让人以为功能坏了。

**修正**：改用 `trigram`（3 字符滑窗）。实测：

| 查询 | unicode61 | trigram |
|---|---|---|
| `天气`（2 字） | 0 | **0** |
| `今天天`（3 字） | 0 | **1** |
| `今天天气`（4 字） | 0 | **1** |

trigram 的约束：**查询串必须 ≥ 3 字符**。因此做了自动降级 ——
短查询走 LIKE（慢但正确），长查询走 FTS 索引。
**这个判断必须在实现内部完成**，要求调用方记住「查询要 ≥3 字」本身就是设计缺陷。

**FTS5 特殊字符转义**：`C++`、`"未闭合引号`、`NEAR(a b)` 这些会让 SQL 抛异常。
每个词用双引号包裹，引号内特殊字符失去语义。有测试覆盖 6 种危险输入。

### 8.1 关于「首包 500ms」目标的说明

需求文档 `Fun-CosyVoice3.0_RTX5070_12GB_…提示词.md` 要求首包 ≤ 500ms，
4.7.0 实测最低 **1.48s**（流式、长句），差距约 3 倍。

**这不是工程优化不到位，而是模型架构约束**。首包构成（zjy13 已量化）：

| 环节 | 耗时 | 占比 |
|---|---|---|
| LLM 生成 28 token | 约 0.86s | 52% |
| Flow 处理 28 token | 约 0.50s | 30% |
| HiFT 生成音频 | 约 0.30s | 18% |

LLM 自回归占一半以上。要突破必须换模型或改架构（如非自回归 TTS），
属 `5.0.0` 级别的路线变更，不是调参能解决的。

### 8.2 关于情绪控制的说明

4.6.0 的否定结论是**用安慰剂对照证明的**，不是「感觉不行」：

- 真情绪指令让 F0 变化 10.1 / 24.3 Hz
- 无意义指令（「请用蓝色的语气」）让 F0 变化 15.4 / 72.5 Hz

后者更大，说明模型只对 prompt 变长有反应。因此当前**不应**在任何对外
材料中声称「支持情绪控制」。若这是产品的硬需求，只能换引擎。

### 9.6 排障中的两次误判（留档避免重犯）

**误判 1：把上游路由器当成移动热点**

看到 `netsh wlan show networks` 扫不到 `Isla2Badge`，就断定热点改名，
把固件 SSID 改成扫描到的 `没实力了吧2` —— 结果板子报 `reason 15`
（四次握手超时 = 密码错），反证那是 PC 连接的上游路由器。

事实：**`netsh wlan show networks` 不会列出本机自己开的移动热点**。
正确做法是用 WinRT `NetworkOperatorTetheringManager` 读权威配置。

教训：**不要用「看不到」推断「不存在」**。

**误判 2：兜底条件依赖了错误的变量**

为修「卡在 PLAYING」加的兜底写成 `if (s_got_end_marker && s_playing)`。
但卡死场景下 `s_playing` **已经是 false**（播放任务已退出），
`s_state` 才是卡住的 `ST_PLAYING` —— 兜底永远不触发，白等一轮。

教训：**加兜底时必须确认条件变量在故障场景下的真实取值**。

### 9.7 网络拓扑变更

移动热点方案被废弃，原因不是配置错误（WinRT 确认 SSID/密码/频段全部正确），
而是**硬件限制**：

```
netsh wlan show drivers → "Hosted network supported: No"
```

Realtek 8851BU 是**单射频** USB 网卡，同时承担「连上游 WiFi」与
「广播虚拟 AP」时会周期性离信道，板子在离信道窗口扫描就收不到 beacon。
实测 30 秒内 3 次 `reason 201`、0 次成功连接。

改为**板子直连上游路由器**，与 PC 同网段：

```c
#define BADGE_WIFI_SSID "没实力了吧2"
#define BADGE_VOICE_AUTOCONNECT_HOST "192.168.43.164"   // PC 局域网 IP
```

> ⚠️ 该 IP 由 DHCP 分配，**可能变化**。板子连不上服务端时先确认 PC 当前 IP。
> 想一劳永逸可在路由器上给 PC 绑定静态 IP。

### 10.3 缺陷 12：两个修复互相冲突（真根因）

`esp_codec_dev` 的 `_i2s_data_set_fmt()` 内部会先**关掉**通道：

```c
// audio_codec_data_i2s.c:594-599
if (dev_type & ESP_CODEC_DEV_TYPE_OUT) {
    _i2s_drv_enable(i2s_data, true, false);   // 关 TX，函数内不再使能
}
```

它设计给 `open()` 流程内部用 —— `open()` 调完 `set_fmt` 会紧接着 `enable`。

而 4.12.1 为修「声音变尖」在 `handle_playback_start` 里
**open 之后**又调了一次 `set_fmt` 作为兜底：

```c
esp_codec_dev_close(s_spk);
esp_codec_dev_open(s_spk, &fs);                            // ← TX 被使能
data_if->set_fmt(data_if, ESP_CODEC_DEV_TYPE_OUT, &fs);    // ← TX 被关掉，没人再开
```

串口时序是决定性证据：

```
i2s tx channel enabled      ← open() 使能
Open codec device OK
i2s tx channel disabled     ← set_fmt 关掉，且不再使能
E i2s_common: i2s_channel_write(1361): The channel is not enabled
W voice: 写 codec 失败 ret=-1（已连续 1 次，state=4 avail=1024）
```

**单看任何一处代码都正确** —— 所以静态审计不可能发现。
修法：`set_fmt` 之后显式补一次 `enable`。

### 10.4 对 4.12.1 归因的修正

4.12.1 把「卡在正在回应、无声音」记为**问题 7**，
归因为「`play_task` 霸占 CPU，心跳被饿死」。

本次证明那个归因**不完整**：

| 4.12.1 的判断 | 本次实测 |
|---|---|
| `play_task` 饿死心跳 → 服务端 36s 断连 | 真实存在，但只解释「断连」，不解释「没声音」 |
| 加 `finish_playback_force()` 兜底 | 兜底**写在预缓冲门之后**，断流场景下是死代码（缺陷 1） |
| `set_fmt` 兜底修「声音变尖」 | 副作用是把 I2S TX 关掉 → **完全没声音**（缺陷 12） |

也就是说：4.12.1 的两个修复**互相抵消** ——
一个让状态机能收尾，另一个让声音出不来。
这解释了为什么用户当时反馈「还是不行」。

### 10.5 12 个缺陷一览

| # | 现象 | 根因 | 层次 |
|:-:|---|---|---|
| 1 | 卡在正在回应、按不动 | 预缓冲门 `continue` 跳过全部收尾兜底 → 看门狗是死代码 | ESP32 固件 |
| 2 | 同上（触发源） | 结束标记帧被 `turn_short` 校验连坐丢弃 | ESP32 固件 |
| 3 | 只听到「嗯…」然后无声 | 填充音期间回报 `playback_done` 被回 error → 板子复位 → 正文全丢 | zjy13 服务端 |
| 4 | 状态在播但完全无声、无日志 | `esp_codec_dev_write` 返回值被丢弃 | ESP32 固件 |
| 5 | 卡死后连 `playback_done` 都不发 | `finish_playback()` 首行 `if (!s_playing) return;` | ESP32 固件 |
| 6 | 异常轮次板子收不到结束标记 | 只有成功路径发结束标记帧 | zjy13 服务端 |
| 7 | 怎么按都没反应 | `RECORDING` 是唯一没有超时的 BUSY 状态 | zjy13 服务端 |
| 8 | 卡死后要干等 135 秒 | 三处看门狗都用 120 秒估计值 | zjy13 服务端 |
| 9 | 偶发断连 | 心跳超时 30s vs 固件间隔 20s，余量仅 10s | zjy13 服务端 |
| 10 | 每轮必播填充音 | `_record_latency` 全仓库无调用点 | zjy13 服务端 |
| 11 | 精简固件每轮必卡 | 完全不识别结束标记帧 | zjy13 固件 |
| **12** | **完全没声音（真机确认）** | **`set_fmt` 兜底关掉 I2S TX 且不再使能** | **ESP32 固件** |

另有 4 个连带修复：重复 `recording_stop` 覆盖流水线、`_on_cancel` 不停填充音、
`ERROR` 状态无法自愈、精简固件无音频也推进状态。

### 10.7 三条教训

1. **静态审计有明确能力边界**：缺陷 12 是「两个各自正确的修复互相冲突」，
   任何只读代码的审计都不会把它列为缺陷。报告里写「已修复」时，
   必须区分「静态推断正确」与「真机验证通过」。
2. **诊断日志本身就是生产力**：缺陷 12 之所以能定位，是因为阶段一在
   `play_task` 里加了 `写 codec 失败 ret=%d`。修复前这个故障**完全无痕** ——
   状态机在播放、缓冲在消耗、就是没声音，串口一个字都没有。
3. **加诊断代码要防止引入新缺陷**：我加的第一版写失败处理直接造出一个死循环
   （写失败 → 不清缓冲 → 无限重试），把串口刷爆、状态反复横跳。
   任何「新增分支 + `continue`」的改动，都要检查循环不变量是否被破坏。

## 十一、`4.13.0`（2026-11-26）语音链路一键启动控制台

> **完整记录**：[`zjy14/docs/33_LAUNCHER.md`](../zjy14/docs/33_LAUNCHER.md)

### 11.1 为什么是次版本号

按 §一 的判定规则：

> **次版本**（X.Y.0）：在形态不变的前提下，加入**有分量的新能力**。

本日交付的是**新的运维能力**，不是缺陷修复：

- 新增一个**独立控制台进程**（网页一键启动 ASR/LLM/TTS/网关）
- 新增 zjy14 主界面的「语音链路启动」页
- 新增 **ASR 独立服务**（原本内嵌在网关里）

因此进位 `4.13.0`，而非 `4.12.3`。

### 11.2 解决的真实痛点

改造前让板子说话要开 2~3 个终端、顺序不能错：

| 痛点 | 后果 |
|---|---|
| 要开多个终端 | 顺序错了网关直接退出码 2 |
| TTS 加载 10~15 秒 | 分不清「还在加载」还是「已经崩了」 |
| ASR 内嵌在网关 | ASR 出问题要重启网关 → 板子连接全断 |
| TTS 容易指错 | `zjy13/.env` 的 `TTS_BASE_URL=:50000` 是 **zjy13 的** TTS |

### 11.3 关键设计：TTS 归属被钉死

启动网关时**显式注入** `TTS_BASE_URL=http://127.0.0.1:50001`：

```python
env["TTS_BASE_URL"]    = "http://127.0.0.1:50001"   # zjy14 CosyVoice3
env["ASR_SERVICE_URL"] = "http://127.0.0.1:50002"
```

能生效的原因：zjy13 的 `load_env_file()` 用 `load_dotenv(override=False)`，
**进程环境变量优先于 `.env`**。

> 实测证据：一轮对话后 zjy14 的 `/api/v1/history` 出现
> `engine=cosyvoice3 voice=elysia dur=18.44s`，与该轮 19.13s 音频吻合。

### 11.4 ASR 独立化

新增 `zjy13/server/asr_service.py`（标准库 HTTP，:50002）；
网关新增 `--asr-url`，配置后**不再本地加载 FunASR**：

| 收益 | 说明 |
|---|---|
| 不重复占显存 | 模型只驻留一份（网关不再加载第二份） |
| 可独立重启 | ASR 崩了不用断板子连接 |
| 可独立验证 | `POST :50002/transcribe` 直接测识别 |

为什么用标准库：`.venv-asr` 里没有 fastapi/uvicorn（实测 `find_spec` 均 False）。
