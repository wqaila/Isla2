### 二·附三　一条**被我误判为「不成立」、实际成立**的判断（2026-09-28 更正并**已修复**）

#### ✅ P0（**成立**）　chibtaici 的 OCR「版本错配导致不可用」

- **初判**（正确）：环境里装的是 `paddleocr 3.4.0`，而代码按 2.x 解析，
  导致 OCR 静默返回空
- **我第一次复核时误判为「不成立」**，理由是「三个 Python 环境里 paddleocr
  都没装」。**这个推理是错的** —— 当时 `zjy5/.venv` 已损坏（见二·附二），

- **2026-09-28 修复 venv 后实测**：
  - 实际装的是 `paddleocr 3.4.0` + `paddlepaddle 3.0.0` + `paddlex 3.4.3`
  - 而 `requirements.txt` 钉的是 `paddleocr==2.7.0` + `paddlepaddle-gpu==2.6.2`
  - 3.4.0 的 `ocr()` 已标注 `@deprecated("Please use predict instead")`，
    `predict()` 返回**字典列表**；而 `main.py` 按 2.x 的
    `result[0]` / `line[1][0]` 解析 → **抛异常**
  - 异常被 `try/except` 吞掉只 print → **OCR 静默返回空**

1. 新增 `_extract_texts_from_ocr_result()`：把 2.x 的

2. `_ocr_from_frame()` 优先用 `predict()`（3.x 推荐 API），2.x 自动回退到 `ocr()`
3. **不再静默**：调用失败前 3 次逐条打印，`extract_ocr_lines()` 结束时汇总
   `⚠️ OCR 调用失败 N/M 帧`；全部失败且零结果时额外提示
   「先看失败原因，别误以为视频里没字幕」

### 二·附四　另一个真正的 GPU 阻塞点：PyTorch 不支持 sm_120（2026-09-28 发现并**已修复**）

**GPU 本身没问题**（见前文更正），但 **zjy7 的 `lora_env` 里装的 torch 用不了它**：

| 项 | 值 |
|---|---|
| `torch`（修复前） | **2.5.1+cu121**（CUDA 12.1 构建） |
| 该 torch 编译的架构 | `sm_50 / 60 / 61 / 70 / 75 / 80 / 86 / 90` |
| 本机 GPU | RTX 5070 = **`sm_120`**（Blackwell） |
| 实测结果 | `is_available()` = True，但一跑运算就 `CUDA error: no kernel image is available for execution on the device` |

**RTX 50 系（Blackwell）需要 CUDA 12.8+ 的 PyTorch 构建。**

#### ✅ 已修复（2026-09-28）

升级为 **`torch 2.9.1+cu128`** + `torchvision 0.24.1+cu128` + `torchaudio 2.9.1+cu128`：

| 验证项 | 结果 |
|--------|------|
| 编译支持的架构 | `sm_70 / 75 / 80 / 86 / 90 / **100** / **120**` |
| 3000×3000 矩阵乘 | ✅ 成功 |
| softmax | ✅ 成功 |
| 5 步训练（含 `backward()`） | ✅ loss 正常下降，参数在 `cuda:0` |
| `bfloat16` 前向 | ✅ 输出 `(64, 256) torch.bfloat16` |
| 训练栈 import | ✅ `transformers 5.8.0` / `peft 0.19.1` / `bitsandbytes 0.49.2` / `datasets` / `accelerate` / `safetensors` 全部正常 |

> **踩坑记录**：装的时候 pip 卸载旧包那一步被本机 `safe-delete` 拦截层打断，
> 报 `SHFileOperationW 失败: 0x2`（它把删除重定向到回收站，回收站 API 失败就
> 直接抛异常）。沙箱内/外都一样。解法：该拦截层由 `CODEBUDDY_SAFE_DELETE_ENABLED`
> 控制，**为这一条 pip 命令设成 `0`** 即可 —— pip 卸载旧包是正常且必要的操作。
>
> 另外下载走**阿里云镜像**（`mirrors.aliyun.com/pytorch-wheels/cu128`），
> 实测 1.6-2.1 MB/s，比官方源快一倍多；已核对三个文件的 `content-length`
> 与官方**完全一致**。用可续传的 curl 下载（pip 不支持断点续传，
> 2.67 GB 一次下完风险太高）。

> **结论**：**「GPU 能不能用」要分两层看** ——
> ① 驱动/CUDA 能不能识别设备（**能**）② 装的框架有没有编译对应架构的内核
> （原先是**不能**，现已修复）。
> 只测 `torch.cuda.is_available()` **不够，必须真跑一次运算**。

### 二·附五　paddle 的 GPU 支持（2026-09-28 发现并**已修复**）

修完 paddleocr 版本错配后，顺带发现 **OCR 其实一直跑在 CPU 上**：

- venv 里**同时装着** `paddlepaddle 3.0.0`（CPU）和 `paddlepaddle-gpu 2.6.2`，
  实际生效的是 CPU 版 → `is_compiled_with_cuda()` = `False`、GPU 数 = 0
- 而 `paddlepaddle-gpu 2.6.2`（PyPI 上 Windows 的最新版）**也不支持 sm_120**，
  所以单纯把它「换回来」没用 —— 和 torch 是同一类问题

#### ✅ 已修复

1. 卸掉两个冲突的 paddle，从 **PaddlePaddle 官方源**装 `paddlepaddle-gpu==3.4.0`（cu129）：
   ```
   pip install paddlepaddle-gpu==3.4.0 \
       --index-url https://www.paddlepaddle.org.cn/packages/stable/cu129/
   ```
   > 该索引 URL 被百度 WAF 拦（curl 拿不到），但 **pip 会跟到真实 CDN**
   > （`paddle-whl.cdn.bcebos.com`）—— 1.05 GB，用 curl 续传比 pip 快得多
   > （4 MB/s vs 1.7 MB/s）。
2. **补 CUDA 运行时 DLL**：这个 wheel **不打包** cuBLAS/cuDNN 等，
   装完一跑就报 `cublas64_12.dll is not configured correctly (error code 126)`。
   解法是把 cuBLAS/cuDNN/cudart/nvrtc 等 **22 个** DLL 放进
   `<venv>/Lib/site-packages/paddle/libs/`。
   本机零下载：直接从 zjy7 的 `torch/lib` 复制（torch 的 wheel 自带完整 CUDA 运行时）。

> ⚠️ **`nvJitLink_120_0.dll` 千万别漏**（2026-09-28 补记）。
> 收尾清理临时轮子后例行复核，`import paddle` 突然抛：
> ```
> OSError: [WinError 126] Error loading "...\libs\cusolver64_11.dll"
> ```
> **报错文件名会误导** —— 它指向 cusolver，但 cusolver 本身是好的。
> 用 `ctypes.WinDLL` **逐条加载**才定位到断点：
> `cublas` / `cublasLt` / `cudart` 全 OK，只有 `cusolver` FAIL
> → 说明断点在更冷门的依赖上：`cusolver64_11.dll` 依赖 `nvJitLink_120_0.dll`，
> 而补 DLL 时漏拷了它。补上（22 个）后恢复。
>
> **两个可复用的结论**：
> 1. 排查 DLL 加载失败，**逐条加载**比盯着单个报错文件名有效得多；
> 2. **`get_default_device()` 也证明不了能用** —— 缺 DLL 时它照样输出 `gpu:0`，
>    真正的错误要等第一次运算才抛。这次就是靠真跑运算发现的。
>
> `zjy5/chibtaici/README.md` 已补上该警告 + 逐条加载自检脚本。

**验证**：

| 项 | 结果 |
|---|---|
| paddle 版本 | `3.4.0`，`编译含 CUDA: True`，GPU 数 1 |
| 识别的算力 | `GPU Compute Capability: 12.0`（**认得 sm_120**） |
| 真实矩阵乘 | ✅ 2000×2000 成功，张量 `Place(gpu:0)` |
| PaddleOCR 选的设备 | `get_default_device()` → **`gpu:0`** |
| **端到端 OCR** | ✅ 识别出 `'你今天怎么来了'`，**单帧约 0.7s**，零失败 |
| CPU 回退路径 | ✅ 仍可用（不会因为这次改动把 CPU 路走死） |
| 补 DLL 后复测 | ✅ 矩阵乘通过，`sm_120` 正确识别 |

> PaddleOCR 3.x 自己会调 `get_default_device()` 选设备，所以只要它返回 `gpu:0`，
> OCR 就自动走 GPU，**代码不用改**。
>
> **教训（和 torch 那次一样）**：`is_compiled_with_cuda()` 返回 `True` 只说明
> 「编译时带了 CUDA」，**不代表运行时能找到 CUDA 库、更不代表能真跑**。
> 必须实际跑一次运算。

#### zjy5：SRT 输出 + 进度显示（2026-09-28 完成）

| 做了什么 | 说明 |
|---------|------|
| **chibtaici 出 SRT** | `merge_and_deduplicate` 原本把 `start`/`end` **丢掉**、只返回纯文本，所以出不了字幕。重构为 `merge_timeline`（保留时间轴）+ `_dedup_texts`（纯文本，行为不变），新增 `to_srt` 与 `--format {txt,srt,both}` |

**两个关键设计决定**：

1. **两条输出路线的去重策略必须不同** —— `txt` 是**语料**（要的是去重后的句子集合，
   喂给 zjy7），`srt` 是**字幕**（要的是时间对齐）。所以不是同一个文件换个扩展名。
   默认仍是 `txt`，保证既有流程不受影响。
2. **OCR 条目只有时间点、没有持续时间**（命中某一帧时 `start == end`）。
   转 SRT 时补 1.2s 最小持续时间，并把结束时间**夹在下一条开始之前**，避免字幕重叠。

**验证**（13 项断言 + 回归对照）：

- 用**逐字照抄的旧算法**当基准，500 组随机输入下 txt 输出**逐字节一致** —— 确认没破坏既有行为
- 400 组随机输入生成的 SRT 全部满足：条数一致 / 起<止 / 不重叠 / 索引递增
- `--help` 仍零依赖可跑（新增的 `--format` 已生效）
- 顺带修掉一个既有副作用：`merge_and_deduplicate` 原本会**就地修改**调用方传入的列表

**⚠️ 实施中踩的坑（值得记一笔）**：

用 bash heredoc 内联传 Python 代码时，**MSYS2 会把 `\d` 这类序列当路径转换**
（`\d\d:` 被改成 `/d/d:`）。结果测试里的正则**静默失效**，而 `all()` 在空列表上
返回 `True`，把失败伪装成了"通过"。**教训：测试脚本要写成文件再跑，
不要在 shell 里内联带反斜杠的代码；空集合上的 `all()` 是假阳性陷阱。**

#### zjy9：音频鉴权缺陷修复 —— `/tts_cache` 改为签名 URL（2026-09-28）

**发现方式**：做 Android 接入时，先写探针脚本验证「原生播放器能不能播」，
结果发现设了 `api_token` 的机器上音频请求返回 **401**。

**问题本质**（两个方向都错）：

| 方案 | 后果 |
|---|---|
| `StaticFiles` 直接挂载（原实现） | **完全绕过** `_check_api_token`，任何人猜到文件名就能下载合成音频 |
| 强制带 `Authorization` 头 | 原生播放器（ExoPlayer/MediaPlayer）**只吃一个 URL，塞不进请求头**，Android 永远播不出声 |

**修法 —— 签名 URL**：链接自带短期凭证，服务端在路由内校验。

```
/tts_cache/<文件>?exp=<unix>&sig=<hmac>
```

- 签名覆盖「文件名 + 过期时间」，**不含 `api_token` 本身**（避免令牌随链接泄漏）
- 有效期 `TTS_URL_TTL_SEC = 3600`（1 小时，够听完一轮对话）
- 未设 `api_token` 时不做校验，**行为与从前完全一致**（不破坏本机默认用法）
- 中间件把 `/tts_cache` 加进放行前缀 —— 但**这不是免认证**，
  只是把校验责任交给路由（路由内 `hmac.compare_digest` 常量时间比较）
- 附带防目录穿越（拒绝 `/`、`\`、`..`）与 `FileResponse` 的正确 MIME

**验证**（`tests/test_tts.py` 第 14 组，10 项）：

| 用例 | 结果 |
|---|---|
| 未设令牌直连可播（向后兼容） | ✅ 200 |
| 设令牌后裸链被拒 | ✅ 401 |
| 正确签名可播 + MIME 正确 | ✅ 200 / `audio/mpeg` |
| 篡改签名 | ✅ 401 |
| 过期签名 | ✅ 401 |
| 签名不可跨文件复用 | ✅ 401 |
| 换令牌后旧签名立即失效 | ✅ 401 |
| 目录穿越 | ✅ 404 |
| `/api/tts` 返回的 URL 自带签名 | ✅ |

`test_tts.py` 从 **44 项 → 54 项**，全过。

> ⚠️ **测试必须用临时配置**（本轮新加的隔离）。原因有两个，都是踩过的坑：
> ① **污染**：用例要反复 `PUT /api/config`，打真实配置的话一旦中途异常退出，
> 用户配置就被留成测试值；
> ② **被真实配置干扰**：用户一旦设了 `api_token`，所有裸请求都 401，
> 整套用例会集体失败 —— 测的是「用户的配置」而不是代码。
> 现在把 `config_persistence._CONFIG_FILE` 重定向到临时文件，
> finally 里还原，并**兜底校验真实配置字节级未变**。

> ✅ 顺带确认了一个**不是 bug 的行为**：设了令牌之后，
> **改配置本身也要带令牌**（不带会 401）。最初我把这当成"令牌切换没生效"，
> 排查后确认是设计正确 —— 记录在此避免下次重复误判。
