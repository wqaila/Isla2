# 2026-11-12 延迟优化、音量调整与代理回退

> 起因：用户反馈「板子从说完话到听到回复有 4~5 秒延迟」，并要求把音量调大。
> 结果：
> - 首块音频延迟 **5106ms → 1685ms（省 3.42 秒，67%）**
> - 默认音量 **60 → 85**
> - 新增代理自动回退，**Clash 没开也能用**（不再报 network_error）
> 涉及：服务端流式 TTS、WebSocket 协议扩展、固件烧录、LLM 网络容错。

---

## 一、延迟到底花在哪

先看日志里一次真实对话的耗时分解：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| ASR 识别 | 约 100 ms | 2% |
| LLM 首字 → 完成 | 约 1200 ms | 24% |
| **TTS 合成** | **约 4800 ms** | **74%** |
| 音频下发 + 板子播放 | 见下 | — |

**TTS 是绝对瓶颈**，而且不是算力问题——RTF 0.6 意味着合成 8 秒音频要 4.8 秒，
这是模型本身的实时率。真正的问题在于**流程是串行的**：

```
说完话
  → ASR（0.1s）
  → LLM（1.2s）
  → TTS 整段合成（4.8s）   ← 这 4.8 秒板子完全静默
  → 才开始下发第一帧
  → 板子开播
```

也就是说，用户等待的是「TTS 把**整段**话合成完」的时间，
而不是「第一句话合成完」的时间。

## 二、改法：流式 TTS

CosyVoice 的 `inference_zero_shot(stream=True)` 会按句切分逐段 yield。
改造后：

```
说完话
  → ASR（0.1s）
  → LLM（1.2s）
  → TTS 首句合成完（约 0.4s）→ 立刻下发 → 板子开播
  → 后续句子在播放期间继续合成、继续下发
```

**实测对比**（34 字文本，8 秒音频）：

| 指标 | 非流式 | 流式 | 改善 |
|---|---|---|---|
| 首块可用 | 5106 ms | **1685 ms** | **省 3422 ms（67%）** |
| 全部完成 | 5106 ms | 6464 ms | 慢 1.4s（但用户已在听） |

「全部完成」变慢了，因为流式多了一些调度开销；但**用户感知的是首块延迟**，
后面的合成与播放并行，不影响体验。

### 实现要点

**1. TTS 服务端新增 `/synthesize_stream`**

传输格式刻意选得简单，不依赖 chunked 语义：

```
每块 = 4 字节大端 uint32 长度 + 该长度的裸 PCM16LE 单声道数据
末尾发长度 = 0 的块表示结束
采样率通过响应头 x-sample-rate 告知
```

不伪造结束标记：如果中途出错就直接断开，调用方会看到「未收到结束标记」
并报错，避免把截断的音频当成完整回复播出去。

**2. 客户端加 `synthesize_stream()`**

采样率必须在读第一块**之前**拿到——因为调用方收到首块就要发 `playback_start`，
里面得带采样率。所以先读响应头再开始迭代。

**3. 协议扩展：`playback_start.frames = 0`**

这是本次唯一动协议的地方。原来板子靠 `frames`（总帧数）判断何时发
`playback_done`；流式下总长度未知，因此：

- `frames = 0` + `streaming = true` 表示流式模式
- 板子改为在收到**负载长度为 0 的二进制帧**时判定收尾
- 旧的定长路径（`frames > 0`）**完整保留**，旧服务端不受影响

**4. 固件配套修改**

| 改动 | 说明 |
|---|---|
| 新增 `s_got_end_marker` | 收到空负载帧时置位 |
| `handle_binary` 增加 `if (plen == 0)` 分支 | 放在帧计数**之前**，否则会被算成多收一帧 |
| 保留 `s_expect_frames` 判断 | 向后兼容旧服务端 |
| 新增 `s_idle_ticks` 兜底 | 流式下 12 秒无数据且无结束标记 → 强制收尾，避免永久卡 `PLAYING` |

## 三、音量

板载扬声器口径小、效率低，默认 60 在安静环境偏轻。

改动：`s_volume` 默认值 **60 → 85**。

留 15 的余量是有原因的——实测 100 时高音量素材会破音（`FAULT` 文档记录过
brownout 也与功放峰值电流有关）。如果觉得仍偏小，可串口临时调：

```
VOL 92     # 更响
VOL 78     # 更稳
```

## 三·补、代理自动回退（Clash 没开也能用）

### 问题

`.env` 里配了 `LLM_PROXY=http://127.0.0.1:7897`（Clash），但 Clash 不常开。
没开时日志是这样的：

```
llm error turn=... attempt=1/3 code=network_error msg=ConnectError: All connection attempts failed
llm retry turn=... in 0.50s
llm error turn=... attempt=2/3 code=network_error
llm retry turn=... in 1.00s
llm error turn=... attempt=3/3 code=network_error
```

三次全失败，用户只看到 `network_error`，但**不知道是代理没开**。

### 关键实测

同一时刻分别测两条线路：

| 线路 | 结果 | 耗时 |
|---|---|---|
| 直连 | **HTTP 401**（401 = 可达，仅需鉴权） | 0.42 s |
| 代理 7897 | ConnectError | 2.23 s |

也就是说：**配了一个「没开就必然失败」的代理，而直连本来是好的。**

### 修复

新增配置项 `LLM_PROXY_FALLBACK`（默认 `true`）：

```ini
LLM_PROXY=http://127.0.0.1:7897
LLM_PROXY_FALLBACK=true
```

行为：

1. 代理连接失败（`network_error` + `ConnectError`）→ 立即切直连重试
2. 切换是**粘性**的：`_proxy_broken` 标记后，本进程内后续轮次直接走直连，
   不再浪费一次尝试去试探一个已知不可用的代理
3. 回退**不消耗** `LLM_MAX_ATTEMPTS` 配额（`retries_done -= 1`），
   否则 3 次尝试里可能没机会真正重试
4. 只在「连接失败」时回退；鉴权失败、限流等错误不回退——
   换线路一样会失败，白白多打一次请求
5. 设为 `false` 可恢复旧行为（严格按 `LLM_PROXY`），适合合规环境

### 验证

Clash 关闭状态下实测：

```
LLM_PROXY          : http://127.0.0.1:7897
LLM_PROXY_FALLBACK : True

WARNING 代理 http://127.0.0.1:7897 连接失败，已自动切换直连
INFO    llm retry turn=fallback-test 立即改用直连重试
INFO    HTTP Request: POST https://api.deepseek.com/chat/completions "HTTP/1.1 200 OK"

[成功] 回复: 我爱你
       首字: 3082ms  总: 3178ms
       实际尝试次数: 1
```

对照组（`LLM_PROXY_FALLBACK=false`）：

```
proxy_fallback = False
[预期失败] LLMNetworkError: [network_error] 网络错误: ConnectError
```

开关确实有效，不是「无论配什么都成功」。

新增 `tests/test_proxy_fallback.py`（13 个用例）。

> 建议：如果所在网络能稳定直连，把 `.env` 的 `LLM_PROXY` 直接留空更省事
> （少一次失败往返）。回退只是兜底，不是首选。

## 五、未验证与遗留

| 项 | 说明 |
|---|---|
| **板子实测延迟** | 本次验证到「服务端首块 1710ms」，板子实际听到声音的延迟需人工掐表确认 |
| **流式下的播放连续性** | 分块下发是否会造成句间可闻断续，需听感确认 |
| **结束标记的固件实测** | 固件已编译烧录，但尚未在真实对话中确认 `收到结束标记帧` 日志 |
| **LLM 延迟** | 本次未优化（占 24%）。若要进一步降，可换更快的模型或缩短回复 |
| **ASR 延迟** | 占 2%，不值得优化 |

### 进一步优化的空间

若还想更快，按性价比排序：

1. **LLM 流式接 TTS**：现在等 LLM 全部生成完才开始 TTS。
   改成 LLM 每出一句就送 TTS，可再省约 1 秒。
   代价：需要处理「句子边界」与「TTS 并发限流」，复杂度明显上升。
2. **缩短回复长度**：`LLM_MAX_TOKENS=128` 已从 256 降过。
   再降到 96 可让回复更短、合成更快，但角色表现会变单薄。
3. **换更小的 TTS 模型**：CosyVoice3-0.5B 已是最小档，无空间。

## 六、回滚方式

固件有问题时刷回备份（三份 16MB 完整备份都在 `zjy13/backup/`）：

```powershell
python -m esptool --chip esp32s3 -p COM7 -b 921600 write_flash `
  --flash_mode dio --flash_freq 80m --flash_size 16MB `
  0x0 zjy13\backup\board_new_fw\full_16MB_newfw_20261101.bin
```

服务端回滚：把 `server/ws/server.py` 里 `synthesize_stream` 改回 `synthesize`，
并恢复 `playback_start` 的 `frames` 计算即可（旧固件与新服务端不兼容，
但新固件同时支持两种模式）。
