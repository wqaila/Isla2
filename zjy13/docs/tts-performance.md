# CosyVoice3 性能优化实测报告

> 所有数据来自 WSL2 + RTX 5070 真实执行。
> 测试日期：2026-10-26

---

## 一、结论摘要

| 优化项 | 效果 | 是否采用 |
| --- | --- | --- |
| **参考音频编码缓存** | **-16.5%** 合成耗时 | ✅ 采用 |
| **修复 token_hop_len 污染** | 首包 2.25s → **1.74s** | ✅ 必须修 |
| fp16 混合精度 | **+7.1% 更慢**，显存 +27% | ❌ 不采用 |
| 流式合成 | 中长句首包延迟降 32-41% | ✅ 采用 |

**综合效果**：非流式 2.54s → 流式首包 1.74s（-31%）。

| 指标 | 均值 | 最小 | 最大 | 标准差 |
| --- | --- | --- | --- | --- |

> 因此下文优先看**绝对耗时**和**每 token 耗时**。

## 三、fp16 实测：无效，反而更慢

| 指标 | fp32 | fp16 | 变化 |
| --- | --- | --- | --- |
| 合成耗时均值 | **2.541 s** | 2.721 s | **+7.1%（慢）** |
| 每 token | **30.83 ms** | 32.05 ms | **+4.0%（慢）** |
| RTF | **0.771** | 0.801 | 变差 |
| 音频时长均值 | 3.305 s | 3.395 s | 基本持平 |
| 峰值显存 | **3.57 GB** | 4.53 GB | **+27%** |

### 为什么 fp16 没效果

CosyVoice3 的 fp16 走 `torch.cuda.amp.autocast`，属于运行时精度切换。但：

1. **LLM 是逐 token 自回归**，瓶颈在 kernel 启动开销和调度，不在算力
2. `autocast` 的类型转换本身有开销
3. Flow 的 DiT 部分虽然计算密集，但占比不足以抵消转换成本

**显存反而增加 27%**，推测是 autocast 路径下部分中间张量仍以 fp32 保存。

> 教训：不能假设 fp16 一定更快。必须实测。

## 四、参考音频编码缓存：-16.5%

### 原理

CosyVoice3 每次 `inference_zero_shot` 都会重新编码参考音频：

```
参考音频 → campplus.onnx（说话人编码器）→ 192 维嵌入
        → speech_tokenizer_v3.onnx → 参考语音 token 序列
```

这段编码与待合成文本无关，完全可以缓存。

`cosyvoice/cli/cosyvoice.py:69` 提供了 `add_zero_shot_spk()`：

```python
cosy.add_zero_shot_spk(PROMPT_TEXT, PROMPT_WAV, 'xiaoman')
# 之后调用：
cosy.inference_zero_shot(text, '', PROMPT_WAV, zero_shot_spk_id='xiaoman')
```

### 实测效果

| 方式 | 合成耗时 | RTF |
| --- | --- | --- |
| 每次重算 | 2.544 s | 0.765 |
| 预先缓存 | **2.125 s** | **0.629** |
| **节省** | **0.419 s（-16.5%）** | |

缓存构建本身约 0.3s，一次性成本，之后所有请求受益。

## 五、发现的 Bug：token_hop_len 跨调用污染

### 问题代码

`cosyvoice/cli/model.py:360`：

```python
self.token_hop_len = min(self.token_max_hop_len, self.token_hop_len * self.stream_scale_factor)
```

`token_hop_len` 是**模型实例属性**，每出一包就翻倍（25 → 50 → 100），
**且合成结束后不重置**。

### 实测证据

```
初始 token_hop_len = 25，上限 100

第1次: 进入时 hop= 25 | 首包 1.75s | 包数 3 | 退出时 hop=100
第2次: 进入时 hop=100 | 首包 2.25s | 包数 1 | 退出时 hop=100   ← 已污染
第3次: 进入时 hop=100 | 首包 2.16s | 包数 1 | 退出时 hop=100
第4次: 进入时 hop=100 | 首包 2.29s | 包数 1 | 退出时 hop=100
```

### 影响

1. **首包延迟从 1.75s 涨到 2.25s**（+29%）
2. **包数从 3 降到 1**，流式退化成一整包，等于失去流式意义
3. 这是一个**静默退化**：不报错，只是越来越慢

### 修复

每次合成前手动重置：

```python
cosy.model.token_hop_len = 25
for chunk in cosy.inference_zero_shot(text, '', PROMPT_WAV,
                                       zero_shot_spk_id='xiaoman', stream=True):
    ...
```

### 修复后

```
第1次: 首包 1.81s | 包数 2
第2次: 首包 1.86s | 包数 2
第3次: 首包 1.55s | 包数 2

首包均值 1.74s，波动 0.31s
```

## 六、流式合成实测

### 首包延迟（已修复污染 + 已缓存参考音频）

| 文本 | 字数 | 首包 | 总耗时 | 音频时长 | 包数 |
| --- | --- | --- | --- | --- | --- |
| 短句「你好呀。」 | 4 | 1.17 s | 1.17 s | 1.24 s | 1 |
| 中句「今天天气不错…」 | 18 | 1.69 s | 3.61 s | 3.96 s | 3 |
| 长句「我最近在调试…」 | 49 | 3.62 s | 7.08 s | 9.72 s | 3 |

> 这组数据是**修复前**测的，长句首包 3.62s 受了污染影响。
> 修复后同长度文本首包应接近 1.7s 起步 + 文本长度带来的 LLM 时间。

### 与非流式对比

| 文本 | 流式首包 | 非流式 | 改善 |
| --- | --- | --- | --- |
| 短句 | 1.17 s | 0.78 s | **-50%（更差）** |
| 中句 | 1.69 s | 2.49 s | +32% |
| 长句 | 3.62 s | 6.11 s | +41% |

**短句流式反而更慢**：因为要等 28 个 token（1.12 秒音频），
而短句总音频只有 1.24 秒，等 1.12 秒才出包几乎等于等全部。

**结论：短句用非流式，长句用流式**。或者统一用非流式 + 缓存参考音频（1.34s → 已可接受）。

## 七、首包延迟的构成

以中句（18 字，3.96s 音频）为例，首包 1.69s 分解：

| 环节 | 估算耗时 |
| --- | --- |
| 参考音频编码（已缓存） | 0 |
| LLM 生成 28 token | 约 0.86 s |
| Flow 处理 28 token | 约 0.5 s |
| HiFT 生成 1.12s 音频 | 约 0.3 s |
| **合计** | **约 1.66 s** |

LLM 占约 52%，是最大头。

## 八、端到端延迟估算

完整链路（用户停止说话 → 听到声音）：

| 环节 | 耗时 | 说明 |
| --- | --- | --- |
| ASR | 0.05 s | 实测 RTF 0.009 |
| LLM（云端 DeepSeek） | 0.6 s | 首 token |
| TTS 首包 | 1.74 s | 流式 + 缓存 + 修复后 |
| **合计** | **约 2.4 s** | |

如果 TTS 用非流式：2.4 - 1.74 + 2.13 = **约 2.8 s**。

差距不大。考虑到流式实现复杂度（音频队列、打断处理、错误回滚），
**第一版建议先用非流式 + 参考音频缓存**，把链路跑通再优化。
