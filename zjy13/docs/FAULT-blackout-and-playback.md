# 故障报告：板子黑屏与语音播放中断

> 记录日期：2026-10-30
> 项目：ESP32-S3 智能角色语音交互系统（`yuanma/AI-Pet-Badge-main` 固件 + `zjy13` 服务端）
> 硬件：Waveshare ESP32-S3-Touch-LCD-1.85B（ESP32-S3R8 / 16MB Flash / 8MB PSRAM / MAC `44:bd:8d:78:14:68`）
> 现象：板子间歇性黑屏，Wi-Fi 随之断开，重新亮屏后自动重连

本文只记录**实际观测到的现象与证据**，并把已确认的原因、已排除的原因、仍未确认的部分分开陈述。

---

## 一、故障现象（用户侧观察）

1. 板子运行中**屏幕会间歇性变黑**。
2. 黑屏同时或随后，**Wi-Fi 断开**。
3. 屏幕恢复后，**Wi-Fi 自动重连**成功。
4. 语音对话过程中，**板子收不到 TTS 音频**，服务端始终等不到 `playback_done`。

---

## 二、已确认的事实（有日志/实测证据）

### 2.1 板子确实发生了自动重启

串口在不主动复位的情况下，抓到了完整的启动日志（从 `PCF85063A initialized` 开始），证明板子曾自行重启。

### 2.2 音频下发与连接关闭发生在同一毫秒

服务端日志呈现固定模式（三个不同轮次均如此）：

```
10:30:02,034  音频已下发 turn=57b2cf3fc722-t85445 帧=94/94 字节=384000
10:30:02,034  连接关闭 session=57b2cf3fc722          ← 同一毫秒

10:39:28,711  音频已下发 turn=688dc424f126-t52122 帧=158/158 字节=643200
10:39:28,711  连接关闭 session=688dc424f126

10:59:03,847  音频已下发 turn=d17cb5f927f7-t28283 帧=105/105 字节=430080
10:59:03,847  连接关闭 session=d17cb5f927f7
```

这说明**不是超时**（超时不会精确到毫秒），而是音频下发瞬间发生的连接级事件。

### 2.3 录音与识别链路本身是通的

同一批失败轮次中，录音与推理完全正常：

```
开始录音 turn=...  fmt=16000 Hz / 16 bit / 2 ch / pcm_s16le / RMNM
录音结束 turn=...  块=146 字节=373760 乱序=0 重复=0
ASR 完成           文本='二零一零二零零零零零...'  耗时=91ms
LLM 完成           首字=848ms 总=1502ms
回复='哎呀，舰长这是在念什么神秘咒语吗？😳'
TTS 完成           音频=14.72s 耗时=8896ms RTF=0.604
```

**上传零丢包、识别成功、爱莉希雅语气正常、语音合成成功** —— 故障只发生在"音频回传播放"这一段。

### 2.4 扬声器与功放硬件本身正常

使用固件自带的 `TONE` 命令（三音测试 523/659/784Hz @16000Hz）实测：

```
ES8311: Work in Slave mode
I2S_IF: STD Mode 1 bits:16/16 channel:2 sample_rate:16000
Adev_Codec: Open codec device OK
重启迹象: 0        ← 播放全程零复位
```

**结论：扬声器、功放、供电在正常播放场景下完全正常。**

### 2.5 Wi-Fi 存在反复重连与热点拒绝

在未连接语音服务的空闲状态下，串口抓到连续失败：

```
I (13668) wifi:Association refused temporarily time 1000, comeback time 1100 (TUs)
W (11368) badge_net: Wi-Fi disconnected, reason 2
W (15797) badge_net: Wi-Fi disconnected, reason 4
W (19090) badge_net: Wi-Fi disconnected, reason 2
```

原因码含义：

| 码 | 含义 |
|---|---|
| 2 | `AUTH_EXPIRE` 认证超时 |
| 4 | `ASSOC_EXPIRE` 关联超时 |
| 201 | `NO_AP_FOUND` 找不到热点 |

`Association refused temporarily` 是**热点侧主动拒绝**，不是板子主动断开。

### 2.6 空闲 5 分钟板子稳定

主动探测（每 10 秒一次 `STATUS`）连续 5 分钟：

```
探测次数: 33
成功: 33
失败: 0
全程无失败 → 板子稳定运行，未黑屏
```

**说明：黑屏不是常态，只在特定条件下触发。**

## 四、代码缺陷（已发现并修复）

排查过程中在自研语音模块 `main/voice_client.c` 中发现并修复了以下缺陷。它们**不是**黑屏的直接原因，但会导致播放链路异常。

### 4.1 录音结束无条件覆盖状态（严重）

```c
// 修复前
esp_codec_dev_close(s_mic);
s_state = ST_IDLE;          // 无条件赋值

// 修复后
esp_codec_dev_close(s_mic);
if (s_state == ST_RECORDING) { s_state = ST_IDLE; ui_sync(); }
```

**后果**：若服务端回复很快、已进入 `ST_PLAYING`，录音任务的收尾会把播放状态强行改回 `IDLE`，导致 `playback_done` 不上报、状态机错乱。

### 4.2 录音时误初始化扬声器

```c
// 修复前：录音时把麦克风和扬声器一起初始化
s_mic = bsp_audio_codec_microphone_init();
s_spk = bsp_audio_codec_speaker_init();   // ← 不必要

// 修复后：按需初始化
static esp_err_t mic_ensure(void);   // 录音只开麦克风
static esp_err_t spk_ensure(void);   // 播放只开扬声器
```

**后果**：每次 `TALK` 都会唤醒 ES8311 功放（日志中 `TALK` 时出现 `ES8311: Work in Slave mode` 即为证据），在供电本就紧张时白耗电流。

### 4.3 采样率与原厂验证值不一致

```c
// 修复前
#define MIC_SAMPLE_RATE 22050     // BSP 默认值
#define SPK_DEV_RATE    22050

// 修复后
#define MIC_SAMPLE_RATE 16000     // 对齐原厂 TONE 命令
#define SPK_DEV_RATE    16000
```

**依据**：原厂 `TONE` 用 16000Hz 播放零复位；22050 在实测中从未成功过。16000 也是 ASR 的目标采样率，服务端无需重采样。

### 4.4 WebSocket 传输层未显式指定

```c
// 修复前：transport 默认为 WEBSOCKET_TRANSPORT_UNKNOWN(0)
// 组件内部只判断 OVER_TCP(1)/OVER_SSL(2)，UNKNOWN 落入 else 分支被当作 SSL
// 结果明文 ws:// 也走 TLS 握手，报：
//   ESP_ERR_ESP_TLS_FAILED_CONNECT_TO_HOST, errno=118

// 修复后
.transport = WEBSOCKET_TRANSPORT_OVER_TCP,
```

### 4.5 缺少心跳

服务端 `HEARTBEAT_TIMEOUT_S = 30`，客户端每 20 秒需发心跳。原实现完全没有心跳，连接在约 29 秒后被断开，表现为"刚连上能握手，过一会儿 `TALK` 就返回 false"。已补 20 秒周期心跳任务。

### 4.6 播放写入阻塞网络回调

原实现直接在 WebSocket DATA 回调里调 `esp_codec_dev_write()`，133 帧约 11 秒，期间收不到后续帧、发不出心跳。已重构为：回调只入环形缓冲，独立 `play_task` 负责写 codec 并做 24k→16k 重采样。

## 五、当前最可能的原因（尚未最终证实）

综合 2.2、2.5、2.6：

**最可能的因果链**：

```
手机热点侧拒绝/超时（reason 2 / 4）
   → 板子进入 Wi-Fi 重连循环（射频反复上电、电流尖峰）
   → 瞬时电压跌落
   → 背光闪断（黑屏）+ 芯片复位
   → WebSocket 连接在同一毫秒断开
```

支持这一判断的证据：

1. **音频下发与连接关闭同一毫秒** —— 若是播放本身耗电导致，通常会先有若干帧成功、再断开，而不是精确同时。
2. **`TONE` 播放零复位** —— 说明单纯的音频播放不会触发掉电。
3. **热点返回 `Association refused temporarily`** —— 热点侧存在主动拒绝行为。
4. **空闲 5 分钟稳定** —— 无射频重连时不会黑屏。

**但仍有未解释的部分**：为什么断开总是恰好发生在音频下发时刻，而不是任意时刻。这一点目前没有直接证据。

## 六、已尝试的缓解措施与结果

| 措施 | 内容 | 结果 |
|---|---|---|
| 降低音量 | 60 → 30 | ❌ 仍复位 |
| 播放软启动 | 开功放后先写 150ms 静音 | ❌ 仍复位 |
| 关闭前淡出 | 关功放前写 80ms 静音 + 延时 | ❌ 仍复位 |
| 关闭 brownout 检测 | `CONFIG_ESP_BROWNOUT_DET` = n | ⚠️ 复位原因从 `0xC BROWN_OUT` 变为不再出现 brownout 复位，但连接仍在音频时刻断开 |
| 换 USB 口 | 前面板 → 主板后置 USB 3.0 | ⚠️ 有改善（空闲 5 分钟零失败），未根治 |

**关于 brownout 配置的说明**（来自 IDF 5.5.5 `Kconfig.power`）：

- 电平 7 对应 **2.44V**（最低档，即最不敏感）
- `ESP_BROWNOUT_USE_INTR` 的官方说明：检测到掉电后，**默认回调末尾仍会执行软件重启**
- 因此关闭 INTR 不等于避免复位，只有 `CONFIG_ESP_BROWNOUT_DET=n` 才是真正关闭检测

## 九、结论

1. **语音链路的软件部分已全部打通**：录音上传零丢包、ASR/LLM/TTS 全部成功、爱莉希雅音色正常。
2. **扬声器硬件正常**：`TONE` 测试零复位。
3. **黑屏与 Wi-Fi 重连高度相关**：热点侧返回 `reason 2/4` 与 `Association refused temporarily`，板子进入重连循环。
4. **播放中断是连接断开的伴生现象**，不是独立故障。
5. **尚未彻底解决**，最可能指向热点稳定性与供电裕量，需通过更换热点/供电条件来验证。
