## 二、成果（按模块分类）

### 2.1 网络：改为主机热点直连

- 主机新增无线网卡 **Realtek 8851BU（WiFi 6 USB）**，用它开 Windows 移动热点，板子直接连主机。
- 通过 WinRT `NetworkOperatorTetheringManager` 以程序方式配置并启动热点：

  ```powershell
  $mgr = [Windows.Networking.NetworkOperators.NetworkOperatorTetheringManager]::CreateFromConnectionProfile($prof)
  $cfg = New-Object Windows.Networking.NetworkOperators.NetworkOperatorTetheringAccessPointConfiguration
  $cfg.Ssid = 'Isla2Badge'
  $cfg.Passphrase = 'isla2badge2026'
  $cfg.Band = [Windows.Networking.NetworkOperators.TetheringWiFiBand]::TwoPointFourGigahertz
  $null = $mgr.ConfigureAccessPointAsync($cfg)
  $null = $mgr.StartTetheringAsync()
  ```

- 关键参数：

  | 项 | 值 |
  | --- | --- |
  | SSID / 密码 | `Isla2Badge` / `isla2badge2026` |
  | 频段 | **强制 2.4GHz** |
  | 主机地址（ICS 固定网关） | `192.168.137.1` |
  | 板子地址 | `192.168.137.174` |

- **收益**：`192.168.137.1` 是 Windows ICS 固定网关，彻底消除了"换热点后 IP 漂移"的隐患，也为开机自动连接提供了固定目标。

### 2.2 固件：开机自动连接服务端

- `wifi_config.h` 新增自动连接配置（该文件本地私有、已被 `.gitignore` 排除）：

  ```c
  #define BADGE_VOICE_AUTOCONNECT_HOST "192.168.137.1"
  #define BADGE_VOICE_AUTOCONNECT_PORT 8765
  ```

- `badge_network.c` 的网络任务中：已联网且 `voice_is_started()` 为假时自动 `voice_start`，失败每 5 秒重试；WiFi 断开时重置计时。
- `voice_client` 新增 `voice_is_started()`，保证自动逻辑不会干扰手动 `VOICE <ip>` 命令。
- **实测**：WiFi 拿到 IP 后 **18ms** 自动连上，`server_hello` 正常，全程未发任何串口命令。

### 2.3 音质：改为 24kHz 直通播放（当天最重要的修复）

- `SPK_DEV_RATE` 由 `16000` 改为与 `SPK_SAMPLE_RATE` 相同的 **24000**，播放任务直接写出、不再重采样。
- **采样率正确性验证**：TTS 生成 10.32s 音频，板子实际 `PLAYING` 窗口 10.40s，**比值 1.01**。
- 同时回收三处过度分配的静态缓冲（详见 3.3），内部 RAM 净增 28.7KB。

### 2.4 交互与可用性

| 功能 | 实现 |
| --- | --- |
| 音量上屏 | 新增 `badge_dashboard_volume()`，语音状态行显示为「语音待命 60」；`VOL` 改音量后 100ms 内刷新 |
| 音量命令 | `VOL`（查询）/ `VOL 75`（设置 0~100），默认 60 |
| 长按说话 | 长按屏幕说话、松开发送；阈值从 LVGL 默认 400ms 调到 **300ms** |
| 短按保留 | 短按仍是动画切换，不与录音冲突 |

### 2.5 服务端：音频下发节流

- 下发循环由"全速推送"改为**按播放进度节流**（允许领先播放进度 2 秒），峰值带宽降到约 1/8。
- 配合板子播放缓冲从 20 秒缩到 8 秒。

## 三、修复的 Bug（按类型分类）

### 3.1 通信类

#### Bug 1：录音上传只传 3 块就断（WiFi 省电导致）

| 项 | 内容 |
| --- | --- |
| **现象** | 录音 3.5 秒应收约 87 块音频，实际只上传 **3 块**即断线；串口报 `transport_poll_write(0)` / `esp_transport_write() returned 0` |
| **根因** | ESP32 默认开启 WiFi 省电（`WIFI_PS_MIN_MODEM`），在 Windows 移动热点（WiFi Direct）下上行发送被挂起；手机热点下则不触发 |
| **修复** | `esp_wifi_start()` 后调用 `esp_wifi_set_ps(WIFI_PS_NONE)` |
| **验证** | 上传恢复 **68~72 块**，transport 错误 **0 次** |

#### Bug 2：16 秒以上长音频下发必断连

| 项 | 内容 |
| --- | --- |
| **现象** | 长音频（16s / 约 780KB）下发瞬间 `transport_poll_write` 超时 → 断连 → 服务端「轮次被取消」 |
| **根因** | 服务端 `for off in range(...): await send_audio(...)` 无节流全速推送，几秒内灌满 WiFi Direct 链路 |
| **修复** | ① 下发按播放进度节流（`lead_sec = 2.0`）；② 板子播放缓冲 20s→8s |
| **验证** | 连续 5 轮（含 16.08s 音频）**0 崩溃、0 transport 错误、0 下发失败** |

### 3.2 崩溃类

#### Bug 3：`record_loop` 返回路径 `retw.n` 崩溃

| 项 | 内容 |
| --- | --- |
| **现象** | `TALK STOP` 后 `IllegalInstruction`，PC 落在 `record_loop` 结尾，返回地址寄存器 `A0 = 0` |
| **排查** | 用 `addr2line` 反查地址；加日志测得 `stack_hwm=5840`，把栈 4096→8192 仍崩，**排除栈溢出** |
| **修复** | 任务末尾显式 `vTaskDelete(NULL)` 绕开异常返回路径；并清理 `s_task` 悬空句柄（任务自删后句柄未置空，下一轮 `vTaskDelete(s_task)` 命中已释放 TCB） |
| **验证** | 连续多轮 0 崩溃 |

#### Bug 4：`record_loop` 退出时缺失 UI 同步

| 项 | 内容 |
| --- | --- |
| **现象** | 录音结束后屏幕状态不立即回"待命"，要等下一轮消息才更新 |
| **原因** | 排查 Bug 3 期间把 `ui_sync()` 移除了，未恢复 |
| **修复** | 改为调用 `badge_dashboard_voice(2)`（不经过 `ui_sync()` 的 switch 内联路径），并放在 `esp_codec_dev_close()` 之前，远离函数尾部 |
| **验证** | 3 轮 0 崩溃 |

### 3.3 音质类

#### Bug 5：音色失真（三处叠加）

| 项 | 内容 |
| --- | --- |
| **现象** | 使用者反馈"音色有一点点不像" |
| **根因 1** | TTS 输出 24kHz，设备按 **16kHz** 播放，做 24k→16k 降采样 → **8~12kHz 频段被整体丢弃**，声音发闷、缺高频细节 |
| **根因 2** | 降采样用的是**裸线性插值，无抗混叠滤波** → 8kHz 以上内容折返成谐波失真，听感发毛 |
| **根因 3** | 重采样相位**每块重置**（`src = i * 24000/16000` 从 i=0 重算）→ 每约 43ms 一个断点，周期性毛刺 |
| **修复** | `SPK_DEV_RATE` 改为 24000，直接写出、零重采样 |
| **附带收益** | 删除 `resamp`、缩小 `out_buf`/`softstart`/`fadeout`，内部 RAM 净增 28.7KB |

### 3.4 显示类

#### Bug 6：LCD `ESP_ERR_NO_MEM` 刷屏（内存被自家缓冲挤占）

| 项 | 内容 |
| --- | --- |
| **现象** | 播放期间串口刷屏：`spi_master: Failed to allocate priv TX buffer` / `st77916_spi: send color data failed` / `ESP_ERR_NO_MEM`，每轮 21~42 次 |
| **根因** | `play_task` 的 `out_buf`（16KB）、`softstart`（7.2KB）、`fadeout`（3.8KB）、`resamp`（2KB）静态占用约 29KB **内部 RAM**，挤压了 LCD 的 SPI DMA 所需的 DMA-capable 内存 |
| **修复** | 三个缓冲改为固定 1024 采样（各 2KB），删除 `resamp` |
| **验证** | 内部可用 **50.4KB → 79.2KB**，LCD 报错 **降为 0** |

> 注：这条最初被我误判为"第三方 BSP/LVGL 的 SPI DMA 竞争、属已知限制"，实际是自家缓冲过度分配。见第四节「判断错误」。

### 3.5 服务端配置

#### Bug 7：LLM 回复过长导致长音频

| 项 | 内容 |
| --- | --- |
| **现象** | 爱莉希雅偶发长篇回复，合成长达 17 秒音频，加重链路压力 |
| **根因** | `.env` 中 `LLM_MAX_TOKENS=256`（约 170 汉字），而角色卡本身要求"以短句为主，一句不超过 30 字" |
| **修复** | 降为 `LLM_MAX_TOKENS=128`（约 85 汉字 / 3 句） |
| **遗留** | 128 token 仍可能产生约 17s 音频（中文 TTS 约 5 字/秒），**单靠降 token 不足以解决**，必须配合下发节流（Bug 2） |

## 四、遇到的问题与走过的弯路（含判断错误）

1. **移动热点默认选 5GHz，板子扫不到**
   首次连主机热点，板子持续报 `reason 201`（NO_AP_FOUND）。一开始怀疑 SSID/密码写错，实际是热点默认 `Band = Auto` 选到了 5GHz，而 **ESP32 只支持 2.4GHz**。强制 `TwoPointFourGigahertz` 后立刻连上。

2. **把 LCD 报错误判为第三方 BSP 缺陷**
   先入为主认定为"BSP/LVGL 的 SPI DMA 竞争、属已知限制、不建议改"，还据此写了"已知限制"文档。后来顺着内部内存变化追查，才发现是自家三个静态缓冲超配。**这是当天最主要的判断错误**，已改正并撤回原结论。

3. **尝试"播放时暂停动画重绘"——无效且负优化**
   为消除 LCD 报错，加了"播放期间跳过角色重绘"。实测报错数没有下降（仍 21~42 次/轮），而且角色在说话时僵住不动。已回滚，真正的解法是缩小缓冲（见 Bug 6）。

4. **测量播放时长的方法写错，差点误判采样率**
   服务端改为节流后，"音频已下发"日志出现在**发送完成之后**，我按"看到该日志再开始计时"测出的播放时长只有 2.8s（实际 12.76s），得出错误的"比值 0.22"。改为持续轮询 `PLAYING` 状态窗口后才得到正确结果（比值 1.01）。

5. **`git push` 报 TLS 错误**
   `TLS connect error: unexpected eof while reading`。原因是 **git 全局配置残留 `http.proxy = http://127.0.0.1:7897`**（此前会话留下），而当时 Clash 代理状态异常。改用 SSH remote 推送成功。
   如要改回 HTTPS，需先 `git config --global --unset http.proxy`。

6. **板子卡在 `PLAYING` 状态不退出**
   上一轮连接中断后，播放任务在等缓冲排空而不退出，状态机停在 `PLAYING`，导致后续 `TALK` 返回 false。用 `VOICE STOP` 可复位，再 `VOICE <ip>` 重连。
   （属断连后的状态残留，未做自动恢复）

7. **DeepSeek 直连被墙**
   `api.deepseek.com` 直连超时，但百度、open-meteo 均正常。必须走 Clash 代理（`LLM_PROXY=http://127.0.0.1:7897`）。
   验证方法：`Invoke-WebRequest https://api.deepseek.com -Proxy http://127.0.0.1:7897` 返回 **401** 即表示网络可达（401 属正常，仅表示需鉴权）。

## 五、已知限制与未解决

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | **扬声器物理限制** | 板载扬声器口径小，约 300Hz 以下低频基本没有，解析力与动态范围有限，高音量易破音。软件已做到"无损直通"，剩余差距属硬件天花板 |
| 2 | **音色克隆本身的上限** | 当前参考音频为 9.70s 素材（`ref_elysia.wav`），克隆相似度受素材质量与长度限制。若要更接近，需换更长/更干净的参考音频重新克隆 |
| 3 | **断连后状态残留** | 若在播放中连接中断，板子可能停在 `PLAYING`，需 `VOICE STOP` 复位，未做自动恢复 |
| 4 | **云端配对方案（B）** | 已判定弃用：云端要求邮箱登录，且「电脑工作端」实现不在本仓库 |
| 5 | **LCD 长时间稳定性** | 报错已降为 0，但仍需长时间运行观察 |
| 6 | **长音频仍受链路约束** | 节流后 16s 音频可稳定播放，但更长音频（>20s）未做压测 |
