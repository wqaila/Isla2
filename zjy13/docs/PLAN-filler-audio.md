# 实现方案：填充音（三轮换 · 只改服务端 · 追求自然）

> 依据用户决策：**三个轮换**、**只改服务端**、**长度要自然（像日常对话）**
> 状态：设计定稿，待实施

---

## 一、先纠正我上一版方案的错误

上一版我建议「用拖长版填充音 `嗯——`（1.8~2.5 秒）」。实测推翻了它：

```
嗯——   生成结果只有 0.28 秒
```

wetext 把破折号规范化掉了，**TTS 根本无法生成"拖长音"**。
而且真人说话也不会拖长一个语气词。

**真实对话是这样的**：

```
你：你觉得这个怎么样？
我：嗯……（0.6s）这个嘛……（1.2s）我觉得还行
```

是**短促的多个语气词连起来**，不是拖长一个音。这恰好能覆盖等待，
而且听起来自然。

**所以正确做法：短填充音 + 按需连续播 2~3 个。**

### 两个必须处理的发现

**发现 1：TTS 输出自带首尾静音，最多 0.35 秒**

`um_soft` 开头有 0.35 秒静音。如果直接播，用户先听到 0.35 秒静音
才听到「嗯」——**恰好抵消了填充音的作用**。

必须裁剪：去掉首尾静音，只保留有效语音。

**发现 2：`嗯——` 只有 0.28 秒**

破折号被规范化掉了。这也证明「拖长音」思路不可行。

## 三、选定三个填充音

按「自然、互补、覆盖不同情绪」来选：

| 序号 | 文本 | 有效时长 | 用在什么场景 |
|---|---|---|---|
| 1 | **嗯…** | 0.58s | 通用思考，最中性 |
| 2 | **这个嘛…** | 0.86s | 被问到需要斟酌的问题 |
| 3 | **唔…** | 0.49s | 有点为难/不确定 |

**为什么这三个**：
- 都是日常对话高频语气词，不突兀
- 时长互补（0.49 / 0.58 / 0.86），可按等待时长选
- 音色是爱莉希雅克隆，与正文同源
- 避开「嗯哼~」——那是角色招牌口头禅，角色卡明确要求「不能每句都用」，
  拿它做固定填充会退化成模板化

## 四、核心逻辑：按等待时长动态拼接

### 4.1 时序

```
T0     板子收到 recording_stop（音频上传完毕）
T0+?   服务端开始 ASR
        ↓
        同时：立刻下发填充音 1（约 50ms 后板子开始播）
        ↓
        ASR 完成（约 100ms）→ LLM（约 600~900ms）→ TTS 首块（约 1500ms）
        ↓
        正文音频开始到达 → 若填充音还没播完，淡出切入
```

### 4.2 关键：填充音要「够长但不冗余」

三种策略，按等待时长自适应：

| 等待时长 | 播几个 | 总时长 | 例子 |
|---|---|---|---|
| < 0.8s | 1 个短的 | 0.5s | `嗯…` |
| 0.8~1.6s | 1 个长的 | 0.86s | `这个嘛…` |
| 1.6~2.4s | 2 个 | 1.44s | `嗯…` + `这个嘛…` |
| > 2.4s | 3 个 | 1.93s | `嗯…` + `这个嘛…` + `唔…` |

**但服务端无法预知等待多久**（LLM/TTS 耗时波动大）。

**解法：不预判，边播边补。**

```
1. 立刻发第一个填充音（随机选，约 0.5~0.9s）
2. 若正文还没到，再发第二个
3. 若还没到，发第三个
4. 正文一到，立刻发「停止标记」，板子淡出填充音
```

这样**永远不会播多**（正文到了就停），也**不会播空**（没到就继续补）。

### 4.3 板子侧需要的能力（复用现有流式）

好消息：**现有流式播放协议刚好够用**，不需要新协议。

```
playback_start (frames=0, streaming=true)   ← 已有
  ↓
音频帧 × N（填充音 PCM）                     ← 已有
  ↓
（若正文到了）
音频帧 × M（正文 PCM，无缝接在后面）          ← 已有
  ↓
结束标记帧（负载 0）                          ← 已有
```

**关键**：填充音和正文用**同一个 playback_start 会话**，
中间不插入新的 playback_start，板子就会把两段 PCM 当成连续音频播。

**唯一需要确认**：板子的 `s_prebuf_done` 预缓冲逻辑。
填充音只有 0.5 秒，若预缓冲要 120ms，第一次开播会等 120ms 才出声。
但填充音总长 0.5s > 120ms，够触发预缓冲，没问题。

### 4.4 淡出切换

填充音播到一半正文到了，直接切会突兀（像被掐断）。

**做法**：在填充音 PCM 末尾做 80ms 淡出，正文开头 40ms 淡入。

但流式下服务端不知道"正文什么时候到"，无法提前给填充音加淡出。

**解法**：填充音本身在生成时就带淡出尾（音频处理时加），
即使播完整也不会突兀；若中途被切断，因为音量已在下降段，也不明显。

## 五、实现步骤

### 步骤 1：准备填充音资源（一次性）

```python
# 用 TTS 生成 → 裁掉首尾静音 → 加淡入淡出 → 存为 raw PCM
for text in ["嗯…", "这个嘛…", "唔…"]:
    wav = tts.synthesize(text, voice_id="elysia")
    pcm = trim_silence(wav)        # 去掉首尾静音
    pcm = apply_fade(pcm, 10, 80)  # 10ms 淡入，80ms 淡出
    save_pcm(pcm, f"filler_{i}.pcm")
```

产物：3 个 PCM 文件，合计约 **45KB**（0.58+0.86+0.49 秒 × 48000 B/s）。

### 步骤 3：接入 `_run_pipeline`

在 `_run_pipeline` 里，ASR 开始**之前**插入：

```python
# 立刻下发填充音，覆盖后续等待
filler_task = asyncio.create_task(
    self._send_fillers(client, my_turn)
)
try:
    ... ASR / LLM / TTS ...
finally:
    filler_task.cancel()
```

`_send_fillers` 逻辑：

```python
async def _send_fillers(self, client, my_turn):
    """边播边补：正文一到就停。"""
    await self._start_playback(client, my_turn)   # 发 playback_start(frames=0)
    sent = 0
    while not self._body_ready.is_set():
        clip = self.fillers.pick()
        await self._send_pcm(client, clip)
        sent += len(clip)
        if sent > MAX_FILLER_BYTES:      # 兜底上限（如 3 秒）
            break
        await asyncio.sleep(0.05)
```

正文 TTS 首块到达时，`_body_ready.set()`，然后**接着同一个 playback_start 继续发正文 PCM**。

### 步骤 4：边界情况

| 情况 | 处理 |
|---|---|
| ASR 失败（没听清） | 仍然播填充音，然后播「没听清」的错误提示音（或直接让 LLM 处理） |
| LLM 失败 | 填充音已播，正常发 error 让板子显示 |
| 用户取消 | 立刻停填充音（现有 `_on_cancel` 已有此能力） |
| 填充音播放中用户又按下 | 现有逻辑会 `turn_busy` 拒绝；建议改为「允许打断」 |
| 极快响应（<0.5s） | 填充音刚播 0.1 秒正文就到了，淡出切入（略突兀但可接受） |

## 七、风险与代价

| 风险 | 说明 | 缓解 |
|---|---|---|
| **音色不连贯** | 填充音与正文都是 TTS 生成，理论上一致；但填充音是预生成的，正文是实时合成的，可能有细微差异 | 用同一 voice_id、同一 speed 生成 |
| **重复感** | 三个轮换仍可能听出规律 | 避免连续两次相同 + 按等待时长选不同长度 |
| **打断体验** | 若正文突然插入，填充音被硬切 | 填充音自带 80ms 淡出尾 |
| **增加首包数据量** | 多传 45KB | 可忽略（正文通常 300KB+） |
| **首次响应变"啰嗦"** | 如果 LLM 很快（<0.5s），填充音显得多余 | 可设阈值：若历史平均延迟 < 1s 则跳过填充音 |

## 八、需要你确认

1. **三个填充音选得对吗？**
   我选的是「嗯…」「这个嘛…」「唔…」。
   备选：「诶？」「啊，」「让我想想…」。
   如果你觉得某个更符合爱莉的语气，告诉我换掉。

2. **要不要「延迟自适应」？**
   若上一轮实测延迟很短（<1 秒），是否跳过填充音？
   - 跳过：更快进入正文，但偶发长延迟时会突兀
   - 不跳过：一致性好，但快响应时略显啰嗦

3. **打断行为**
   填充音播放期间用户再按屏幕，是：
   - 拒绝（现状，`turn_busy`）
   - 允许打断（体验更好，但要改服务端状态机）
