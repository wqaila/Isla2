# 方案：先说「嗯」「这个嘛」等填充音，降低感知延迟

> 提出者：用户
> 目标：板子在收到语音后**立刻**先播一个短促的语气词，再衔接正式回复，
> 让用户感觉「反应很快」。
> 状态：**方案设计，未实施**

---

## 一、当前延迟构成

一次完整交互的时间轴（实测数据）：

```
用户松手
  │
  ├─ 上传音频 + 服务端 ASR            ~100 ms
  ├─ LLM 首字                         ~600~900 ms
  ├─ TTS 首块（流式）                 ~1500~1700 ms
  ├─ 下发 + 板子预缓冲                ~120 ms
  └─ 开始出声
                                     ─────────────
  合计                               约 2.3~2.8 秒
```

**用户感知到的「沉默」主要来自 LLM + TTS 首块，约 2.1~2.6 秒。**

填充音能覆盖的正是这段沉默。

---

## 二、核心思路与三种实现路径

| 方案 | 做法 | 填充音延迟 | 改动量 | 风险 |
|---|---|---|---|---|
| **A. 板子本地预存** | 把「嗯」「这个嘛」的音频烧进固件/SPIFFS，松手即播 | **~0 ms** | 中 | 低 |
| **B. 服务端预合成缓存** | 服务端启动时把填充音合成好缓存，收到 `recording_stop` 立刻下发 | ~50~100 ms | 小 | 低 |
| **C. 让 LLM 以填充词开头** | 改角色卡，要求回复以「嗯」「这个嘛」起手 | 不改善（仍要等 LLM） | 极小 | **违背角色卡约束** |

### 推荐：**A + B 组合**

- **A** 负责「0 延迟」的即时反馈（松手瞬间就有声音）
- **B** 负责音色一致（本地预存是固定录音，与爱莉希雅克隆音色不同）

但**先做 A 就够了**——因为 B 的 50~100ms 相比 2.3 秒可忽略，
且 B 需要处理「填充音与正式音频的无缝衔接」，复杂度高。

**建议：第一版只做 A。**

---

## 三、方案 A 详细设计

### 3.1 音频从哪来

填充音必须是**爱莉希雅的声音**，否则前后音色不一致，反而更假。

三个来源，按推荐度：

| 来源 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **用现有 TTS 生成** | 用 CosyVoice 合成「嗯」「这个嘛」「唔…」，导出 WAV | 音色完全一致 | 需要一次性操作 |
| 从原始素材剪 | 从 21 分钟角色语音里剪出语气词 | 最自然（真人） | 要人工挑选 |
| 板子合成正弦音 | 像 `diagnostic_tone()` 那样 | 零成本 | **不像人声，绝对不可用** |

**推荐第一种**：用现有 TTS 服务生成，音色与正式回复同源。

```bash
# 在 WSL 里跑，导出到 Windows
curl -X POST http://127.0.0.1:50000/synthesize \
  -H "Content-Type: application/json" \
  -d '{"text":"嗯","voice_id":"elysia","speed":1.0}' \
  -o /mnt/d/xiangmudaima/zjy13/firmware/.../filler_um.wav
```

需要生成的候选（8~10 个）：

| 文本 | 用途 | 时长 |
|---|---|---|
| 嗯 | 通用思考 | ~0.3s |
| 嗯哼 | 角色招牌（爱莉常用） | ~0.5s |
| 这个嘛 | 思考/犹豫 | ~0.6s |
| 唔… | 为难/困惑 | ~0.5s |
| 诶？ | 意外 | ~0.4s |
| 让我想想 | 明显思考 | ~0.9s |
| 呀 | 惊讶/开心 | ~0.3s |

### 3.2 存在哪

**关键约束**：app 分区已用 8.5 / 9 MB，**只剩 0.5 MB**。

但 `model` 分区（SPIFFS，5168K）**当前完全没被使用**——固件代码里搜不到任何
`spiffs` / `model` 引用。这是理想的存放位置。

| 方案 | 容量 | 改动 |
|---|---|---|
| **存 SPIFFS（model 分区）** | 5 MB 可用 | 需加 SPIFFS 挂载代码 |
| 编进固件（C 数组） | 只剩 0.5MB | 8 个短音约 8×20KB=160KB，**塞得下** |
| 存 SD 卡 | 看卡 | 板子不一定插卡 |

**推荐：编进固件**。理由：
- 8 个填充音按 24kHz/16bit/0.6s ≈ 29KB each，合计约 230KB，0.5MB 够用
- 无需 SPIFFS 挂载，代码最简单，启动即可用
- 缺点：以后要换填充音得重烧固件（可接受，因为不常改）

> 若担心 0.5MB 余量，可先只做 3 个最常用的（嗯/嗯哼/这个嘛），约 90KB。

### 3.3 什么时候播

**关键设计点：播完填充音后，正式音频不能从头开始，要「接上」。**

两种策略：

**策略 1：填充音独立播放，正式音频稍后开始（简单）**

```
松手 → 立刻播「嗯」(0.4s) → 静音等待正式音频 → 播正式音频
```

问题：如果正式音频 2.3 秒后才到，「嗯」播完还有 1.9 秒沉默，
**填充音反而放大了沉默感**。

**策略 2：填充音作为「引子」，正式音频紧随（推荐）**

```
松手 → 等正式音频就绪（约 1.7s）→ 先播「嗯」(0.4s) → 无缝接正式音频
```

这样总时长不变，但**用户听到的第一个声音是「嗯」而不是直接开始念正文**，
听感更自然（像人在思考后开口）。

**但这样并不能降低感知延迟**——因为「嗯」也要等 1.7 秒才播。

### 3.4 真正能降感知延迟的做法

要让「嗯」在**松手后立刻**响，必须：

```
松手（T0）
  ├─ T0+50ms   板子立刻播「嗯」（本地预存，不等网络）
  └─ T0+2300ms 正式音频到达 → 播正文
```

**问题**：「嗯」0.4 秒就播完了，然后还有 1.9 秒沉默。
用户会听到「嗯……（长沉默）……正文」，**比不播更奇怪**。

**所以必须配合「拖长填充音」或「连续填充」**：

| 做法 | 说明 |
|---|---|
| **拖长版填充音** | 「嗯——」（1.5~2 秒的长音），覆盖大部分等待 |
| **连续短填充** | 「嗯…这个嘛…」（多个拼接），按需播 2~3 个 |
| **循环低音** | 像「哼唱」一样的持续音，正式音频到达即切掉 |

**推荐：拖长版 + 可中断**

```
松手 → 立刻播「嗯——」（长 2.5 秒，带淡出）
         ↓
    正式音频到达（约 2.3s）→ 立刻淡出填充音，无缝切正文
```

这样：**0 延迟有声音反馈**，且填充音刚好被正式音频接上。

### 3.5 完整时序（推荐设计）

```
T0     用户松手
T0+0   板子立刻开始播「嗯——」（本地，2.5s 长，循环或长音）
T0+100 ASR 完成
T0+900 LLM 完成
T0+1700 TTS 首块到达 → 服务端发 playback_start
T0+1700 板子收到 playback_start → 填充音开始淡出（100ms 淡出）
T0+1800 正文开始播放
```

用户听到：`嗯——（约 1.8 秒）→ 正文`，中间无静默。

### 3.6 技术难点

| 难点 | 说明 | 解法 |
|---|---|---|
| **单 I2S 半双工** | 录音与播放共用 I2S，松手后才能播 | 松手 → `esp_codec_dev_close(mic)` → 开 speaker，已有流程 |
| **播放任务抢占** | 填充音与正式音频都走 `play_task` | 填充音用**独立的任务/标志**，正式音频到达时置标志让填充音淡出 |
| **无缝切换** | 突然切会爆音 | 填充音淡出 100ms，正文淡入 50ms（现有 `softstart` 已有类似逻辑） |
| **可中断** | 用户可能马上又说一句 | 长按录音时立刻停填充音 |
| **音色一致** | 填充音必须用克隆音色 | 用现有 TTS 生成 |

## 四、方案 B（服务端预合成）作为补充

如果不想动固件，可以只改服务端：

```
服务端启动时：
  合成「嗯」「这个嘛」「唔…」并缓存为 PCM

收到 recording_stop 后：
  立刻下发缓存的填充音（用现有的流式协议，frames=0）
  → 同时并行跑 ASR + LLM + TTS
  → TTS 首块到达后，继续下发正文
```

**优点**：零固件改动，音色天然一致。

**缺点**：
- 填充音要等 `recording_stop` 上传到服务端（约 50~100ms），不是 0 延迟
- 需要处理「填充音与正文的 PCM 拼接」，且正文是流式的，拼接点难对齐
- 板子侧仍要能「边收边播」，即现有的流式播放能力——**已具备**

**实际收益**：约 100ms 的即时反馈 + 覆盖后续 1.6 秒沉默。

**但要覆盖 1.6 秒沉默，填充音得足够长**，同样需要「拖长版」。

## 五、我的建议

### 分两步走

**第一步（改动小、收益明确）：服务端方案 B 的简化版**

1. 用 TTS 生成 3 个填充音：「嗯——」（1.8s 长音）、「这个嘛」（0.8s）、「唔…」（0.8s）
2. 服务端启动时预合成并缓存为 PCM
3. 收到 `recording_stop` 立刻下发一个填充音（按 LLM 首字延迟选长的还是短的）
4. 正文到达后无缝接上

**预期效果**：松手后约 **100ms** 就有声音（原来 2.3 秒），
配合 1.8 秒长音可完整覆盖等待。

**第二步（可选）：固件本地播放，做到真 0 延迟**

把同样 3 个音频编进固件，松手即播，彻底不等网络。

### 不建议做的事

| 做法 | 原因 |
|---|---|
| 让 LLM 回复以「嗯」开头 | 角色卡已明确禁止模板化开头（`catchphrase_usage`），会退化成每句都以「嗯」起手 |
| 用板子合成正弦音 | 不像人声，会显得很假 |
| 只播 0.4 秒短填充 | 会放大沉默感，比不播更差 |

## 六、需要你确认的三个问题

1. **填充音用哪种？**
   - 只用「嗯——」一个长音（最简单，最自然）
   - 三个轮换（嗯 / 这个嘛 / 唔…，更有变化但需要随机选择逻辑）

2. **愿意改固件吗？**
   - 只改服务端（方案 B）：约 100ms 反馈，零固件风险
   - 服务端 + 固件（A+B）：真 0 延迟，但需重烧且占用 0.5MB 余量中的一部分

3. **填充音长度取多少？**
   - 1.8 秒（覆盖大多数情况，但 LLM 很快时会显得啰嗦）
   - 2.5 秒（覆盖更充分，但需支持中断）
   - 动态：按上一轮实测延迟自动选长短（最理想，但要维护统计）
