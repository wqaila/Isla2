## 一、播放中止：TTS 分块超出协议上限

### 现象

板子播到一半中止，`/api/devices` 记录：

```
turn xxx-t1  09:14:54
  tts_failed: TTS 流式分块长度异常：声明 130560 字节，
              超过上限 98304（协议规定单块 ≤ 48KB）
  bad_message: 当前状态 idle 不是播放中
```

### 根因

zjy13 引擎按「句」yield PCM，一整句可达 195840 字节（约 4 秒音频），
直接加长度前缀下发，远超协议上限 48KB。

客户端 `_iter_length_prefixed` 有上限校验（96KB），超限直接抛错 →
TTS 流判失败 → 播放状态未建立 → 后续音频块被拒 → **播放中止**。

### 修复

`tts_server_wsl.py` 新增 `MAX_STREAM_CHUNK_BYTES = 48 * 1024`，发送前切片：

```python
for offset in range(0, len(pcm), MAX_STREAM_CHUNK_BYTES):
    piece = pcm[offset:offset + MAX_STREAM_CHUNK_BYTES]
    yield struct.pack(">I", len(piece)) + piece
```

### 验证

| 项 | 修复前 | 修复后 |
|---|---|---|
| 块数 | 10 块 | 20 块 |
| 最大块 | ❌ 192000 字节 | ✅ 49152 字节 |
| 字节完整性 | — | ✅ 拼接后与原始一致 |

覆盖 9 组边界尺寸（含原始报错的 130560 / 195840），全部通过。

## 二、播放卡顿：分块间隔 + 预发量不足

### 现象

一次真实对话的日志：

```
音频已下发: 107 帧, 393600 字节, 音频=8.20s
板子 playback_ms = 10834ms        ← 播放花了 10.83 秒
```

**音频只有 8.20 秒，播放却用了 10.83 秒，多出 2.6 秒中断。**

### 根因（两层）

**第一层：分块间隔过大**

实测分块到达时刻：

```
第1块 1.63s  (1.02s 音频)
第2块 3.10s  ← 间隔 1.47s，且只有 0.14s 音频
第3块 3.10s  (1.02s)
第4块 5.95s  ← 间隔 2.85s
```

上游 `token_hop_len` 从 25 按 ×2 增长到 `token_max_hop_len`（默认 **100**）。
包越大，单次推理越久，间隔越大。

**第二层：预发量不足**

服务端 `lead_sec = 0.8`，只肯领先播放 0.8 秒发送。
TTS 一停顿 2.85 秒，板子 0.8 秒后就饿死了。

### 修复

**① 限制包上限**（`tts_server_wsl.py`）：

```python
model.model.token_max_hop_len = 50   # 原来默认 100
```

实测对比：

| max_hop | 最大间隔 | 饥饿时长 | RTF |
|---|---|---|---|
| 100（原） | 2.85s | 1.60s | 0.80 |
| **50（新）** | **1.69s** | **0.47s** | **0.94** |
| 25 | 1.17s | 1.15s | 1.13 ❌ |

**不要降到 25**：RTF 升到 1.13，合成跟不上播放，饥饿反而恶化。

**② 提高预发量**（`server.py`）：

```python
lead_sec = 0.8 → 2.0
```

上限受固件 `PLAY_MAX_SECONDS = 8s` 约束，不能无限调大。

### 验证

分块最大间隔 **2.85s → 1.76s（改善 38%）**，饥饿时长 **1.60s → 0.47s（改善 71%）**。

## 三、声音变尖：I2S 时钟被录音采样率污染

### 现象

用户反馈：「用久了之后板子播放出来的声音不对，会变尖」，
补充说明「**明显变快，像快进**」「**重启后恢复正常**」。

### 根因

数学验证：`24000 / 16000 = 1.5`，正好是「快进」的倍率。

机制：

1. 录音用 **ES7210 @ 16kHz**，播放用 **ES8311 @ 24kHz**，是两个独立 codec 句柄
2. 但两者**共用同一条 I2S 总线**，I2S 时钟**全局只有一个**
3. `esp_codec_dev_open()` 开头有早退（`esp_codec_dev.c:153`）：

```c
if (dev->input_opened || dev->output_opened) {
    return ESP_CODEC_DEV_OK;   // ← 直接返回，set_fmt 不被调用
}
```

一旦 `s_spk` 的 `output_opened` 残留为 true，本次 open 就**跳过 `set_fmt`**，
I2S 时钟仍停在录音的 16kHz。此时播放 24kHz 音频 → **1.5 倍速、音调变尖**。

4. 第二条路径（`audio_codec_data_i2s.c:517`）：麦克风还在录音时，
   扬声器的 disable 被推迟（`out_disable_pending`），但
   `esp_codec_dev_close()` 仍无条件把 `output_opened` 置 false →
   **句柄认为已关，硬件其实还开着**。

### 修复

`voice_client.c` 的 `handle_playback_start` 加两道保险：

```c
/* ① 先 close 一次，清掉残留的 output_opened，保证 open 不早退 */
esp_codec_dev_close(s_spk);
if (esp_codec_dev_open(s_spk, &fs) != ESP_OK) { ... }

/* ② 兜底：直接对共享 I2S 数据接口再设一次格式，强制拉回 24kHz */
const audio_codec_data_if_t *data_if = bsp_audio_get_codec_itf();
if (data_if && data_if->set_fmt) {
    data_if->set_fmt(data_if, ESP_CODEC_DEV_TYPE_OUT, &fs);
}
```

### 验证

- 采样率日志 8 轮全部 `TTS=24000Hz 设备=24000Hz`，**始终一致**
- ES8311 分频表确认含 `{6144000, 24000}`（MCLK_DIV=256）

## 四、填充音与正文之间的空档

### 现象

用户反馈：「填充音和要播放的正文音频之间感觉有点长了，听起来不太自然」。

### 根因

填充音在**松手瞬间**就开始播，而它只有约 0.7 秒：

- TTS 首块 1.5s 才到 → 填充音早已播完，中间留约 0.8s 死寂
- TTS 更快时 → 填充音播到一半被正文顶掉，像被硬生生掐断

### 修复

`server.py` 新增 `FILLER_DELAY_S = 0.5`，在发送循环前先静默一段：

```python
if FILLER_DELAY_S > 0:
    await self._wait_filler_played(
        FILLER_DELAY_S, body_ready=body_ready, cancel=cancel
    )
    if body_ready.is_set() or cancel.is_set():
        return 0, 0, 0   # 正文提前到，连填充音都不发
```

关键：复用 `_wait_filler_played` 的**可打断等待**，不是 `asyncio.sleep` 死等。
正文提前就绪时连一个填充音都不发。

### 验证

- 填充音专项测试 28 passed（含新增 3 项延迟测试）
- 完整套件 **531 passed**，零回归

## 五、松手就断连：任务栈溢出

### 现象

用户反馈：「在松开屏幕后板子就断开重连了」。

### 根因

**代码注释和实际参数不一致**：

```c
/* 4096 字节栈不足以承载 esp_websocket_client_send_bin 的调用链，
 * 实测会在 record_loop 返回时（retw.n）因栈窗口损坏触发 IllegalInstruction。
 * 与同工程其他任务对齐，加大到 8192。 */          ← 注释说要 8192
xTaskCreate(record_loop, "voice_rec", 4096, NULL, 5, &s_task);
                                     ^^^^ 实际还是 4096
```

松手 → `voice_talk_stop` → `record_loop` 退出循环 → 执行收尾
（`esp_codec_dev_close` + `send_text` 发 `recording_stop`）→
**4096 栈溢出，破坏栈窗口** → 任务崩溃 → WebSocket 连接被底层关闭。

### 修复

三处任务栈统一为 8192（**注释全都写着 8192，实际全是 4096**，同一疏漏）：

| 任务 | 修复前 | 修复后 |
|---|---|---|
| `record_loop`（录音） | 4096 | **8192** |
| `play_task`（播放） | 4096 | **8192** |
| WS 客户端 `task_stack` | 4096 | **8192** |

### 验证

连接存活时长：

```
16:23:17  开始录音 → 16:23:20  连接关闭   仅 3 秒  ← 旧固件
16:23:30  开始录音 → 16:23:35  连接关闭   仅 5 秒  ← 旧固件
16:26:37  连接建立 → 至今 80 秒+ 稳定              ← 新固件
```

DEBUG 日志 42 秒内 PING/PONG 全程正常，**零断连**。

## 六、卡在正在回应：播放任务饿死心跳

### 现象

用户反馈：「又卡在正在回应，还是没有声音」。

现场数据：

| 位置 | 状态 |
|---|---|
| 服务端 | `active=0` — 板子已断开 |
| 板子 `BADGE_VOICE` | `state=PLAYING`，已收 **126 帧 / 497744 字节** |
| 板子 `BADGE_STATUS` | `playing=false` — 音频早已播完 |

服务端日志：

```
16:28:56  音频已下发：126 帧 / 464640 字节 / 9.68s（等待 playback_done）
16:29:15  心跳超时 session=xxx 已 36s 无消息，断开连接
```

**板子收了完整音频，但 19 秒内没发任何消息（含心跳），被服务端断开。**

### 根因

`play_task` 优先级 **6（全工程最高）**，而心跳任务只有 **3（最低）**：

```c
if (avail > 0 && s_spk) {
    esp_codec_dev_write(s_spk, out_buf, (int)(avail * 2));
    continue;      // ← 有数据就立即 continue，一次都不让出 CPU
}
```

只要缓冲里有数据，这个任务就长时间霸占 CPU，把心跳任务饿死。

**第二层问题**：断连时状态清理不完整。

```c
case WEBSOCKET_EVENT_DISCONNECTED:
    s_connected = false;
    s_playing = false;
    s_state = ST_CONNECTING;      // ← 直接改状态，但没清挂起标志
```

导致 `s_play_draining` / `s_got_end_marker` 残留，
且收尾兜底判断的是 `s_state == ST_PLAYING`，而这里已改成 `ST_CONNECTING`
—— **兜底永远不触发**。

### 修复

**① `play_task` 写完让出 CPU**

```c
esp_codec_dev_write(...);
vTaskDelay(1);    // 1 tick = 10ms，远小于一次写入的 42ms 音频
continue;
```

**② 断连时彻底清理挂起状态**

```c
case WEBSOCKET_EVENT_DISCONNECTED:
    s_play_draining = false;
    s_got_end_marker = false;
    s_end_grace_ticks = 0;
    s_talk_requested = false;
    // 清空播放缓冲、关闭 codec
```

**③ 心跳任务优先级 3 → 5，并记录发送结果**

```c
const esp_err_t hb_ret = send_text(buf);
if (hb_ret != ESP_OK) {
    ESP_LOGW(TAG, "心跳发送失败 ret=%d connected=%d state=%d", ...);
}
```

### 附加修复：强制收尾兜底

新增 `finish_playback_force()`，**不看 `s_playing`**，只看 `s_state`：

```c
static void finish_playback_force(void)
{
    // 不做 if (!s_playing) return; 检查
    s_playing = false;
    s_play_draining = false;
    // 静音淡出 → close codec → 发 playback_done → 复位 s_state
}
```

兜底条件改为基于状态机（3 秒）：

```c
if (s_got_end_marker && s_state == ST_PLAYING) {
    if (s_end_grace_ticks++ >= 300) {
        finish_playback_force();
    }
}
```

## 七、WiFi 反复掉线与重连风暴

### 现象

```
W badge_net: Wi-Fi disconnected, reason 201   ← NO_AP_FOUND
心跳超时 4 次（33s / 36s / 30s / 32s 无消息）
```

### 根因

`badge_network.c` 断线后**无条件立即 `esp_wifi_connect()`**。
`reason 201`（NO_AP_FOUND，热点暂时不可见）时，立即重连会形成重试风暴：
扫描→失败→立刻再扫，射频长期忙态，反而更难重新发现 AP，
同时挤占同芯片 WebSocket 的收发。

### 修复

改为指数退避（500ms 起、每次翻倍、上限 8s），连上后重置：

```c
uint32_t delay_ms = s_retry_delay_ms;
if (s_retry_delay_ms < 8000) {
    s_retry_delay_ms *= 2;
    if (s_retry_delay_ms > 8000) s_retry_delay_ms = 8000;
}
ESP_LOGI(TAG, "Wi-Fi 将在 %ums 后重连（下次退避 %ums）", ...);
vTaskDelay(pdMS_TO_TICKS(delay_ms));
esp_wifi_connect();
```

### 验证

串口确认新日志出现：`Wi-Fi 将在 8000ms 后重连（下次退避 8000ms）`

## 八、网络方案变更：放弃移动热点

### 背景

排查中板子持续报 `reason 201`（NO_AP_FOUND），但热点配置经
WinRT `NetworkOperatorTetheringManager` 确认**完全正确**：

```
SSID        : Isla2Badge
Passphrase  : <已脱敏>
Band        : TwoPointFourGigahertz
AuthKind    : Wpa2
State       : On
```

### 真正根因：单射频网卡限制

```
netsh wlan show drivers → "Hosted network supported: No"
```

**Realtek 8851BU 是单射频 USB 网卡**，同时要做两件事：

| 职责 | 需求 |
|---|---|
| 保持上游 WiFi（信道 5） | 射频停在信道 5 |
| 广播移动热点 | 周期性离信道维持 beacon |

实测 30 秒：**3 次 reason 201、0 次成功连接**。
板子若在离信道窗口扫描，就收不到 beacon。

### 方案

板子**直连上游路由器**，与 PC 同网段，不再依赖单射频虚拟 AP。

`wifi_config.h`：

```c
#define BADGE_WIFI_SSID "没实力了吧2"
#define BADGE_WIFI_PASSWORD "<见本机 wifi_config.h，不入库>"
#define BADGE_VOICE_AUTOCONNECT_HOST "192.168.43.164"   // PC 在路由器网段的 IP
```

> `wifi_config.h` 已在 `.gitignore` 中（属凭据文件），密码不写入任何入库文档。

### 验证

```
板子 IP: 192.168.43.252
PC  IP: 192.168.43.164
同网段: ✅
WebSocket: ✅ hello=True，心跳正常，连接稳定 80s+
```

> ⚠️ **注意**：`192.168.43.164` 是 DHCP 分配，**可能变化**。
> 板子连不上服务端时，先查 PC 当前 IP，变了就改这里并重烧。
> 想一劳永逸可在路由器上给 PC 绑定静态 IP。

## 九、zjy14 引擎：流式分块同样超限

### 发现过程

在「全面体检」zjy14 时，24 项检查中发现流式接口异常：

```
文本 70 字 → 10 块，总 710400 字节
最大块 = 192000 字节  ← 超过 48KB 上限 4 倍
```

### 根因

`server/routes/synthesis.py:386` 绕过协议封装，直接拼长度前缀：

```python
yield struct.pack(">I", len(chunk.pcm)) + chunk.pcm
```

引擎按「句」产出，一整句 192000 字节原样下发。
**与 zjy13 是同一个坑**，但 zjy14 侧未同步修复。

### 修复

统一走 `encode_length_prefixed()`，并让该函数本身按上限切块：

```python
def encode_length_prefixed(pcm: bytes, *, max_chunk_bytes=MAX_AUDIO_CHUNK_BYTES):
    if len(pcm) <= max_chunk_bytes:
        return struct.pack(">I", len(pcm)) + pcm
    parts = []
    for off in range(0, len(pcm), max_chunk_bytes):
        piece = pcm[off:off + max_chunk_bytes]
        parts.append(struct.pack(">I", len(piece)) + piece)
    return b"".join(parts)
```

### 验证

| 项 | 修复前 | 修复后 |
|---|---|---|
| 最大块 | ❌ 192000 字节 | ✅ 49152 字节 |
| 测试套件 | 477 passed / **2 failed** | **483 passed / 0 failed** |
| 接口体检 | 21/24 | **24/24** |

新增 4 项回归测试：超限必须切块、不超限不拆、块长必须偶数、非法上限必须报错。

## 十、测试断言缺陷（跨仓库字面量匹配过脆）

assert re.search(r'struct\.pack\(\s*">I"\s*,\s*len\(\w+\)\s*\)\s*\+\s*\w+', src)

## 十一、踩坑复盘：我犯的两次错误

> 记录在这里，目的是下次不重犯。这两次都导致用户额外等待。

### 错误 1：误判移动热点 SSID

**我做了什么**：看到 `netsh wlan show networks` 扫不到 `Isla2Badge`，
就断定热点改了名，把固件 SSID 改成扫描到的 `没实力了吧2`。

**实际事实**：

1. **`netsh wlan show networks` 不会列出本机自己开的移动热点**。
   扫描不到 `Isla2Badge` 完全正常。
2. `没实力了吧2` 是 PC 连接的**上游路由器**，不是热点。
   改过去后板子报 `reason 15`（四次握手超时 = 密码错）才反证了这一点。

**正确做法**：用 WinRT `NetworkOperatorTetheringManager.GetCurrentAccessPointConfiguration()`
读热点的权威配置，而不是靠扫描列表推断。

**教训**：诊断网络问题时，**不要用「看不到」推断「不存在」**。

### 错误 2：修复条件写错，导致兜底不生效

**我做了什么**：为修「卡在 PLAYING」加了兜底：

```c
if (s_got_end_marker && s_playing) {   // ← 依赖 s_playing
    finish_playback_force();
}
```

**为什么错**：`finish_playback()` 首行就是 `if (!s_playing) return;`。
而卡死场景下 `s_playing` **已经是 false**（播放任务已退出），
`s_state` 才是卡住的 `ST_PLAYING`。

所以我依赖 `s_playing` 的兜底**永远不会触发**，白等了一轮。

**正确做法**：判断依据应是 `s_state`（对外状态机），不是 `s_playing`（播放任务标志）。

**教训**：加兜底时，**必须确认兜底条件的变量在故障场景下的真实取值**，
不能假设它和非故障时一样。
