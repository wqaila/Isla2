## 一、阶段一：静态审计（11 个缺陷）

审计覆盖 `zjy13` 服务端、板上实际运行的 `yuanma/AI-Pet-Badge-main` 固件、
以及 `zjy13/firmware` 自带精简固件。

### 1.1 三个致命缺陷

| # | 位置 | 缺陷 |
|:-:|---|---|
| 1 | `voice_client.c:624` | 预缓冲门的 `continue` 跳过了后面**全部**收尾兜底 → 两段看门狗是死代码 |
| 2 | `voice_client.c:819` | 结束标记帧被 `turn_short` 校验**连坐丢弃** |
| 3 | `server.py:1141` | 填充音期间回报 `playback_done` 被回 error → 板子复位 → 正文 PCM 全丢 |

### 1.2 缺陷 1 的机制（本次最隐蔽的一条）

```c
while (true) {
    if (!s_prebuf_done) {
        if (avail < prebuf_need && !s_play_draining) {
            vTaskDelay(5);
            continue;              // ← 从这行往后，全部被跳过
        }
        s_prebuf_done = true;
    }
    ...
    s_prebuf_done = false;         // ← 让下一轮又回到门口
    if (s_got_end_marker && ...) { /* 3 秒兜底 */ }
    if (s_playing && ...)        { /* 12 秒兜底 */ }
}
```

只要「收到 `playback_start`、但音频凑不够 120ms 预缓冲、且等不到结束标记」，
`continue` 就**永久成立**；即使偶有数据进来，`s_prebuf_done = false`
也会让下一轮重新落回门口，两个计数器每段最多 +1，永远到不了阈值。

**结论：这两段兜底在「彻底断流」场景下是死代码，不是「可能不触发」。**

后果链：卡在 `ST_PLAYING` → 屏幕「正在回应」→ 无音频写入 → 完全没声音
→ `voice_talk_start` 因 `ST_PLAYING` 永久拒绝长按 → 只能断电重启。

### 1.3 缺陷 3 的完整链路（需同时读服务端与固件）

```
1. 服务端 _start_playback_session(reason="filler") → FILLER，发 playback_start
2. 板子 handle_playback_start → s_playing=true, s_state=ST_PLAYING
3. 板子播完填充音（约 0.7s）→ finish_playback() → 发 playback_done
4. 服务端此时已在 ASR/LLM/TTS_PROCESSING（FILLER 只存活一个 await）
   → _on_playback_done 判 state != PLAYING → 回 error
5. 板子收到 error → 固件把任何 error 当无条件复位 → s_playing=false
6. 正文首块到达，服务端走「填充音已开会话」分支：不再发 playback_start
7. 板子 handle_binary：if (s_playing && s_play_buf) → s_playing 已 false
   → 正文 PCM 全部丢弃
8. 用户听到：只有「嗯…」，然后彻底无声
```

### 1.4 其余 8 个

异常路径从不补发结束标记帧、`RECORDING` 是唯一没有任何超时的 BUSY 状态、
`esp_codec_dev_write` 返回值被丢弃、`finish_playback()` 首行
`if (!s_playing) return;`、播放看门狗恒为 135 秒（`PLAYBACK_GRACE_S` 成了死常量）、
心跳余量仅 10 秒、`_record_latency` 全仓库无调用点、
精简固件完全不识别结束标记帧。

## 二、阶段二：上板实测（11 个修复有效，但没声音）

### 2.1 先解决「连不上」

用户插上板子后报「并没有连接服务」。排查发现是**三个问题叠加**：

| 现象 | 实情 |
|---|---|
| 板子报 `reason 201`（NO_AP_FOUND） | 当时 PC 的 WLAN 处于断开态（射频报 powered down） |
| 板子反复重连 `192.168.43.164:8765` | 该 IP 是 WLAN 的残留地址，服务端根本没启动 |
| 8765 / 50000 无监听 | TTS 与 WS 服务都没起 |

依次恢复：WLAN 连上 `没实力了吧2`（IP 恰好是固件里配的 `192.168.43.164`）
→ 启动 WSL 的 CosyVoice3（cuda，9.16s 加载）→ 启动 WS 服务端。
板子随即自动连上（`192.168.43.252`，`hello=True`，心跳正常）。

> 附带发现：`logs/board_serial_live.log` 里全是 `reason 201` 与
> `Host is unreachable`，**没有一轮成功播放**。所以这个仓库里
> 没有任何历史日志能证实缺陷 1/2 的实际发生次数 ——
> 阶段一的结论全部来自代码路径推演。

### 2.2 烧录第一版修复后：状态机通了，声音还是没有

| 指标 | 结果 |
|---|---|
| 状态序列 | `recording → llm_processing → tts_processing → playing → idle` ✅ |
| `playback_ms` | **`None`** ❌ 板子从未回报 `playback_done` |
| 收尾方式 | `播放看门狗触发 20s 内未收到 playback_done` ❌ |
| 本轮耗时 | 30 ~ 34 秒（看门狗兜底） |

**修复确实生效了**：看门狗从 135 秒收敛到 20 秒（缺陷 8 的修复），
异常路径补发结束标记也让板子能收尾了。但**声音依然完全没有**。

## 三、阶段三：串口取证，找到真根因（缺陷 12）

### 3.1 决定性证据

这次串口里出现了阶段一新增的诊断日志（修复前它不存在）：

```
E (343373) i2s_common: i2s_channel_write(1361): The channel is not enabled
W (343373) voice: 写 codec 失败 ret=-1（已连续 1 次，state=4 avail=1024）
W (353383) voice: 写 codec 失败 ret=-1（已连续 11 次，state=4 avail=1024）
```

再看 `playback_start` 附近的 I2S 时序：

```
i2s tx channel enabled      ← open() 使能了 TX
Open codec device OK
i2s tx channel disabled     ← set_fmt 把它关掉，之后没人再开
```

### 3.2 根因：两个修复互相冲突

`esp_codec_dev` 的 `_i2s_data_set_fmt()` 内部会先**关掉**通道：

```c
// audio_codec_data_i2s.c:594-599
if (dev_type & ESP_CODEC_DEV_TYPE_OUT) {
    _i2s_drv_enable(i2s_data, true, false);   // 关 TX，函数内不再使能
}
```

它设计给 `open()` 流程内部用 —— `open()` 调完 `set_fmt` 会紧接着 `enable`。

而 2026-11-23 为修「声音变尖」在 `handle_playback_start` 里
**open 之后**又调了一次 `set_fmt` 作为兜底：

```c
esp_codec_dev_close(s_spk);
esp_codec_dev_open(s_spk, &fs);                            // ← TX 被使能
data_if->set_fmt(data_if, ESP_CODEC_DEV_TYPE_OUT, &fs);    // ← TX 被关掉，没人再开
```

于是时钟确实被拉回 24kHz 了（「声音变尖」修好了），
但通道也死了（「完全没声音」）。**单看任何一处代码都正确。**

### 3.3 修复

```c
data_if->set_fmt(data_if, ESP_CODEC_DEV_TYPE_OUT, &fs);
if (data_if->enable) {
    data_if->enable(data_if, ESP_CODEC_DEV_TYPE_OUT, true);   // ← 补回使能
}
```

### 3.4 附带：我自己引入的死循环

第一版写失败处理漏了「丢弃已取出的数据」，导致：

```
写失败 → avail>0 分支末尾 continue → 下一轮又取同一块 → 又失败 → ...
→ 计数到 50 → 强制收尾（清零计数）→ 但缓冲仍有数据 → 再失败 → 再 50 次 → ...
```

实测串口每秒数十行，状态在 `ST_IDLE`/`ST_PLAYING` 间反复横跳。修复两处：

1. 写失败后**丢弃该块并让出 CPU**，不重试同一块；
2. `avail > 0` 分支增加 `s_state == ST_PLAYING` 条件 ——
   强制收尾（已 `close`）后不再尝试写 codec。

## 五、教训

### 5.1 静态审计有明确的能力边界

缺陷 12 是「**两个各自正确的修复互相冲突**」。任何只读代码的审计
都不会把它列为缺陷 —— 每一处单独看都符合设计意图。
只有把固件跑起来、看 I2S 时序日志，冲突才会显形。

**所以**：报告里写「已修复」时，必须区分
「静态推断正确」与「真机验证通过」。本次阶段一的报告把 11 项
都标了 ✅，但其中 0 项解释了「没声音」。

### 5.2 诊断日志本身就是生产力

缺陷 12 之所以能定位，是因为阶段一在 `play_task` 里加了
`写 codec 失败 ret=%d` 这一行。修复前这个故障**完全无痕** ——
状态机在播放、缓冲在消耗、就是没声音，串口一个字都没有。

### 5.3 加诊断代码要防止引入新缺陷

我加的第一版写失败处理直接造出一个死循环（写失败 → 不清缓冲 → 无限重试），
把串口刷爆、状态反复横跳。**任何「新增分支 + continue」的改动，
都要检查循环不变量是否被破坏。**

### 5.4 变量语义必须逐处确认

`PLAYBACK_GRACE_S` / `PLAYBACK_MIN_TIMEOUT_S` 这两个常量
定义了却从未生效（三处调用都传 `PLAYBACK_MAX_GUESS_S=120`）。
`_record_latency` 有定义、有测试，但**全仓库无调用点**。
「有定义、有测试」不等于「真的在用」。

## 八、与 4.12.1 的关系（重要）

4.12.1（2026-11-23）把「卡在正在回应、无声音」记为**问题 7**，
归因为「`play_task` 霸占 CPU，心跳被饿死」，修法是 `vTaskDelay(1)` + 心跳提优先级。

本次体检证明：**那个归因不完整。**

| 4.12.1 的判断 | 本次实测 |
|---|---|
| `play_task` 饿死心跳 → 服务端 36s 断连 | 真实存在，但只解释「断连」，不解释「没声音」 |
| 加 `finish_playback_force()` 兜底 | 兜底**写在预缓冲门之后**，在断流场景下是死代码（缺陷 1） |
| `set_fmt` 兜底修「声音变尖」 | 副作用是把 I2S TX 关掉 → **完全没声音**（缺陷 12） |

也就是说：4.12.1 的两个修复**互相抵消** ——
一个让状态机能收尾，另一个让声音出不来。
这也解释了为什么用户当时反馈「还是不行」。
